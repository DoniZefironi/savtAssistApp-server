## Работа с Docker

Конфигурация разделена на прод и dev:

- `docker-compose.yml` — **продакшн**: без hot-reload, код внутри образа, nginx с HTTPS (`nginx.conf`).
- `docker-compose.dev.yml` — **локальная разработка**: `--reload`, монтирование кода, nginx без TLS (`nginx.dev.conf`).

```bash
# ЛОКАЛЬНАЯ РАЗРАБОТКА — сборка и запуск
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d --build

# ПРОД (на сервере) — сборка и запуск
docker compose up -d --build

# Миграции
docker exec savt-backend-api-1 alembic upgrade head

# Создание новой миграции (после изменения моделей)
docker exec savt-backend-api-1 alembic revision --autogenerate -m "описание"

# Логи
docker compose logs api --tail=20

# Подключение к БД
docker exec -it savt-backend-db-1 psql -U postgres -d savt
# \dt — все таблицы
# \d <таблица> — структура таблицы
# \q — выход
```

> После изменения кода на проде нужен пересбор: `docker compose up -d --build` (код копируется в образ, а не монтируется).

## Развёртывание и HTTPS (прод)

Прод-nginx (`nginx.conf`) принимает только HTTPS: порт 80 отдаёт ACME-челленджи и редиректит на 443. Без сертификата контейнер nginx **не стартует** — поэтому порядок первого развёртывания такой:

Какой конфиг nginx использовать, задаётся переменной `NGINX_CONF` в `.env` (по умолчанию `nginx.conf`):

| Конфиг | Когда использовать |
|---|---|
| `nginx.conf` (умолч.) | Прод: 443 с TLS, порт 80 — только редирект и ACME |
| `nginx.http-fallback.conf` | Переходный: порт 443 снаружи ещё не проброшен — API работает и по 80, и по 443 |
| `nginx.dev.conf` | Локальная разработка (подключается автоматически через `docker-compose.dev.yml`) |

Переходный режим (пока сеть/роутер не пробрасывает 443):

```bash
echo "NGINX_CONF=nginx.http-fallback.conf" >> .env
docker compose up -d nginx
```

После проброса 443 вернуть строгий режим: удалить строку `NGINX_CONF` из `.env` и снова `docker compose up -d nginx`.

### 1. Подготовка

```bash
# В .env выставить боевые секреты:
#   JWT_SECRET_KEY  — минимум 64 случайных символа
#   POSTGRES_PASSWORD — длинный случайный пароль
#   STATIC_LINK_SECRET — секрет подписи ссылок на файлы (обязателен!)
openssl rand -hex 48   # генератор секретов
```

> **`STATIC_LINK_SECRET` обязателен.** nginx проверяет подпись ссылок на `/static/`
> (`secure_link`), и при пустом секрете **все файлы будут отдавать `403`** — фото,
> вложения чата, документы. Значение подставляется в оба сервиса из одного места в
> `.env` (см. `environment:` у `nginx` в `docker-compose.yml`), так что разъехаться
> они не могут. Подробности — в разделе «Подписанные ссылки на файлы».
>
> Конфиг nginx монтируется **как шаблон** (`/etc/nginx/templates/nginx.conf.template`),
> из которого штатный энтрипойнт образа собирает итоговый `/etc/nginx/nginx.conf` с
> подставленным секретом. Поэтому после обновления нужен пересоздающий `docker compose up -d`,
> а не только `nginx -s reload`. Проверить, что секрет подставился:
> ```bash
> docker exec savt-backend-nginx-1 grep secure_link_md5 /etc/nginx/nginx.conf
> ```

> Если меняете `POSTGRES_PASSWORD` на уже работающей БД, одного .env мало — пароль хранится в самой БД:
> ```bash
> docker exec -it savt-backend-db-1 psql -U postgres -c "ALTER USER postgres PASSWORD 'новый_пароль';"
> # затем обновить POSTGRES_PASSWORD и DATABASE_URL в .env и перезапустить api
> ```

### 2. Получить сертификат (первый раз — standalone, порт 80 должен быть свободен)

```bash
sudo apt install certbot            # если ещё не установлен
docker compose stop nginx           # освободить порт 80
sudo certbot certonly --standalone -d helper.savt.by
mkdir -p certbot-www                # webroot для последующих продлений
docker compose up -d                # nginx стартует уже с сертификатом
```

### 3. Автопродление сертификата

`crontab -e`, добавить:

```
0 4 * * 1 certbot renew --webroot -w /path/to/savt-backend/certbot-www --deploy-hook "docker exec savt-backend-nginx-1 nginx -s reload" >> /var/log/certbot-renew.log 2>&1
```

### 4. Проверка

```bash
curl -I http://helper.savt.by/health    # → 301 на https (в переходном режиме — 200)
curl https://helper.savt.by/health      # → {"app":"ok","db":true}
```

## Вебхуки внешних интеграций

Эти эндпоинты не вызываются фронтендом — их дёргают внешние сервисы (Bitrix24, Telegram). Настройка — на стороне соответствующего сервиса, не в коде.

### POST `/webhooks/bitrix/task-comment`
Исходящий вебхук Bitrix24 на событие `ONTASKCOMMENTADD` (добавление комментария к задаче). Пересылает в чат заявки в приложении только комментарии, начинающиеся с префикса `_FORWARD_PREFIX` (см. `app/services/bitrix_webhook_service.py`, сейчас `/sa`) — остальная переписка в задаче остаётся только в Bitrix. Сам вебхук несёт только `data[FIELDS_AFTER][TASK_ID]`/`[MESSAGE_ID]` (без текста и без автора).

> **Новая карточка задачи Bitrix**: комментарии физически хранятся в чате (IM-модуль), а не в классической ленте комментариев. Методы `task.commentitem.get`/`task.commentitem.add` в этой конфигурации не работают (стабильно возвращают `ITEM_NOT_FOUND_OR_NOT_ACCESSIBLE`). Текст сообщения дотягивается через `tasks.task.get` (получить `chatId`) → `im.dialog.messages.get` (получить сообщение по ID из `MESSAGE_ID`), см. `bitrix_service.get_task_chat_id`/`get_dialog_message`. Префикс тоже стоит выбирать так, чтобы он не совпадал со слэш-командами/упоминаниями чата (например, `/all` — команда «уведомить всех» — не долетает до вебхука как обычный текст).

Настройка в Bitrix24: Приложения → Разработчикам → Другое → **Исходящий вебхук** → событие "Добавление комментария к задаче" → обработчик `https://<домен>/webhooks/bitrix/task-comment` → полученный `application_token` добавить в `BITRIX_INCOMING_WEBHOOK_TOKENS` (через запятую, если там уже есть токен от другого правила — например, от вебхука сделок ниже). Дополнительно у **входящего** вебхука (`BITRIX_WEBHOOK_URL`) нужна область **«Чат и звонки» / IM** — без неё `im.dialog.messages.get` вернёт `401 insufficient_scope`.

Пересланное сообщение в чате приложения отображается от лица «Ася» (см. `bitrix_service._INCOMING_USER_NAME`) — визуально как ответ бота, но сам текст сообщения явно начинается с «Ответ от оператора {имя}:», чтобы не создавалось впечатление, будто это настоящий ИИ-ответ.

Обратное направление уже работает всегда: сообщения из чата заявки в приложении (от заявителя **и** от оператора/админа/суперадмина) дублируются в чат Bitrix-задачи через `tasks.task.chat.message.send` (актуальная замена устаревшего `task.commentitem.add`) — это не требует отдельной настройки, работает через уже существующий `BITRIX_WEBHOOK_URL`.

### POST `/webhooks/bitrix/deal`
Исходящий вебхук Bitrix24 на события `ONCRMDEALADD` и `ONCRMDEALUPDATE` — один и тот же обработчик на оба (`handle_deal_event` → `upsert_project_from_deal`). Событие несёт только `ID` сделки, сама сделка дотягивается отдельным запросом (`crm.deal.get`). Это единственный способ завести или изменить проект — **ручного создания и переименования в приложении нет** (см. «Рут `admin: projects`»).

Настройка в Bitrix24: Приложения → Разработчикам → Другое → **Исходящий вебхук** → события "Сделка добавлена" (`ONCRMDEALADD`) и "Сделка изменена" (`ONCRMDEALUPDATE`) → обработчик `https://<домен>/webhooks/bitrix/deal` → полученный `application_token` добавить в `BITRIX_INCOMING_WEBHOOK_TOKENS`. У **входящего** вебхука (`BITRIX_WEBHOOK_URL`) нужна область **CRM**.

> **Событие удаления сделки (`ONCRMDEALDELETE`) не обрабатывается вообще.** Удаление сделки в Bitrix никак не влияет на проект в приложении — он останется в последнем синхронизированном виде. Единственный способ убрать проект — `DELETE /admin/projects/{id}` в самом приложении, и то не навсегда: `production_number` уникален в БД, и если по этой же сделке позже прилетит `ONCRMDEALUPDATE`, мягко удалённый проект **воскресает** автоматически (`deleted_at` снимается) вместо попытки создать дубль — см. подробности в «Рут `admin: projects`».

### Поля сделки в карточке проекта

Из карточки сделки CRM в проект приезжают: **номер в производство**, **планируемая
и фактическая даты отгрузки**, **компания-заказчик** и **контактные лица**.
Обновляются на каждом `ONCRMDEALADD`/`ONCRMDEALUPDATE`, поэтому в админке доступны
**только для чтения** — правки всё равно затрутся при следующем изменении сделки.

Файлы («Документация», «Счёт/договор») из сделки **не импортируются**: на портале
эти поля не заполняются. Внутренние документы загружаются в приложение вручную —
см. `is_internal` в разделе `admin: documents`.

**Гарантия — исключение: её в CRM нет**, даты ставит администратор через
`PATCH /admin/projects/{id}`. По `warranty_ends_at` проекта решается, попадёт ли он
в ночную синхронизацию папок на NAS: если она задана — решает она, если нет —
как раньше, крайняя дата среди гарантий ШУ проекта, а если нет и того —
синхронизируем (не блокируем свежий проект).

**Контактные лица видны только операторам и админам.** В пользовательских ответах
(`GET /projects`, `GET /projects/{id}`) их нет: это персональные данные сотрудников
заказчика, а доступ к проекту выдаётся по QR-коду. Компанию и даты пользователь видит.

Набор контактов синхронизируется с заменой — убранный из сделки контакт удаляется
и у нас. Если Bitrix в этот момент недоступен, набор не трогается вовсе: иначе
разовый сетевой сбой стирал бы все контакты проекта.

#### Как найти коды пользовательских полей

Коды вида `UF_CRM_1730705809359` свои у каждого портала, поэтому задаются в `.env`,
а не в коде. Получить список:

```bash
cd savt-backend
WEBHOOK=$(grep -m1 '^BITRIX_WEBHOOK_URL=' .env | cut -d= -f2- | tr -d '"' | sed 's:/*$::')
curl -s "$WEBHOOK/crm.deal.fields.json" > /tmp/deal_fields.json
python3 - <<'PY'
import json
res = json.load(open('/tmp/deal_fields.json')).get('result') or {}
for k, v in sorted(res.items()):
    if k.startswith('UF_'):
        print(f"{k:30} {v.get('formLabel') or v.get('title') or ''} [{v.get('type')}]")
PY
```

> `BITRIX_FIELD_SHIPMENT_ACTUAL` принимает **несколько кодов через запятую** и берёт
> первое непустое. Это на случай, когда в портале живут два поля одновременно —
> старое и новое, — и часть сделок заполнена по-старому. Когда переезд завершится,
> лишний код убирается из строки.

#### Номер проекта: поле, потом название

Номер (`26_138`) берётся из `BITRIX_FIELD_PRODUCTION_NUMBER`, а если поле пустое —
как раньше, из начала названия сделки. Название правят руками, и опечатка в начале
раньше означала, что проект не создастся или не найдётся; выделенное поле надёжнее.

**Год больше не фиксирован.** Раньше принимался ровно один префикс, и сделки других
лет не импортировались вовсе. Теперь подходит любой двузначный год, а ограничить
список можно через `BITRIX_PRODUCTION_YEARS` — это стоит сделать **перед разовым
импортом**, иначе в базу приедут проекты за все годы, какие есть в портале.

### POST `/webhooks/bitrix/task-update`
Исходящий вебхук Bitrix24 на событие `ONTASKUPDATE` (любое изменение задачи, включая смену статуса). ID задачи несёт просто как `data[FIELDS_AFTER][ID]` (не `TASK_ID`, как в `ONTASKCOMMENTADD`) — само событие не говорит, какое именно поле изменилось, поэтому по срабатыванию просто перепроверяется текущий `STATUS` этой задачи (`tasks.task.list`) и применяется к заявке, если отличается от сохранённого. Даёт мгновенную синхронизацию статуса вместо ожидания планового опроса (см. ниже) — но сам опрос при этом никуда не делся и продолжает работать как подстраховка (например, если этот вебхук не настроен или Bitrix недоступен в момент события).

Настройка в Bitrix24: Приложения → Разработчикам → Другое → **Исходящий вебхук** → событие "Обновление задачи" (`ONTASKUPDATE`) → обработчик `https://<домен>/webhooks/bitrix/task-update` → полученный `application_token` добавить в `BITRIX_INCOMING_WEBHOOK_TOKENS` (через запятую вместе с остальными).

> Плановый опрос статусов задач (`sync_statuses_from_bitrix`, каждые 15 минут) продолжает работать независимо от этого вебхука — он и раньше был единственным механизмом синхронизации статуса из Bitrix, теперь просто подстраховывает вебхук.

### POST `/webhooks/telegram`
Вебхук Telegram Bot API — принимает `/start <token>` при открытии пользователем deep-link из `/auth/register/start` (и аналогичных эндпоинтов). Проверяется заголовком `X-Telegram-Bot-Api-Secret-Token` (сверяется с `TELEGRAM_WEBHOOK_SECRET`).

Настройка (разово, curl):
```bash
curl -X POST "https://api.telegram.org/bot<TELEGRAM_BOT_TOKEN>/setWebhook" \
  -H "Content-Type: application/json" \
  -d '{"url": "https://<домен>/webhooks/telegram", "secret_token": "<TELEGRAM_WEBHOOK_SECRET>"}'
```
Проверка: `curl "https://api.telegram.org/bot<TOKEN>/getWebhookInfo"` — смотреть на `last_error_message`.

> **Вебхук Viber удалён вместе с самим каналом.** Подтвердить владение номером
> через Viber нечем — аналога Telegram `request_contact` у него нет. Единственный
> канал доставки кода — Telegram.

> Точные имена полей во входящих payload'ах Telegram/Bitrix стоит свериться на реальном тесте — при неудачном парсинге сырой payload логируется, см. `app/services/*_webhook_service.py`.

# savtAssistApp — сервер мобильного приложения поддержки SAVT

API для управления пользователями, шкафами управления (ШУ), документацией, QR-кодами, чатами, сервисными заявками, уведомлениями, базой знаний и FAQ.

**Роли (иерархия от низшей к высшей):**
1. **Пользователь** (`user`) — добавляет ШУ, пользуется чатом поддержки, просматривает/запрашивает документацию, создаёт сервисные заявки.
2. **Оператор** (`operator`) — отвечает в чате, просматривает все данные. Создаётся через `POST /admin/users/operators` или CLI.
3. **Администратор** (`admin`) — полное управление данными, создаёт операторов. Создаётся суперадмином через API или CLI.
4. **Суперадмин** (`superadmin`) — управляет администраторами, имеет все права. Создаётся **только через CLI**.
5. **Бот** (`bot`) — системная роль для Аси, не отображается в списках пользователей.

> Иерархия: каждая роль выше автоматически имеет все права более низкой роли.

## 1. Авторизация

### Формат ошибок и лимиты запросов

Все ошибки API — единый JSON `{ "detail": "<текст для показа пользователю>" }`,
код ответа — `400`/`401`/`403`/`404`/`409`/`429`. Исключение — `422` (тело запроса
не прошло валидацию): там `detail` не строка, а **массив** объектов
`{loc, msg, type}` от pydantic — это единственный случай, когда `detail` нельзя
показывать пользователю как есть.

> До недавнего времени `429` от превышения лимита запросов (`@limiter.limit`)
> отдавался библиотекой slowapi в своём формате — `{"error": "..."}`, другим
> ключом, чем всё остальное API. Если где-то в старом клиентском коде обработка
> ошибок написана под `{"error": ...}` — это относится только к `429` и теперь
> не актуально, формат унифицирован.

Лимиты на auth-эндпоинтах (по IP):

| Эндпоинт | Лимит |
|---|---|
| `POST /auth/register/start` | 5/мин |
| `POST /auth/register/complete` | 10/мин |
| `POST /auth/register/resend` | 3/мин |
| `GET /auth/register/status` | 60/мин |
| `POST /auth/login` | 10/мин |
| `POST /auth/admin-login` | 5/мин |
| `POST /auth/refresh` | 20/мин |
| `POST /auth/guest` | 30/мин |
| `POST /auth/password-reset/start` | 5/мин |
| `POST /auth/password-reset/complete` | 5/мин |
| `POST /auth/change-phone/request` | 5/мин |
| Всё остальное | 200/мин (общий лимит по умолчанию) |

На `429` бессмысленно ретраить немедленно — почти всегда это или экран с паролем,
который человек вводит не быстрее раза в секунду, или баг в клиенте (например,
`/auth/refresh` вызван параллельно из нескольких мест, см. ниже).

### Обновление сессии (access/refresh)

`access_token` живёт `JWT_ACCESS_TOKEN_TTL_MINUTES` (по умолчанию 30 минут),
`refresh_token` — `JWT_REFRESH_TOKEN_TTL_DAYS` (по умолчанию 60 дней) и
**одноразовый**: `POST /auth/refresh` отзывает переданный и выдаёт новую пару.
Повторное использование уже отозванного `refresh_token` трактуется как
компрометация — обрываются **все** сессии пользователя на всех устройствах, и
следующий `/auth/refresh` вернёт `401`.

```
1. Каждый запрос — Authorization: Bearer <access_token>
2. Ответ 401 →
   a. POST /auth/refresh { refresh_token }
   b. Успех → сохранить НОВУЮ пару, повторить исходный запрос
   c. 401 от /auth/refresh → сессия невосстановима, разлогинить
3. Несколько параллельных 401 — обновлять ОДИН раз (single-flight/мьютекс),
   не запускать /auth/refresh из каждого запроса отдельно: второй вызов
   придёт с уже отозванным refresh_token и попадёт под защиту от
   компрометации, разлогинив пользователя без причины
```

У одного пользователя одновременно живо не больше 5 `refresh`-сессий: при входе
на 6-м устройстве самая старая тихо отзывается (`trim_sessions`). Держащий
`refresh_token` неактивным месяцами клиент («запомнить меня», см. ниже) может
быть вытеснен просто тем, что пользователь много раз входил с других устройств.

### «Запомнить меня»

Решается на клиенте местом хранения `refresh_token` — сервер про чекбокс не
знает и ничего для него не выдаёт отдельно.

| Чекбокс | Где хранить `refresh_token` | Поведение |
|---|---|---|
| Отмечен | Keychain (iOS) / Keystore (Android) | Переживает перезапуск приложения, тихий вход через `/auth/refresh` до 60 дней |
| Не отмечен | Только в памяти | При закрытии приложения (не сворачивании) токены пропадают, при следующем запуске — экран входа |

`access_token` в обоих случаях достаточно держать в памяти — он короткоживущий.
При логауте — всегда `POST /auth/logout { refresh_token }`, чтобы токен
отозвался и на сервере, а не просто исчез с устройства.

### Гостевой доступ без регистрации

`POST /auth/guest` — без пароля и без пользователя, доступ только к
`GET /kb/*`, `GET /faq/*` и `GET /tags` (см. `POST /auth/guest` в разделе
ниже). Хранить гостевой `access_token` в памяти, не в Keychain/Keystore — это
не аккаунт, и "запоминать" его незачем: закончился — просто запросить новый.

На гостевом токене не пытаться вызывать `POST /auth/refresh` при 401 — у гостя
нет `refresh_token`, и такой запрос сам вернёт ошибку. При 401 на гостевом
токене просто запросить новый через `POST /auth/guest`, без редиректа на экран
входа: гость и не должен был логиниться.

### Регистрация пользователя

> **Поля «телефон» в форме регистрации больше нет.** Номер аккаунта берётся из
> контакта Telegram и потому подтверждён по построению: Telegram проверил его при
> регистрации аккаунта, ввести произвольный в боте нельзя. Раньше номер вводился
> руками и не сверялся ни с чем — занять можно было любой незарегистрированный.
>
> Вместо него в форме есть **необязательный `contact_phone`** — рабочий номер. Он
> не подтверждается, на вход не влияет, виден операторам и правится в профиле
> когда угодно. Нужен потому, что Telegram у человека часто на личном номере.
>
> **SMS отключено полностью, Viber удалён.** Единственный канал — Telegram.

```
1. POST /auth/register/start
   Тело: { password, password_confirm, full_name, user_type,
           organization_name?, contact_phone? }      ← телефона-логина здесь НЕТ
   Ответ: { registration_token, deep_link, resend_after_seconds }

   → Сохранить registration_token: им идентифицируются оба следующих шага.
   → Показать кнопку "Открыть Telegram" (открыть deep_link).
   → В Telegram: Start, затем кнопка "Отправить мой номер".
   → Только после этого бот присылает код.

2. POST /auth/register/complete
   Тело: { registration_token, code }      ← телефон не нужен, клиент его не знает
   Ответ: { access_token, refresh_token, token_type }
   → Сохранить оба токена. Номер аккаунта — из GET /auth/me.

   Если код не пришёл или истёк:
   POST /auth/register/resend
   Тело: { registration_token }
   Ответ: { resend_after_seconds, deep_link }
     deep_link != null → номер ещё не подтверждён, кода пока не существует:
       вернуть пользователя в Telegram нажать "Отправить мой номер".
     deep_link == null → номер подтверждён, отправлен новый код.
```

Что бот отвечает в нестандартных случаях (пользователь видит это **в Telegram**, а не
в приложении — приложение в этот момент ждёт код):
- переслал чужой контакт → «Это чужой контакт, нажмите кнопку»;
- номер уже зарегистрирован → «Войдите в приложение по этому номеру»;
- регистрация истекла → «Начните заново в приложении».

> **Один Telegram — один аккаунт.** Повторно зарегистрироваться с того же
> Telegram-аккаунта нельзя: номер придёт тот же, а он уже занят. Тому, кто хочет
> сменить рабочий номер, нужно войти и отредактировать `contact_phone`, а не
> регистрироваться заново. Разбор всех трёх случаев (повтор, брошенная регистрация,
> смена номера в самом Telegram) — в разделе `POST /auth/register/start` ниже.

### Вход пользователя
```
POST /auth/login
Тело: { phone, password }
Ответ: { access_token, refresh_token }
→ Сохранить токены. Зарегистрировать FCM-токен устройства (см. Уведомления).
```

### Вход администратора / оператора
```
POST /auth/admin-login
Тело: { login, password }
Ответ: { access_token, refresh_token }
→ Сохранить токены.
```

### Использование токенов
```
Каждый запрос: заголовок Authorization: Bearer {access_token}

Если сервер вернул 401:
  POST /auth/refresh
  Тело: { refresh_token }
  Ответ: { access_token, refresh_token }
  → Сохранить новые токены, повторить исходный запрос.

  Если /auth/refresh тоже вернул 401 → разлогинить пользователя.
```

### Выход
```
POST /auth/logout
Тело: { refresh_token }
→ Удалить токены локально.
→ DELETE /device-tokens/{fcm_token} — чтобы перестали приходить push.
```

### Редактирование профиля
```
1. GET /auth/me → получить текущие данные, предзаполнить форму
2. Пользователь меняет поля
3. PATCH /auth/me
   Тело: { full_name?, email?, organization_name? }
   → Передавать только изменённые поля.
   Ответ: обновлённый профиль.
```

### Смена номера телефона

> **Изменено.** Самостоятельной смены номера больше нет: эндпоинты
> `POST /auth/change-phone/start` и `/change-phone/complete` **удалены**.
> Причина — они ничего не подтверждали: SMS отключены, а код доставляется в
> мессенджер по `user_id`, то есть в собственный Telegram/Viber заявителя.
> Владение новым номером таким кодом не доказывается никак, поэтому любой
> пользователь мог поставить себе любой незанятый номер — занять чужой (после
> чего его владелец не смог бы зарегистрироваться) или показывать сотрудникам
> чужой телефон в заявках и чатах. Теперь номер меняет администратор,
> убедившись во владении вне системы.

```
1. POST /auth/change-phone/request
   Тело: { new_phone: "+375291234568", user_comment?: "Сменил оператора" }
   Ответ: 201, PhoneChangeRequestOut со статусом "pending"
   → Показать «Заявка отправлена, ожидайте решения администратора».

   Ошибки:
   409 — это уже ваш текущий номер
   409 — номер занят другим пользователем
   409 — у вас уже есть необработанная заявка

2. GET /auth/change-phone/request
   Ответ: PhoneChangeRequestOut или null, если активной заявки нет.
   → Показывать статус на экране профиля.

3. DELETE /auth/change-phone/request
   → Отозвать свою заявку (ошибся номером). 204.

4. Решение админа приходит push-уведомлением (тип request_status):
   одобрено  → номер уже изменён, вход теперь по новому номеру;
   отклонено → в admin_response причина.
```

## 3. Проекты

> **У проекта есть всё то же, что у ШУ:** собственный чат и собственные фотографии,
> плюс документация, гарантия и данные из сделки. ШУ при этом продолжают работать
> как раньше — это не замена, а второй уровень.

### Чат проекта
```
GET /projects/{project_id}/chat
Ответ: { id, chat_type: "project", project_id, problem_status, bot_active }
→ Дальше — те же эндпоинты, что у чата ШУ: /chats/{chat_id}/messages и т.д.
→ 403, если проект не привязан к аккаунту.
```
Создаётся автоматически при первой привязке проекта к аккаунту, а также по первому
обращению к этому эндпоинту. Один чат на пару пользователь + проект.

В списках чатов (`GET /chats`, `GET /operator/chats`) такие чаты приходят с
`chat_type: "project"` и заполненными `project_id` / `project_name` — по ним и
показывать заголовок вместо названия ШУ. Оператор может фильтровать: `?chat_type=project`.

### Фото проекта
Как и фото ШУ — пользователю не показываются, `GET /projects/{project_id}/photos`
доступен только оператору/администратору. Раздел убрать из клиента.

Проект — группа шкафов управления с общим QR-кодом: добавляя проект, пользователь
разом получает доступ ко всем его шкафам (или подаёт заявку, если проект уже занят
кем-то другим). Проект может быть и пустым (шкафы ещё не привязаны админом).

### Экран "Мои проекты"
```
GET /projects
Ответ: список { project_id, name, is_primary, cabinet_count }
→ Показать карточки. is_primary — пользователь первым добавил этот проект.
→ cabinet_count — сколько шкафов вообще в проекте (не обязательно все доступны юзеру).
```

### Добавление проекта через QR
```
1. Пользователь сканирует QR
2. POST /projects/add-by-qr
   Тело: { qr_data: "savt://project/A3F7BC12..." }
   Ответ: { status, message }

   status = "linked" → проект сразу добавлен (плюс часть шкафов — см. ниже), обновить список.
   status = "request_submitted" → заявка отправлена, ждать одобрения.
```
Что происходит со шкафами проекта при добавлении — фронту знать не обязательно
(сервер решает сам), но полезно для UX-текстов:
- если проект ещё ничей — пользователь получает сразу все свободные шкафы проекта,
  а на шкафы, уже занятые кем-то другим, тихо уходят отдельные заявки (без блокировки
  остального);
- если проект уже занят другим человеком — после одобрения его заявки администратором
  пользователь получает доступ вообще ко всем шкафам проекта одним махом.
→ После `status: "linked"` стоит обновить не только список проектов, но и список ШУ (`GET /cabinets`) — туда могли добавиться новые шкафы.

### Карточка проекта
```
GET /projects/{project_id}
Ответ: { project_id, name, is_primary, cabinets: [{ id, type, object_number, admin_internal_name }] }
→ cabinets — только те шкафы проекта, к которым у пользователя реально есть доступ
  (не обязательно все шкафы проекта — на часть могла остаться pending-заявка).
```

## 4. Чат

### Открытие чата
```
GET /chats
Ответ: список всех чатов { id, chat_type, cabinet_name, last_message_text,
                           unread_count, problem_status, bot_active }
→ cabinet: чат по конкретному ШУ (cabinet_id / cabinet_name)
→ project: чат по проекту в целом (project_id / project_name)
→ service_request: чат заявки на обслуживание
→ support: общий чат поддержки
→ notes: личные заметки пользователя
```

### История сообщений (бесконечный скролл вверх)
```
Первая загрузка:
GET /chats/{chat_id}/messages?limit=30
Ответ: массив сообщений от новых к старым.
→ Отобразить снизу вверх.

Загрузка более старых (пользователь скроллит вверх):
GET /chats/{chat_id}/messages?before_id={oldest_msg_id}&limit=30
→ Добавить в начало списка.

Загрузка вокруг конкретного сообщения (поиск + переход по ссылке):
GET /chats/{chat_id}/messages?around_id={msg_id}&limit=30
→ Возвращает сообщения до и после указанного ID.
```

### Отправка сообщения
```
Только текст:
POST /chats/{chat_id}/messages
Тело: { text: "Сообщение" }

С вложением:
1. POST /upload/attachment (multipart, file)
   Ответ: { url, ... }

2. POST /chats/{chat_id}/messages
   Тело: {
     text: "Смотри файл",
     attachments: [{
       file_url: "/static/documents/abc.pdf",
       file_name: "abc.pdf",
       file_size_bytes: 204800,
       mime_type: "application/pdf"
     }]
   }

Голосовое:
1. POST /upload/voice (multipart, file)
2. POST /chats/{chat_id}/messages
   Тело: {
     attachments: [{
       file_url: "...", file_name: "voice.ogg",
       file_size_bytes: 512, mime_type: "audio/ogg",
       duration_seconds: 15
     }]
   }

Геолокация (без загрузки файла — просто координаты):
POST /chats/{chat_id}/messages
Тело: {
  attachments: [{ latitude: 53.9045, longitude: 27.5615 }]
}
→ Вложение придёт с attachment_type: "location", остальные поля вложения — null.
```

### Отметить прочитанным
```
POST /chats/{chat_id}/read
→ Вызывать когда пользователь открыл чат или прочитал последнее сообщение.
→ Сбрасывает unread_count.
```

### Реакции
```
Поставить: POST /chats/{chat_id}/messages/{msg_id}/reactions/{emoji}
Убрать:    DELETE /chats/{chat_id}/messages/{msg_id}/reactions/{emoji}
```

### Закреплённые сообщения (несколько на чат, до 10)
```
Список:            GET    /chats/{chat_id}/pinned
Закрепить:         PUT    /chats/{chat_id}/pin/{msg_id}   (идемпотентно)
Открепить одно:    DELETE /chats/{chat_id}/pin/{msg_id}
Открепить все:     DELETE /chats/{chat_id}/pin
→ Все 4 ответа: list[MessageOut], от новых к старым по времени закрепления
```

### Обои чата
Обои — личная настройка пользователя; собеседник не видит выбранный фон.
```
Установить: PATCH /chats/{chat_id}/wallpaper
Тело: { "wallpaper_url": "/static/photos/bg.jpg" }
Сбросить:   { "wallpaper_url": null }
→ Ответ: ChatSettingsOut с обновлённым wallpaper_url
   (обои сохраняются в настройках пользователя, а не в самом чате)
```

### Удалить чат
```
DELETE /chats/{chat_id}          — пользователь (только cabinet и notes; поддержку удалить нельзя)
DELETE /operator/chats/{chat_id} — оператор/админ (любой чат)
→ 204 No Content
```

### Очистить историю сообщений (только оператор)
```
DELETE /operator/chats/{chat_id}/messages
→ Soft-delete всех сообщений (тексты обнуляются)
→ 204 No Content
```

### Настройки вида чата (цвета, шрифт, обои)
Все настройки вида — личные: собеседник видит чат со своими настройками.

Глобальные настройки (применяются ко всем чатам пользователя):
```
GET   /chats/settings          → ChatSettingsOut
PATCH /chats/settings          → ChatSettingsOut
```

Per-chat override (приоритет над глобальными):
```
GET    /chats/{chat_id}/settings   → возвращает per-chat если есть, иначе global
PATCH  /chats/{chat_id}/settings   → создаёт/обновляет override для конкретного чата
DELETE /chats/{chat_id}/settings   → сбрасывает override (откат к глобальным)
→ 204 No Content для DELETE
```

Обои — часть настроек per-chat; можно задать через `PATCH /chats/{chat_id}/wallpaper`
или через `PATCH /chats/{chat_id}/settings` (поле `wallpaper_url`).

Тело запроса `ChatSettingsIn` (все поля опциональны):
```json
{
  "own_bubble_color": "#DCF8C6",
  "other_bubble_color": "#FFFFFF",
  "bot_bubble_color": "#E8E8E8",
  "own_text_color": "#000000",
  "other_text_color": "#000000",
  "bot_text_color": "#555555",
  "nick_color": "#128C7E",
  "font_size": 14,
  "wallpaper_url": "/static/photos/bg.jpg"
}
```
Цвета — HEX `#RRGGBB`. `font_size` — от 8 до 24. `wallpaper_url` — URL обоев (null = сброс).

### Голосовое сообщение → текст
```
1. Загрузить: POST /upload/voice (multipart, file)
   Форматы: ogg, mp3, m4a, wav, webm, aac
```

```
2. DELETE /notifications/mute → снять досрочно
```

```
GET /notifications/unread-count → { unread: 3 } для бейджа
```

### Push при новом сообщении
```
Когда оператор или бот пишет пользователю — сервер автоматически
отправляет FCM push на все зарегистрированные устройства пользователя:
  title: имя отправителя ("Ася" / "Оператор Иванов")
  body:  текст сообщения (до 100 символов)
  data:  { chat_id: "3", type: "chat_message" }

Условие: тип уведомления chat_message должен быть включён
в настройках пользователя (по умолчанию — включён) и не стоять
пауза. Обе проверки живут в send_push, поэтому действуют
на все пуши, включая те, что отправляются в обход
NotificationService (сообщения в чатах и ответы бота).
Сообщения чата push-only: записи в GET /notifications
для них НЕ создаются — у чатов свои счётчики непрочитанного.

Рассылка админа (POST /admin/notifications/broadcast) уважает
переключатель promotional — и для пуша, и для записи в списке
уведомлений. Дефолт настройки — true: раньше переключатель не
проверялся вовсе, и оставить прежний дефолт false значило бы
молча отключить рассылки почти всем (см. миграцию
a835bebb7d46). Ответ — { sent_to, skipped_opted_out }; те же числа
пишутся и в журнал действий.
```

## 8.1. Подписанные ссылки на файлы

**Что изменилось:** раньше `/static/` раздавался без всякой авторизации — ссылка на файл
работала вечно и у кого угодно, то есть была бессрочным пропуском к файлу. Теперь ссылка
действительна ограниченное время и только с подписью, которую проверяет nginx.

**Что это значит для фронта — в большинстве случаев ничего.** Правило простое:

> Используй URL ровно в том виде, в каком он пришёл от API, и не собирай его руками
> из имени файла. Отправлять обратно можно как есть — сервер сам отбросит подпись.

Подробности:

- Все ссылки в ответах API приходят с хвостом `?md5=...&expires=...` — это касается
  `file_url` вложений, `url` фото, `file_url` документов и вложений базы знаний,
  `wallpaper_url`, `photo_url` в заявках, а также `url` из `/upload/*`.
- Ссылка живёт **сутки** (`STATIC_LINK_TTL_SECONDS`). Экран, открытый дольше суток,
  должен перезапросить данные — после рефетча ссылки снова свежие. Просроченная
  ссылка отдаёт `410`, ссылка без подписи или с испорченной подписью — `403`.
- **Отправлять URL обратно можно прямо с подписью** (`POST /chats/{id}/messages`,
  `POST /cabinets/add-by-photo`, `PATCH /chats/{id}/wallpaper`, `POST /upload/transcribe`) —
  сервер снимает подпись перед сохранением, в БД лежит голый путь.
- Ссылки, которые сервер сам отправляет в комментарии Bitrix-задач, подписываются
  на **90 дней** — их открывают сотрудники без сессии в нашем API.
- Кешировать файл по URL можно, но помни, что после истечения срока тот же URL
  перестанет работать — кешируй **содержимое**, а не ссылку.

> **Документы с ограниченным доступом** (`requires_approval: true`) прямой ссылки не
> получают **вообще** — у них `file_url: null` даже после одобрения доступа. Скачивать
> только через `GET /documents/{id}/download`: подписанную ссылку можно переслать
> третьему лицу, а download-эндпоинт проверяет права на каждое скачивание.

## 9. PATCH-запросы — как редактировать

### Правило для всех PATCH-эндпоинтов
```
1. Сначала GET → получить текущие данные → предзаполнить форму
2. Пользователь меняет нужные поля
3. PATCH → отправить ТОЛЬКО изменённые поля

Если поле не отправить → оно не изменится.
Если отправить null → значение сбросится (если поле nullable).

Пример редактирования ШУ:
1. GET /cabinets/{id}           → { custom_name: "Старое название", custom_comment: null }
2. PATCH /cabinets/{id}         → { custom_name: "Новое название" }
   ← custom_comment не трогали → не меняется
```

## Чек-лист: что добавить на фронте для проектов

Новая фича, фронта под неё пока нет нигде. Разбито по приложениям.

### Мобильное приложение (пользователь)
- [ ] Экран **«Мои проекты»** — список по `GET /projects` (карточки: название, `cabinet_count`, бейдж «основной» если `is_primary`). Можно разместить как отдельную вкладку или как секцию над списком ШУ.
- [ ] Экран **«Проект»** — детали по `GET /projects/{id}`, список доступных шкафов проекта (переиспользовать существующую карточку ШУ), переход в каждый шкаф как обычно.
- [ ] Сканер QR теперь ведёт только на `POST /projects/add-by-qr` — у ШУ своего QR/эндпоинта добавления больше нет (`POST /cabinets/add-by-qr` убран), если в клиенте ещё зашит cabinet-путь — выпилить.
- [ ] Обработка ответа `add-by-qr`: `status: "linked"` → тост об успехе + обновить и список проектов, и список ШУ (`GET /cabinets`) одновременно — при линковке проекта могли добавиться новые шкафы. `status: "request_submitted"` → тост «заявка отправлена».
- [ ] Экран ошибок: `404` («проект не найден»), `409` («уже привязан» / «заявка уже отправлена»).

### Админ-панель
- [ ] Раздел **«Проекты»**: список (`GET /admin/projects`, поиск/сортировка/пагинация), удаление (`DELETE .../{id}`, с предупреждением что это soft-delete — и что пока сделка жива в Bitrix, проект воскреснет сам на ближайшем изменении сделки). Ни создания, ни переименования на фронте не нужно — проект и его название приходят только из Bitrix.
- [ ] Карточка проекта — `GET /admin/projects/{id}` для метаданных проекта, но список шкафов на странице лучше грузить отдельно через `GET /admin/cabinets?project_id={id}` (полноценные карточки ШУ — с гарантией, тегами и т.п., плюс пагинация/поиск/фильтры/сортировка как в общем списке ШУ); `cabinets[]` из `GET /admin/projects/{id}` — урезанный (`id`/`type`/`object_number`/`admin_internal_name`), годится только для лёгкого превью. Кнопка «Показать QR» → `GET /admin/projects/{id}/qr`, кнопка «Печать/скачать» — единственный источник QR теперь, у ШУ своей кнопки QR больше нет.
- [ ] В карточке/списке ШУ показывать проект по полям `project_id`/`project_name` из ответа **самого эндпоинта ШУ** (`GET /admin/cabinets`, `GET /admin/cabinets/{id}`, `GET /cabinets`, `GET /cabinets/{id}`) — не выводить его из того, откуда была открыта карточка (например, что «открыли со страницы проекта X»). Раньше эти поля не отдавались вообще, из-за чего карточка ШУ всегда показывала «Без проекта» независимо от контекста — теперь отдаются везде, `null`/`null`, если ШУ ни к какому проекту не привязан.
- [ ] Форма **создания ШУ** — поле «Проект» (`GET /admin/projects` списком) теперь обязательное, `POST /admin/cabinets` без `project_id` вернёт `422`. В карточке/форме редактирования того же поля (там же, где теги через `PUT /admin/cabinets/{id}/tags`) — сохранение сменой проекта через `PATCH /admin/cabinets/{cabinet_id}/project` (`{ project_id: null }` для отвязки, отвязать по-прежнему можно). Стоит явно предупредить админа в UI, что если у проекта уже есть участники — они получат доступ к этому шкафу сразу, без дополнительного подтверждения (действует и при создании, и при смене проекта).
- [ ] Новый раздел заявок **«Заявки на проекты»** (`GET /admin/project-requests`) — верстается один-в-один как уже существующий «Заявки на доступ к ШУ» (`shares`): та же таблица, те же кнопки «Одобрить»/«Отклонить» (`POST .../{id}/approve|reject`). Доступен на просмотр оператору, одобрение/отклонение — только админу (как и у заявок на ШУ).
- [ ] На дашборде (`GET /admin/dashboard`) пока нет счётчика pending-заявок на проекты — если нужно, стоит завести отдельный тикет на бэкенд, сейчас в `stats` его нет.

### Карточка проекта: поля из Bitrix и гарантия

- [ ] **Админка.** В карточке проекта показать блок из сделки: номер в производство, планируемая и фактическая даты отгрузки, компания, контактные лица (ФИО, должность, телефоны и почты — списками). Всё это **только для чтения**, поля редактирования не рисовать: `PATCH` их не принимает, они перезаписываются при изменении сделки.
- [ ] **Админка.** Поля гарантии (`warranty_starts_at`, `warranty_ends_at`) — редактируемые, через `PATCH /admin/projects/{id}`. Рядом предупредить, что от `warranty_ends_at` зависит ночная синхронизация папки проекта на NAS.
- [ ] **Админка.** В списке проектов появились `company_name`, `shipment_actual_at`, `warranty_status` — полезно как колонки.
- [ ] **Мобильное приложение.** В карточке проекта показать компанию, даты отгрузки и гарантию (`warranty_status` — тем же индикатором, что у ШУ). **Контактных лиц там нет** и запрашивать их неоткуда.
- [ ] **Мобильное приложение.** Пока `shipment_actual_at` пуст — показывать `shipment_planned_at` как ожидаемую дату с соответствующей подписью.

### Общее
- [ ] Юридический раздел по проектам/шкафам сознательно не делали — если возникнет, потребуется отдельное обсуждение и отдельная задача.

## Чек-лист: что добавить на фронте для авторизации через Telegram

и под подтверждение номера контактом ещё не готов нигде.

- [ ] **Объяснить шаг внутри Telegram.** После Start бот покажет кнопку «Отправить мой номер» — без неё кода не будет. Текст вида: «Откройте Telegram, нажмите Start, затем кнопку "Отправить мой номер"». Это самое частое место, где человек застрянет.

- [ ] **Поллить `GET /auth/register/status`, пока пользователь в Telegram.** Это единственный способ узнать, что бот отказал (`status: "failed"`) — сам отказ виден только в Telegram. Без поллинга приложение зависнет на экране ввода кода: `resend` в этом состоянии вернёт непустой `deep_link` и отправит человека обратно в Telegram по кругу. Разбор всех значений `status`/`reason` — в описании эндпоинта.
- [ ] Экран профиля: показывать `phone` как логин (без кнопки «изменить» — только через заявку) и `contact_phone` как редактируемый телефон для связи.
- [ ] **Сброс пароля:** `deep_link` теперь всегда `null`. Если код не пришёл — у аккаунта нет подтверждённой связки с ботом, самостоятельно это не чинится. Показывать «обратитесь к администратору».

### Админ-панель
- [ ] В списке и карточке пользователя рядом с `phone` (логин, подтверждён) показывать `contact_phone` — рабочий номер, который пользователь указал сам. Он не подтверждён, полагаться на него при идентификации звонящего нельзя.

## Рут `auth` — авторизация и аккаунт

### POST `/auth/guest`
**Гостевой доступ** — без регистрации, для экранов, явно открытым без входа: сейчас это
`GET /kb/*`, `GET /faq/*` и `GET /tags` (см. врезку ниже). Тело не нужно.
```json
{ "access_token": "eyJ...", "token_type": "bearer", "expires_in": 1800 }
```
`expires_in` — секунды, совпадает с `JWT_ACCESS_TOKEN_TTL_MINUTES`. **`refresh_token` не выдаётся**: выпуск гостевого токена не обращается к БД вообще (нет ни пользователя, ни сессии, которую можно было бы продлить), поэтому при истечении клиент просто зовёт `/auth/guest` заново — это так же дёшево, как обновить токен.

Гостевой токен принимается **только** на роутах, явно на это рассчитанных (`get_current_user_or_guest`). На любом обычном эндпоинте (`get_current_user`) он отвергается с `401 "Неверный тип токена"` — гость не может выдать себя за пользователя ни при каких обстоятельствах, проверка на уровне JWT-claim `type`, а не роли.

> **Что открыто гостю:** список и содержимое статей базы знаний, вложения к ним, список вопросов FAQ, список тегов. Всё остальное — чаты, заявки, проекты, ШУ, уведомления — требует полноценного входа.
>
> Анонимного доступа совсем без токена нет намеренно: гостевой JWT ничего не стоит выдать (не трогает БД), а клиентский код при этом не разветвляется на «с токеном» / «без токена» — заголовок `Authorization` есть всегда, просто с одним из двух типов токена внутри.
>
> На 401 с гостевым токеном клиент не должен пытаться `POST /auth/refresh` (у гостя нет `refresh_token`) и не должен редиректить на экран входа — просто очистить токен и запросить новый через `/auth/guest`.

---

### POST `/auth/register/start`
Начало регистрации. **Номер телефона здесь не передаётся** — он придёт из контакта
Telegram (SMS отключено полностью, Viber удалён).
```json
{
  "password": "minLength8",
  "password_confirm": "minLength8",
  "full_name": "Иванов Иван Иванович",
  "user_type": "individual",
  "organization_name": null,
  "contact_phone": "+375291110000"
}
```
- `password` — минимум 8 символов
- `password_confirm` — должен совпадать с `password`
- `user_type` — `individual` или `organization`
- `organization_name` — обязателен если `user_type = organization`
- `contact_phone` — **необязательный** рабочий номер. Не подтверждается, на вход не
  влияет, виден операторам, правится через `PATCH /auth/me`. Номером аккаунта
  (логином) не становится

Ответ:
```json
{
  "message": "Откройте Telegram и подтвердите номер",
  "registration_token": "kQ2f...",
  "deep_link": "https://t.me/<bot>?start=kQ2f...",
  "resend_after_seconds": 60
}
```
- `registration_token` — **сохранить**: им идентифицируются `/register/complete` и
  `/register/resend`. Телефон для этого не годится — клиент его ещё не знает
- `deep_link` — всегда непустая: подтвердить номер можно только в Telegram

**Откуда берётся номер аккаунта.** Открыть ссылку недостаточно — она лишь начинает
диалог. Дальше бот показывает кнопку «Отправить мой номер» (`request_contact`), и
номер из этого контакта становится номером аккаунта. Telegram проверил его при
регистрации аккаунта и подставляет сам — ввести произвольный в боте невозможно.

Единственная проверка на нашей стороне: **контакт принадлежит отправителю**
(`contact.user_id == message.from.id`). Telegram разрешает переслать боту **любой**
контакт из адресной книги — без этой проверки достаточно было бы отправить карточку
жертвы, и её номер стал бы номером чужого аккаунта. Сверять номер с чем-то ещё не
нужно и не с чем: в форме его больше не спрашивают.

Пока номер не подтверждён, ни пользователя, ни кода не существует — данные формы
лежат в `pending_registrations` и протухают вместе с токеном (TTL —
`MESSENGER_LINK_REQUEST_TTL_MINUTES` + `SMS_CODE_TTL_MINUTES`, по умолчанию 25 минут).

> Ранее номер вводился в форме и не сверялся ни с чем: код улетал любому, кто открыл
> ссылку. Занять можно было любой незарегистрированный номер, не имея к нему доступа —
> владелец после этого не мог зарегистрироваться сам.

#### Один Telegram — один аккаунт

Номер аккаунта берётся из Telegram, а `users.phone` уникален. Значит с одного
Telegram-аккаунта можно завести ровно один аккаунт в приложении. Три следствия,
которые надо понимать и обрабатывать на клиенте.

**1. Повторная регистрация с того же Telegram — отказ.**

Человек уже зарегистрирован, но снова проходит регистрацию (частый случай: хочет
поменять рабочий номер и по привычке лезет регистрироваться вместо того, чтобы
войти и отредактировать `contact_phone`). Контакт отдаёт тот же номер, находится
существующий подтверждённый аккаунт — и бот отвечает в Telegram:

> Номер +375XXXXXXXXX уже зарегистрирован. Войдите в приложение по этому номеру,
> а если забыли пароль — воспользуйтесь восстановлением.

Новый аккаунт не создаётся, код не отправляется. **Существующий аккаунт при этом
не изменяется вообще** — ни пароль, ни ФИО, ни организация. Это принципиально:
иначе «повторная регистрация» была бы способом переписать пароль чужого аккаунта.

Объяснение приходит **в Telegram**, а приложение в этот момент ждёт код. Чтобы оно
не ждало вечно, есть `GET /auth/register/status` — он вернёт `status: "failed"` и
`reason: "phone_already_registered"`. Поллить его, пока пользователь в Telegram, и
на `failed` показывать нормальный экран с кнопкой «Войти».

> Проверка идёт **по самому Telegram-аккаунту**, а не только по номеру. Если
> человек сменил номер телефона входа (`PATCH /users/me/phone`), его аккаунт уже
> не совпадёт с тем, что отдаст кнопка «Отправить мой номер» — и проверка «такой
> номер занят» пропустила бы его, заведя второй аккаунт с того же Telegram.
> Поэтому первым делом ищется существующая привязка чата: она даёт
> `reason: "telegram_already_linked"`, и в сообщении называется тот номер, под
> которым человек на самом деле входит.

**2. Брошенная регистрация — можно начать заново.**

Если код так и не был введён, аккаунт остался неподтверждённым. Повторная
регистрация с того же Telegram пройдёт нормально: данные неподтверждённого аккаунта
перезапишутся новыми из формы, придёт код, регистрация завершится. Дубликата не
возникнет.

**3. Пользователь сменил номер в самом Telegram — появится второй аккаунт.**

Telegram позволяет менять номер аккаунта. После этого контакт отдаст уже другой
номер, пользователя с таким номером в системе нет — и заведётся **второй** аккаунт.
Старый останется со старым номером.

Дополнительно: `messenger_links` уникальна по `(user_id, channel)`, но **не** по
`external_chat_id`, поэтому оба аккаунта окажутся привязаны к одному чату Telegram.
Дырой это не является (человек тот же), но восстановление пароля для обоих будет
приходить в один чат, и различать их придётся по тексту сообщения. Правильный выход
для такого пользователя — заявка на смену номера (`POST /auth/change-phone/request`),
а не вторая регистрация.

---

### POST `/auth/register/complete`
Завершение регистрации кодом из Telegram. Опознаётся по `registration_token`, а не по
телефону: клиент номера не знает — он пришёл из контакта Telegram.
```json
{
  "registration_token": "kQ2f...",
  "code": "123456"
}
```
Ответ: `201 Created`
```json
{
  "access_token": "eyJ...",
  "refresh_token": "abc123...",
  "token_type": "bearer"
}
```
Номер аккаунта можно прочитать из `GET /auth/me` (поле `phone`).

Ошибки:
- `404` — регистрация не найдена или истекла, начинать заново
- `400` — номер ещё не подтверждён: пользователь не нажал «Отправить мой номер» в Telegram
- `400` — неверный код / превышено число попыток

---

### GET `/auth/register/status?registration_token=...`
Где сейчас находится незавершённая регистрация. Без авторизации (её ещё нет),
доступ по токену. Лимит — 60 запросов в минуту, рассчитан на поллинг.

**Зачем.** Номер подтверждается в Telegram, и об отказе бот сообщает там же —
приложение об этом иначе не узнает. По одному лишь `/register/resend` отличить
«ещё не нажал кнопку» от «отказано» невозможно: в обоих случаях вернётся непустой
`deep_link`, и клиент будет гонять человека в Telegram по кругу.

```json
{ "status": "waiting_contact", "reason": null }
```

| `status` | Что значит | Что показать |
|---|---|---|
| `waiting_contact` | ждём нажатия «Отправить мой номер» | «Подтвердите номер в Telegram» |
| `code_sent` | номер подтверждён, код отправлен | экран ввода кода |
| `failed` | бот отказал, кода не будет — см. `reason` | см. ниже |
| `expired` | истекли 25 минут | «Начните регистрацию заново» |
| `completed` | регистрация по этому токену уже завершена | перейти ко входу |

`reason` заполняется только при `failed`:

| `reason` | Причина | Что показать |
|---|---|---|
| `phone_already_registered` | под этим номером уже есть подтверждённый аккаунт | «Войдите по этому номеру» + кнопки «Войти» / «Забыли пароль» |
| `telegram_already_linked` | этот Telegram уже привязан к аккаунту (возможно, с другим номером входа — его человек и сменил) | то же самое; номер входа назван в сообщении бота |
| `foreign_contact` | переслал чужой контакт вместо кнопки | «Нажмите кнопку "Отправить мой номер"», вернуть в Telegram |
| `bad_phone` | номер не разобрался | «Обратитесь в поддержку» |

`404` — токен не найден вообще.

> `failed` по причинам `foreign_contact` и `bad_phone` **не закрывает регистрацию**:
> пользователь может вернуться в Telegram и нажать кнопку правильно, отметка
> снимется сама. При `phone_already_registered` и `telegram_already_linked` повтор
> не поможет — Telegram отдаст тот же контакт.

---

### POST `/auth/register/resend`
Повторная отправка кода.
```json
{ "registration_token": "kQ2f..." }
```
Ответ:
```json
{ "message": "Код отправлен повторно", "resend_after_seconds": 60, "deep_link": null }
```
- `deep_link != null` — номер ещё не подтверждён, кода не существует: вернуть
  пользователя в Telegram нажать «Отправить мой номер»
- `deep_link == null` — номер подтверждён, отправлен новый код

### GET `/auth/me`
Данные текущего авторизованного пользователя (требует Bearer-токен).
```json
{
  "id": 1,
  "phone": "+375291234567",
  "contact_phone": "+375291110000",
  "email": null,
  "user_type": "individual",
  "organization_name": null,
  "full_name": "Иванов Иван",
  "role": "user",
  "is_phone_verified": true,
  "is_verified": false
}
```
- `phone` — **подтверждённый номер из Telegram, он же логин.** Пользователь его не
  меняет: только через заявку с одобрением админа (`POST /auth/change-phone/request`)
- `contact_phone` — рабочий номер, необязательный. Не подтверждается, на вход не

- `is_verified` — подтверждён ли аккаунт администратором

### DELETE `/auth/me`
Удаление собственного аккаунта (доступно всем авторизованным пользователям). Отзывает все refresh-токены и удаляет аккаунт безвозвратно.

Ответ: `204 No Content`.

### POST `/auth/password-reset/start`
Запрос кода для сброса пароля (доставка в Telegram, см. `/register/start`).
```json
{ "phone": "+375291234567", "channel": "telegram" }
```
Ответ:
```json
{
  "message": "На телефон отправлен код",
  "resend_after_seconds": 60,
  "deep_link": null
}
```
Если телефон не найден/не подтверждён/деактивирован — ответ тот же (`deep_link: null`,
код никуда не уходит), чтобы нельзя было по ответу узнать, существует ли номер в системе.

> **`deep_link` здесь всегда `null`.** Сброс пароля больше не заводит новую связку
> с ботом: код уходит только в уже подтверждённый Telegram владельца аккаунта, а
> если связки нет — не уходит никуда.
>
> Так закрыт путь к захвату аккаунта: эндпоинт открыт без авторизации, и раньше при
> отсутствии связки для запрошенного канала он создавал рукопожатие и **возвращал
> токен привязки прямо в ответе**. Атакующему было достаточно запросить сброс на
> чужой номер с каналом, который жертва не подключала, открыть полученную ссылку в
> своём мессенджере — и код сброса пароля приходил ему. Не сработало только потому,
> что Viber не был настроен; с его включением это стало бы рабочим захватом.
> Новые связки теперь заводятся исключительно при регистрации, где номер
> подтверждается контактом из Telegram.
>
> Побочный эффект: пользователь, у которого связки нет вообще (например, заблокировал
> бота), сбросить пароль сам не сможет — только через администратора.

### POST `/auth/change-phone/request`

## Рут `upload` — загрузка файлов

Все эндпоинты требуют Bearer-токен. Принимают `multipart/form-data`.

### POST `/upload/attachment`
Загрузка вложения. Принимает **любой MIME-тип** — лимитов по формату нет. Лимит размера — 500 МБ.

Директория сохранения определяется по MIME-типу:
- `image/*` → `/static/photos/`
- `video/*` → `/static/videos/`
- `audio/*` → `/static/voices/`
- всё остальное → `/static/files/`

Ответ:
```json
{ "url": "/static/photos/abc123.jpg" }
```

Ошибки:
- `413` — файл превышает 500 МБ

---

### POST `/upload/voice`
Загрузка голосового сообщения.

| Форматы | Лимит |
|---|---|
| ogg, mp3, m4a, wav, webm, aac | 25 МБ |

`audio/webm` и `video/webm` (Chrome/Firefox запись) поддерживаются напрямую.

Ответ:
```json
{ "url": "/static/voices/abc123.ogg" }
```

Ошибки:
- `415` — неподдерживаемый MIME-тип файла
- `413` — файл превышает лимит размера

---

### GET `/upload/download?url={file_url}`
Скачать любой файл (фото, документ, видео, голосовое) с заголовком `Content-Disposition: attachment`. Требует Bearer-токен.

Параметр `url` — значение поля `file_url` из вложения или `url` из фото, например `/static/photos/abc123.jpg`.

- `400` — URL не указывает на загруженный файл
- `404` — файл не найден на диске

---

### POST `/upload/transcribe`
Распознать голосовое сообщение в текст через Yandex SpeechKit. Требует настроенных `YANDEX_FOLDER_ID` и `YANDEX_API_KEY`.

Тело запроса (JSON):
```json
{ "file_url": "/static/voices/abc123.ogg" }
```

Ответ:
```json
{ "text": "распознанный текст сообщения" }
```

Принимает любой формат, который умеет читать `ffmpeg` (`ogg/opus`, `webm`, `mp3`, `m4a`, `aac`, `wav` и т.д.) — сервер сам перекодирует файл в OGG/Opus перед отправкой в Yandex, поэтому реальный контейнер/кодек присланного файла значения не имеет. Файл должен быть предварительно загружен через `POST /upload/voice`.

**Размер файла (после перекодирования) обрабатывается гибридно:**
- **≤ 1 МБ** (примерно 30-60 сек записи) — синхронное распознавание (`stt:recognize`), ответ обычно за 1-3 секунды.
- **> 1 МБ** — асинхронное распознавание (`longRunningRecognize`): файл временно загружается в Yandex Object Storage (бакет приватный, доступ для Yandex через presigned URL на 1 час), сервер сам дожидается результата (поллинг, до ~100 сек) и удаляет файл из Object Storage по завершении. Для фронта это прозрачно — ответ остаётся `{ text }`, просто запрос может идти дольше. Требует дополнительно настроенных `YANDEX_STORAGE_BUCKET`, `YANDEX_STORAGE_ACCESS_KEY_ID`, `YANDEX_STORAGE_SECRET_ACCESS_KEY`.

Эндпоинт **stateless**: ничего не сохраняет в БД, не привязан к чату/сообщению — принимает любой `file_url` из `/static/voices/...` и просто возвращает текст. Повторный вызов — повторное распознавание.

Ошибки:
- `400` — некорректный URL, либо файл не распознан как аудио (ffmpeg не смог его обработать)
- `404` — файл не найден
- `503` — Yandex SpeechKit/Object Storage недоступны, не настроены, вернули ошибку, либо распознавание не уложилось в таймаут (для очень длинных записей)

## Рут `admin: cabinets` — управление ШУ (только админ)

### POST `/admin/cabinets`
Создание нового ШУ. **`project_id` обязателен** — ничейных ШУ больше не заводится,
каждый ШУ создаётся сразу внутри проекта. `404`, если проект не найден или удалён.
```json
{
  "project_id": 3,
  "type": "вентиляционная установка",
  "object_number": "29_099",
  "description": "Описание",
  "warranty_starts_at": "2025-01-01T00:00:00Z",
  "warranty_ends_at": "2027-01-01T00:00:00Z",
  "admin_internal_name": "ШУ-18К",
  "admin_comment": "Комментарий для внутреннего использования",
  "purpose": "Вентиляция",
  "latitude": 53.9045,
  "longitude": 27.5615
}
```
`latitude` (-90…90) и `longitude` (-180…180) — необязательны, геолокация ШУ на карте.
`warranty_starts_at`/`warranty_ends_at` — тоже необязательны (можно не указывать вообще, если у ШУ нет гарантии); если заданы оба — `warranty_ends_at` должен быть позже `warranty_starts_at`.

При создании — то же самое, что делает `PATCH /admin/cabinets/{id}/project` при
привязке уже существующего ШУ: участники проекта сразу получают доступ (без
заявок), и на NAS заводится папка ШУ внутри папки проекта.

> Позже отвязать ШУ от проекта (`PATCH .../project` с `{ "project_id": null }`)
> по-прежнему можно — ограничение только на создание, не на дальнейшее управление.

**Поле `type`:**
- Приводится к нижнему регистру автоматически (`"Вентиляция"` = `"вентиляция"`)
- Если тип новый — создаётся тег `scope="cabinet_type"` автоматически
- На фронте: получить список готовых типов через `GET /tags?scope=cabinet_type` и показать выпадающий список

Ответ — полная информация о созданном ШУ включая `tags`.

---

### GET `/admin/cabinets`
Список всех ШУ. Доступно оператору и администратору. Параметры:
- `search` — поиск по типу, номеру объекта, названию, назначению, описанию, комментарию
- `tag_ids` — фильтр по тегам (`?tag_ids=1&tag_ids=2`)
- `has_documents` — `true` / `false` — есть ли документы
- `has_photos` — `true` / `false` — есть ли фото
- `has_users` — `true` / `false` — есть ли привязанный пользователь
- `has_service_requests` — `true` / `false` — есть ли сервисные заявки
- `warranty_status` — `active` (действует, срок > 30 дней) / `expiring_soon` (истекает в течение 30 дней) / `expired` (истекла) / `none` (гарантия не указана вообще)
- `has_project` — `true` / `false` — привязан ли ШУ к какому-либо проекту (`project_id is not null`)
- `project_id` — точная привязка к конкретному проекту (`?project_id=3`) — например, для отображения карточек ШУ на странице проекта (полноценных, с гарантией/тегами/т.п.), в отличие от урезанного `cabinets[]` из `GET /admin/projects/{id}`
- `sort_by` — `type`, `warranty_ends_at`, `object_number`, `admin_internal_name`, `purpose`, `created_at`
- `sort_order` — `asc`, `desc`
- `page`, `size` — пагинация (по умолч. `1` / `20`, максимум `100`)

Каждый элемент содержит:
```json
{
  "id": 1,
  "type": "Вентиляционная установка",
  "object_number": "29_099",
  "purpose": "Вентиляция",
  "warranty_starts_at": "2025-01-01T00:00:00Z",
  "warranty_ends_at": "2027-01-01T00:00:00Z",
  "warranty_status": "active",
  "admin_internal_name": "ШУ-18К",
  "admin_comment": "Внутренний комментарий",
  "tags": [{ "id": 2, "name": "Электрика", "scope": "cabinet" }],
  "project_id": 3,
  "project_name": "Бизнес-центр Космос",
  "created_at": "2026-05-01T10:00:00Z"
}
```
`warranty_status`: `active`, `expiring_soon` (≤30 дней), `expired`, `none` (гарантия не указана — `warranty_starts_at`/`warranty_ends_at` оба `null`).
`warranty_starts_at`/`warranty_ends_at` в самом ШУ — `null`, если гарантия не указана.
`project_id`/`project_name` — `null`, если ШУ не привязан ни к одному проекту.

---

### GET `/admin/cabinets/geo`
Лёгкий endpoint для карты — возвращает **все** ШУ одним запросом без пагинации. Параметры (фильтры под легенду меток на карте):
- `warranty_status` — `active` / `expiring_soon` / `expired` / `none` (те же 4 состояния, что и в `GET /admin/cabinets`)
- `has_open_requests` — `true` / `false` — есть ли новая (открытая) сервисная заявка

Ответ (`list[CabinetGeoItem]`):
```json
[
  {
    "id": 3,
    "object_number": "29_099",
    "admin_internal_name": "Главная подстанция",
    "warranty_status": "active",
    "latitude": 53.9,
    "longitude": 27.56,
    "has_open_requests": true
  }
]
```

`warranty_status`: `active` | `expiring_soon` | `expired` | `none`.
`has_open_requests`: есть ли хотя бы одна сервисная заявка со статусом `open`.  
ШУ без координат тоже включены (`latitude`/`longitude` = `null`) — фронт фильтрует сам.

---

### GET `/admin/cabinets/{cabinet_id}`
Детальная информация о ШУ с тегами. Ответ (`CabinetOut`) включает `project_id`/`project_name` (оба `null`, если ШУ не привязан к проекту) — это единственный источник истины для отображения проекта в карточке ШУ, независимо от того, откуда её открыли (из общего списка или со страницы проекта).

---

### PATCH `/admin/cabinets/{cabinet_id}`
Обновление данных ШУ (все поля опциональны, в т.ч. `latitude` и `longitude`). Возвращает обновлённый ШУ с тегами.

---

### PUT `/admin/cabinets/{cabinet_id}/tags`
Привязать теги к ШУ (полная замена). Только для администратора.
```json
{ "tag_ids": [1, 2] }
```
Пустой список снимает все теги. `204 No Content`.

> Рекомендуется привязывать теги со `scope="cabinet"` (на фронте — выбирать из `GET /tags?scope=cabinet`), но сервер не проверяет `scope` тега при сохранении.

---

### PATCH `/admin/cabinets/{cabinet_id}/project`
Привязать или отвязать ШУ к проекту. Только для администратора.
```json
{ "project_id": 3 }
```
Отвязка — `{ "project_id": null }`. `204 No Content`.

Это **чисто административная группировка** — привязка/отвязка шкафа к проекту никак не меняет существующих владельцев `user_cabinets`. Единственный побочный эффект: если у проекта уже есть участники, каждый из них сразу получает доступ к привязываемому шкафу (в т.ч. если шкаф уже занят посторонним) — без дополнительных заявок, само админское действие достаточно. См. подробности в разделе «Рут `admin: projects`».

---

### DELETE `/admin/cabinets/{cabinet_id}`
Удаление ШУ. `204 No Content`.

**Soft-delete**: запись не стирается из БД, а помечается `deleted_at`. Удалённый ШУ:
- пропадает из `GET /admin/cabinets`, `GET /admin/cabinets/geo` и общего поиска;
- нельзя привязать через одобрение заявок (`POST /admin/cabinet-requests/additions/{id}/approve` и `.../shares/{id}/approve` вернут 404, даже если заявка была создана до удаления);
- не участвует в проверке истечения гарантии (warranty-уведомления не шлются).

Уже существующие привязки пользователей, чаты и заявки на обслуживание по удалённому ШУ не затрагиваются — данные и история сохраняются.

---

### GET `/admin/cabinets/{cabinet_id}/users`
Список пользователей, привязанных к ШУ. Доступно оператору и админу.
```json
[
  {
    "user_id": 1,
    "full_name": "Иванов Иван",
    "phone": "+375291234567",
    "user_type": "individual",
    "is_primary": true,
    "custom_name": "Мой шкаф",
    "added_at": "2026-05-12T10:00:00Z"
  }
]
```

---

### DELETE `/admin/cabinets/{cabinet_id}/users/{user_id}`
Отвязать пользователя от ШУ с указанием причины. Только для админа. Логируется в `audit_log`.
```json
{ "reason": "Причина отвязки" }
```
Ответ: `204 No Content`.

`cabinet_id` — `null` пока заявка не одобрена.

```json
{
  "cabinet_id": 5,
```

### GET `/admin/cabinet-requests/shares`
Заявки на доступ к уже существующему ШУ (сканирован QR, но ШУ уже занят). Параметры:
- `status` — `pending` / `approved` / `rejected`
- `resolved_by_admin_id` — заявки, обработанные конкретным администратором
- `search` — поиск по ФИО/телефону пользователя, типу/номеру/названию ШУ, комментарию пользователя и ответу администратора
- `sort_by` — `created_at` (по умолч.), `resolved_at`, `status`, `user_full_name`, `cabinet_object_number`
- `sort_order` — `asc` / `desc`
- `page`, `size`

```json
{
  "items": [
    {
```

### POST `/projects/add-by-qr`
Привязка проекта через QR-код.
```json
{ "qr_data": "savt://project/A3F7BC1254E8D9F0" }
```

Логика:
- Проект не найден → `404`
- Уже привязан → `409`
- Нет первичного владельца → мгновенная привязка (`status: "linked"`), плюс пользователь
  сразу получает все свободные шкафы проекта; на шкафы, уже занятые кем-то другим,
  тихо создаются отдельные заявки (`admin/cabinet-requests/shares`), не блокируя
  остальное.
- Есть владелец → заявка на доступ к проекту (`status: "request_submitted"`),
  нужно одобрение администратора (`admin/project-requests`). После одобрения
  пользователь получает доступ **сразу ко всем** шкафам проекта, включая занятые
  посторонними — второй заявки на конкретный шкаф не требуется.
- Заявка уже есть → `409`

Ответ:
```json
{ "status": "linked", "message": "Проект успешно привязан" }
```

> После `status: "linked"` фронту стоит обновить и `GET /cabinets` — в аккаунт могли добавиться новые шкафы, помимо самого проекта.

## Рут `admin: projects` — управление проектами (только админ)

> **Ручного создания проекта больше нет.** `POST /admin/projects` убран — проект
> заводится **только** сделкой Bitrix (`ONCRMDEALADD`/`ONCRMDEALUPDATE`, см.
> `bitrix_webhook_service.upsert_project_from_deal`, либо разовый импорт
> `app/cli.py import-bitrix-deals`). Переименование сделки в Bitrix переименовывает
> и проект — `name` больше не принимается и через `PATCH` (см. ниже).
>
> **Удаление в приложении не окончательно, пока жива сделка.** `DELETE
> /admin/projects/{id}` — soft-delete как обычно, но если по этому же
> `production_number` позже прилетит `ONCRMDEALUPDATE` (почти любое изменение
> сделки), проект **воскрешается** автоматически: `deleted_at` снимается, папка
> пересинхронизируется. Шкафы/чаты/привязки пользователей нигде не терялись — при
> soft-delete они не трогаются, так что после воскрешения всё на месте.
> Единственный способ удалить проект насовсем — закрыть/удалить и саму сделку в
> Bitrix (после чего в приложении её уже никто не тронет — обратной синхронизации
> удаления из Bitrix нет, см. ниже).

При создании (в том числе через Bitrix-вебхук) сервер автоматически заводит на NAS (если настроен `PROJECT_FOLDERS_ROOT`, см. переменные окружения) папку с шаблонной структурой — внутри **годовой папки**, как разложено в Bitrix:
```
📁 !2026/                             ← год проекта; в корне лежат только такие папки
└── 📁 Название_проекта/              ← корень проекта, основная документация
    ├── 📁 _Проект/                   ← схемы, ТЗ на сборку
    ├── 📁 _Программа/
    │   ├── 📁 SCADA/
    │   ├── 📁 ПЛК/
    │   └── 📁 HMI/
    ├── 📁 _Маркировка/
    │   ├── 🖼️ QR.png                 ← QR-код проекта (savt://project/{unique_code}), для печати и наклейки на объект
    │   ├── 📁 Облако/
    │   ├── 📁 Coral/
    │   └── 📁 Wago/
    ├── 📁 _Руководство/
    ├── 📁 Фото/
    ├── 📁 _Доп.информация/
    └── 📁 Переписка/
```

**Год берётся из производственного номера**: `26_170` → `!2026`, `25_003` → `!2025`. У проектов без номера (сейчас это только исторические записи, заведённые ещё когда ручное создание существовало) берётся год создания записи, чтобы в корне не появлялось исключений и он оставался только из годовых папок. Восклицательный знак — чтобы годовые папки всплывали над остальным при сортировке по имени.

Вложенный проект (`parent_project_id` задан) получает свою полную папку-шаблон **внутри** папки родителя, а не отдельной папкой верхнего уровня. Годовую папку ему определяет **корень ветки**: даже если номера разошлись, вложенный проект не уезжает в другой год отдельно от родителя.

Создание папки — фоновая, best-effort операция: сбой сети/NAS не роняет создание проекта, недостающее досоздаст ближайший ночной прогон синхронизации (см. ниже), включая сам файл `QR.png`, если он был случайно удалён с диска.

> **Переезд существующих папок.** Проекты, заведённые до появления годовых папок, лежат плоско в корне. Их папки переезжают сами — на ближайшей ночной сверке или по кнопке `POST /admin/projects/{id}/sync-folder`. В пределах одной шары это переименование: запись каталога перемещается, файлы не копируются, ссылки внутри не рвутся. Переименование проекта и переезд выполняются **одним** движением, иначе переименованный до переезда проект не нашёлся бы ни по старому пути, ни по новому.
>
> На проекты с истёкшей гарантией ограничение `is_sync_eligible` **не распространяется**: сверка им не нужна, но папка всё равно переедет в свою годовую — иначе основная часть архива навсегда осталась бы в корне. Пустых папок при этом не создаётся: нет папки на диске — нечего и переносить.
>
> Единственный случай, когда перенос не делается автоматически: **два активных проекта с одинаковым `folder_name`**. По имени не определить, чья папка в корне, и достаться она могла бы любому — вместе с чужими файлами. Такой проект пропускается с `WARNING` в логе, папку переносят руками.

### GET `/admin/projects`
Список всех проектов. Доступно оператору и администратору.

**Поиск** — `search`. Ищет по карточке проекта и по контактным лицам заказчика: название, производственный номер, компания, ФИО и должность контакта, его телефоны и почты. Нечёткий (`pg_trgm`), как и остальные поиски в проекте: опечатки и разные разделители переживает.

**Фильтры по самому проекту:**

| Параметр | Что отбирает |
|---|---|
| `year` | год проекта: из производственного номера (`26_170` → 2026), у заведённых вручную — по дате создания. Тот же год, по которому разложены папки на NAS |
| `company` | компания-заказчик (нечётко) |
| `shipped` | `true` — отгружённые (заполнена фактическая дата), `false` — ещё нет |
| `shipment_planned_from` / `shipment_planned_to` | диапазон плановой даты отгрузки |
| `shipment_actual_from` / `shipment_actual_to` | диапазон фактической даты отгрузки |
| | *формат — календарная дата `YYYY-MM-DD`, ровно то, что даёт `input[type=date]`. Обе границы **включающие**: `...to=2026-08-15` забирает весь день 15-го. Время не принимается — сутки трактуются по UTC* |
| `has_project_documents` | есть ли документы, привязанные к проекту напрямую (не к его ШУ) |
| `has_project_photos` | есть ли фотографии проекта |
| `has_project_users` | есть ли участники проекта |
| `has_contacts` | подтянулись ли из сделки контактные лица |
| `warranty_status` | по гарантии **самого проекта**: `active` / `expiring_soon` (≤30 дней) / `expired` / `none` |

**Фильтры по шкафам проекта** — проект попадает в выдачу, если условиям соответствует **хотя бы один** его шкаф: `tag_ids`, `has_documents`, `has_photos`, `has_users`, `has_service_requests`, `cabinet_warranty_status` (те же, что в `GET /admin/cabinets`).

Заданные вместе, оба набора складываются по И: `?year=2026&has_service_requests=true` — проекты 2026 года, у которых хотя бы по одному шкафу заводили заявку.

> **Изменение поведения.** Раньше `warranty_status` фильтровал по гарантии **шкафов**, хотя одноимённое поле в ответе показывало гарантию **проекта** — фильтр и колонка расходились. Теперь `warranty_status` относится к проекту и совпадает с тем, что видно в списке, а прежнее поведение доступно как `cabinet_warranty_status`.

**Сортировка** — `sort_by`: `name`, `created_at` (по умолч.), `production_number`, `year`, `company_name`, `shipment_planned_at`, `shipment_actual_at`, `warranty_ends_at`, `cabinet_count`. `sort_order` — `asc` / `desc`.

> Сортировка **всегда по полям проекта** — эндпоинт возвращает проекты, а не шкафы, поэтому строку упорядочить больше нечем. В частности `warranty_ends_at` — это гарантия самого проекта и при включённом `cabinet_warranty_status` тоже: фильтр отбирает проекты по шкафам, но сортируются отобранные всё равно по своей гарантии. У проекта много шкафов с разными датами, одной «гарантии по шкафам» у строки просто нет. Пустые значения всегда уходят в конец в обе стороны: проект без даты отгрузки не занимает верх списка, отсортированного по ней. При равных значениях порядок стабильный (по `id`), поэтому строки не «прыгают» между страницами.

`page`, `size` — постранично.

```json
{
  "items": [
    {
      "id": 3, "name": "Бизнес-центр Космос", "unique_code": "A3F7BC1254E8D9F0",
      "production_number": "26_170", "year": 2026,
      "cabinet_count": 5, "created_at": "2026-05-01T10:00:00Z",
      "company_name": "ООО Ромашка",
      "shipment_planned_at": "2026-08-15T00:00:00Z",
      "shipment_actual_at": null,
      "warranty_ends_at": "2028-08-24T00:00:00Z",
      "warranty_status": "active"
    }
  ],
  "total": 1, "page": 1, "size": 20, "pages": 1
}
```
`cabinet_count` — общее число шкафов в проекте, **не зависит** от переданных фильтров (фильтры влияют только на то, попадёт ли сам проект в выдачу).
`year` считается по тому же правилу, что и годовая папка на NAS, — фильтр, выдача и раскладка на диске не расходятся.

### GET `/admin/projects/{project_id}`
Подробности проекта (без ограничений по владению — админский вид). Параметры:
- `tag_ids`, `has_documents`, `has_photos`, `has_users`, `has_service_requests`, `warranty_status` — те же фильтры, что и в `GET /admin/cabinets` — но здесь фильтруют, какие шкафы попадут в поле `cabinets` ответа (сам проект находится всегда по ID, независимо от фильтров)

```json
{
  "id": 3,
  "name": "Бизнес-центр Космос",
  "unique_code": "A3F7BC1254E8D9F0",
  "parent_project_id": null,
  "folder_synced_at": "2026-07-29T02:00:00Z",
  "cabinets": [
    { "id": 5, "type": "Вентиляционная установка", "object_number": "29_099", "admin_internal_name": "ШУ-18К" }
  ],
  "production_number": "26_170",
  "shipment_planned_at": "2026-08-24T12:26:00+03:00",
  "shipment_actual_at": null,
  "company_name": "ООО Ромашка",
  "contacts": [
    {
      "id": 12, "full_name": "Иванов Иван Иванович", "post": "Главный энергетик",
      "phones": ["+375291234567", "+375172001122"], "emails": ["ivanov@romashka.by"]
    }
  ],
  "warranty_starts_at": "2026-08-24T00:00:00Z",
  "warranty_ends_at": "2028-08-24T00:00:00Z",
  "warranty_status": "active",
  "created_at": "2026-05-01T10:00:00Z",
  "updated_at": "2026-05-01T10:00:00Z"
}
```
`cabinets` — уже отфильтрован сервером переданными параметрами (без параметров — все шкафы проекта).
`parent_project_id` — родительский проект, если этот вложен в другой (`null`, если проект верхнего уровня).
`folder_synced_at` — когда последний раз успешно прошла синхронизация папки проекта на NAS (`null`, если ни разу или `PROJECT_FOLDERS_ROOT` не настроен).

**Из Bitrix, только для чтения:** `production_number`, `shipment_planned_at`,
`shipment_actual_at`, `company_name`, `contacts`. Обновляются на каждом изменении

сделки — исчезнет и здесь.

**Наше, редактируется:** `warranty_starts_at`, `warranty_ends_at` — см. `PATCH` ниже.

### POST `/admin/projects/{project_id}/sync-folder`
Синхронизировать папку проекта на NAS прямо сейчас — то же, что делает ночной прогон,
но по кнопке. Доступно оператору и администратору.

Ответ — `SyncFolderResultOut`, **не** `ProjectOut`: кнопку нажимают, чтобы узнать, что
именно сделалось, а карточка проекта от сверки не меняется. `message` — готовая фраза
для тоста, собрана на сервере, чтобы клиенты не составляли её каждый по-своему.

```json
{ "synced_at": "2026-08-03T14:22:00Z", "imported_documents": 2,
  "message": "Подхвачено новых файлов из папки: 2" }
```

Что делает: досоздаёт недостающие подпапки шаблона, переименовывает корневую папку
если разошлось название, переносит её в годовую папку если она ещё в корне,
докладывает зеркала документов и фото — и **подхватывает файлы, положенные в папку
напрямую** (документы из корня, фото из подпапки «Фото» — см. ниже).

В отличие от ночного прогона **не смотрит на гарантию**: раз администратор нажал
кнопку осознанно, синхронизируется даже проект с истёкшей гарантией.

`404` — проект не найден либо не настроен `PROJECT_FOLDERS_ROOT`.

#### Что оказывается в папке проекта

Синхронизация раскладывает по шаблонным подпапкам не только документы:

```
!2026/26_170 Промжилстрой/
  _Проект/  _Программа/  _Маркировка/  _Руководство/  _Доп.информация/
  Схема проекта.pdf              ← документы проекта, в корне
  Фото/
    001 Фасад щита.jpg           ← фотографии проекта, номер держит порядок
    002 Фото 2.jpg
    003 Со стройки.jpg           ← или подхвачено обратно с диска (см. ниже)
  Переписка/
    Чат проекта — Иванов Иван.txt
    вложения/
      2_Схема.pdf                ← префикс = id сообщения
  29_099 ШУ-18К/                 ← папка ШУ, тот же шаблон подпапок
    _Проект/  _Программа/  ...
    Фото/                        ← фотографии этого ШУ
    Переписка/
      Чат ШУ — Иванов Иван.txt
      Заявка 12 — Иванов Иван.txt
```

**Папка ШУ** создаётся сразу при привязке шкафа к проекту
(`PATCH /admin/cabinets/{id}/project`) и досоздаётся на каждой синхронизации.
При отвязке или переносе в другой проект старая папка **не переносится и не
удаляется** — в ней могут лежать файлы, положенные вручную; новая просто создаётся
на новом месте. Так же, как со сменой родителя у проекта.

**Стенограммы переписки** — по файлу на чат, в формате «дата, автор, текст»:

```
Чат проекта — Иванов Иван
Выгружено: 03.08.2026 13:21 UTC

[01.08.2026 10:15] Иванов Иван: Не работает вентилятор
[01.08.2026 10:16] Ася: Посмотрите схему
    [вложение: Схема.pdf]
[01.08.2026 10:20] Иванов Иван: (сообщение удалено)
```

Стенограммы **перезаписываются** на каждой сверке: переписка растёт, и собрать файл
заново проще и надёжнее, чем дописывать хвост. Вложения и фотографии наоборот
копируются **один раз** — уже лежащий на NAS файл не трогается, чтобы не затирать
то, что могли переименовать или дополнить вручную.

> Имя фото на NAS (`cabinet_photos.nas_filename`) запоминается один раз при
> первом экспорте, а не пересчитывается из подписи на каждой сверке. Смена
> подписи в приложении **не** переименовывает и не дублирует файл на диске —
> старая копия просто продолжает использоваться под прежним именем.

Перезаписываются, впрочем, не все: чат пропускается, если после прошлой сверки
(`projects.folder_synced_at`) в нём никто не писал **и** файл стенограммы уже лежит
на месте. Удалили файл руками — соберётся заново. На проекте с десятками чатов это
и есть основная экономия: читается только то, что изменилось.

**Заявка выгружается сразу при закрытии.** Закрытие архивирует чат заявки (он
становится read-only), поэтому ждать ночной сверки незачем — стенограмма
`Заявка {id} — {ФИО}.txt` пишется в папку ШУ или проекта в тот же момент. На
ближайшей сверке этот чат будет пропущен как неизменившийся.

Личные заметки (`notes`) в выгрузку не попадают: они не привязаны ни к проекту, ни
к ШУ, и это приватное пространство пользователя.

#### Файл положили в папку напрямую

Файл, скопированный в **корень** папки проекта мимо приложения, при следующей
синхронизации (ночной или по кнопке) заводится как документ проекта: копия кладётся
в `/uploads`, документ появляется в `GET /projects/{id}/documents` и скачивается как
обычно. Название берётся из имени файла, `doc_type` и `mime_type` определяются сами.

Сканируется **только корень**. Вложенные папки шаблона (`_Проект`, `_Программа`,
`Переписка` и т.п.) не трогаются: файлы там разложены осмысленно, и
сваливать их в плоский список документов означало бы потерять эту структуру.
Временные файлы Office (`~$…`) пропускаются.

> Подхваченный документ запоминает **фактическое имя файла** в папке
> (`documents.nas_filename`). Без этого сверка была бы неустойчивой: имя зеркала
> вычисляется из названия документа, и файл с длинным или «неудобным» именем не
> совпал бы сам с собой — и забирался бы заново при каждом прогоне.

**Подпапка `Фото`** — исключение из правила «только корень»: файлы, положенные
туда напрямую (и в папке проекта, и в папке каждого ШУ), на той же сверке
заводятся как `CabinetPhoto` — появляются в `GET /cabinets/{id}/photos`.
Название без числового префикса и расширения становится подписью (`caption`).
Не-изображения (по mime-типу) в `Фото` пропускаются молча — не заводится ничего.
Как и у документов, реальное имя файла запоминается (`cabinet_photos.nas_filename`),
так что подхваченный файл не заводится повторно на следующей сверке, а смена
подписи в приложении задним числом файл на диске не переименовывает.

**Удаление фото — двустороннее** (в отличие от документов, где пропавший
зеркальный файл просто восстанавливается копией из `/uploads`):
- **Удалили фото в приложении** (`DELETE /admin/photos/{photo_id}`) — файл
  убирается и из `Фото` на NAS, фоново, тем же запросом.
- **Удалили файл из `Фото` на диске** — на следующей сверке (ночной или по
  кнопке) `CabinetPhoto` удаляется и в приложении, а не восстанавливается.
  Действует только для уже синхронизированных фото (`nas_filename` заполнен);
  на итоговое поведение это не влияет — для только что добавленных, ещё ни
  разу не попадавших на NAS, восстанавливать пока и нечего.

**Редактирование:**
- **Подпись/порядок в приложении** (`PATCH /admin/photos/{photo_id}`) —
  правится только в БД. Имя файла на NAS не меняется вслед за новой подписью
  (см. выше про `nas_filename`) — это осознанно, не баг.
- **Заменили содержимое файла на диске под тем же именем** — подхватывается:
  сверка сравнивает mtime файла с сохранённым (`cabinet_photos.nas_mtime`), и
  при расхождении перезаливает новое содержимое в `/uploads`, обновляя `url`
  фото. `caption`/`sort_order` при этом не трогаются — это поля приложения, не
  диска. Разница меньше 2 секунд не считается изменением (запас на грубость
  mtime у сетевых шар).

### PATCH `/admin/projects/{project_id}`
Смена родителя и гарантия. Все поля опциональны — передавать только изменённые.
```json
{
  "parent_project_id": null,
  "warranty_starts_at": "2026-08-24T00:00:00Z",
  "warranty_ends_at": "2028-08-24T00:00:00Z"
}
```
> **`name` сюда не принимается.** Название — из Bitrix (title сделки), правится
> только там; здесь правка молча затёрлась бы на ближайшем `ONCRMDEALUPDATE`. Папка
> на NAS переименовывается автоматически вслед за сделкой (фоново), как и раньше.

- Смена `parent_project_id` — `404`, если родитель не найден; `409`, если это создаст цикл (проект не может быть вложен сам в себя, в т.ч. через цепочку). **Папка на NAS при смене родителя не переносится автоматически** — если она уже была создана, её нужно перенести на диске вручную, сервер только меняет связь в БД (и пишет предупреждение в лог).
- **Гарантия** — единственное, что администратор реально задаёт руками: в CRM такого поля нет.

> ⚠️ **`warranty_ends_at` управляет ночной синхронизацией папок на NAS.** Если она
> задана и уже истекла (плюс неделя запаса) — папка проекта перестаёт
> синхронизироваться. Пока поле пустое, отбор идёт как раньше: по крайней дате
> среди гарантий ШУ проекта. Подробности — в разделе «Поля сделки в карточке проекта».

Поля из Bitrix (`shipment_*`, `company_name`, `production_number`, `contacts`) этот
эндпоинт **не принимает**: они перезаписываются на каждом изменении сделки, и любая
правка была бы молча потеряна.

### POST `/admin/projects/sync-folders`
Синхронизировать папки **всех** активных проектов одним запросом — то же самое,
что делает ночной прогон, но по кнопке, без ожидания до 2:00 и без похода в
каждый проект отдельно. Доступно оператору и администратору.

В отличие от `POST /admin/projects/{project_id}/sync-folder` (один конкретный
проект) ограничение по гарантии здесь **сохраняется** — иначе на большом
архиве кнопка запускала бы полную сверку сотен давно закрытых проектов зря.
Проекты с истёкшей гарантией только переезжают в свою годовую папку, без
полной сверки (как и в ночном прогоне).

```json
{
  "total_projects": 42,
  "synced_projects": 38,
  "relocated_projects": 3,
  "failed_projects": 1,
  "message": "Проектов всего: 42 — синхронизировано: 38, перенесено без полной сверки (гарантия истекла): 3, с ошибкой: 1"
}
```

Ошибка на одном проекте (например, недоступна сеть до NAS) не останавливает
прогон остальных — считается в `failed_projects`, дальше обработка продолжается.
`404` — не настроен `PROJECT_FOLDERS_ROOT`.

### Автоматическая синхронизация папок

Ручной запуск — `POST /admin/projects/{project_id}/sync-folder` (один проект) или
`POST /admin/projects/sync-folders` (все проекты разом), описаны выше.

> Исключение — **раскладка по годам**: она делается и для проектов с истёкшей гарантией. Сверять там нечего, но папка переезжает в свою годовую, иначе весь архив остался бы в корне.

## Рут `admin: phone change requests` — заявки на смену номера (просмотр — оператор/админ, решение — только админ)

Смена номера телефона идёт только так — самостоятельной больше нет, см.
`POST /auth/change-phone/request`.

> **Ответственность на администраторе.** Система подтвердить владение номером не
> может: SMS отключены, а мессенджер-связка привязана к `user_id`, а не к номеру.
> Перед одобрением нужно убедиться во владении вне системы — позвонить на новый
> номер, сверить документы организации и т.п. Одобрение меняет номер немедленно,
> а номер — это логин пользователя.

### GET `/admin/phone-change-requests`
Список заявок. Параметры: `status` (`pending`/`approved`/`rejected`/`cancelled`),
`resolved_by_admin_id`, `search` (по ФИО, текущему телефону, запрошенному номеру,
организации), `sort_by` (`created_at`/`resolved_at`/`status`/`user_full_name`),
`sort_order`, `page`, `size`.

Элемент списка — поля заявки плюс данные заявителя и `pending_rivals`:
```json
{
  "id": 12,
  "user_id": 5,
  "new_phone": "+375291234568",
  "old_phone": "+375291234567",
  "user_comment": "Сменил оператора связи",
  "status": "pending",
  "admin_response": null,
  "resolved_by_admin_id": null,
  "created_at": "2026-07-31T10:00:00Z",
  "resolved_at": null,
  "user_full_name": "Иванов Иван",
  "user_type": "individual",
  "organization_name": null,
  "user_is_verified": true,
  "user_registered_at": "2026-01-15T08:00:00Z",
  "pending_rivals": 1
}
```
`pending_rivals` — сколько всего необработанных заявок на **этот же номер**, включая
текущую. Значение `> 1` означает, что на номер претендует несколько аккаунтов —
повод разобраться, а не одобрять первую попавшуюся. На фронте стоит подсветить.

### POST `/admin/phone-change-requests/{request_id}/approve`
Одобрить — номер меняется сразу. Только админ.
```json
{ "admin_response": "Проверено звонком" }
```
`admin_response` необязателен. Ответ: `204 No Content`.

Занятость номера перепроверяется **на момент одобрения**, а не только подачи:
владелец мог сам зарегистрироваться, пока заявка ждала → `409`.

Пользователю уходит уведомление (тип `request_status`) о том, что вход теперь по
новому номеру. Сессии при этом не отзываются: номер — идентификатор входа, а не
пароль, выданные токены остаются валидными.

### POST `/admin/phone-change-requests/{request_id}/reject`
Отклонить. Только админ. `admin_response` обязателен (1–1000 символов) — причина
уходит пользователю в уведомлении.
```json
{ "admin_response": "Не удалось подтвердить владение номером" }
```
Ответ: `204 No Content`.

Оба действия пишутся в журнал (`admin: audit`) как `phone_change_request.approve` /
`phone_change_request.reject` со старым и новым номером.

### POST `/admin/documents`
Загрузка документа. `multipart/form-data`.

| Поле | Тип | Обязательно |
|---|---|---|
| `file` | файл | ✅ |
| `cabinet_id` | int | ровно одно из `cabinet_id`/`project_id` |
| `project_id` | int | ровно одно из `cabinet_id`/`project_id` |
| `title` | string | нет (берётся имя файла) |
| `requires_approval` | bool | нет (по умолчанию `false`) |
| `is_internal` | bool | нет (по умолчанию `false`) |

`doc_type`, `mime_type`, `file_size_bytes` извлекаются автоматически. Если передать оба
поля или ни одного — `422`.

**`requires_approval` и `is_internal` — разные вещи, не путать:**

| | Виден пользователю в списке | Можно запросить доступ | Скачивание |
|---|---|---|---|
| обычный | ✅ | — | ✅ |
| `requires_approval` | ✅ (без ссылки) | ✅ | после одобрения |
| `is_internal` | ❌ **не виден вовсе** | ❌ | ❌ |

ни в одном ответе: он отсекается прямо в SQL-выборке, а `GET /documents/{id}/download`
и `POST /documents/{id}/request-access` отвечают `404` — как на несуществующий, чтобы
по коду ответа нельзя было узнать, что документ есть. Операторам и админам он виден
в `GET /admin/documents` как обычно.

Если задан `project_id` (и настроен `PROJECT_FOLDERS_ROOT`) — файл дополнительно (фоново,
best-effort) зеркалится в **корень** папки проекта на NAS, рядом с шаблонными подпапками
(см. «Рут `admin: projects`»). Источник истины для скачивания через API остаётся
`/code/uploads` — копия на NAS только для тех, кто открывает файлы напрямую с шары.

## Рут `chats` — чаты

Четыре типа чатов:
- `cabinet` — при привязке ШУ (по QR или одобрении заявки)
- `support` — при регистрации (общая поддержка с ботом)
- `notes` — при регистрации (личные заметки, видны только самому пользователю)
- `service_request` — автоматически при создании сервисной заявки (`POST /service-requests`), виден и пользователю, и операторам/админам. Бот (Ася) в чатах заявок не участвует — ни отвечает на сообщения, ни шлёт follow-up (`bot_active: false` по умолчанию, `chat_type` жёстко исключён из логики бота независимо от значения `bot_active`); ведёт переписку человек, сообщения заявителя дублируются в Bitrix (см. «Рут `service requests`»)

### GET `/chats`
Список чатов текущего пользователя. Параметры:
- `chat_type` — `cabinet` / `support` / `notes` / `service_request`, без параметра — все типы
- `archived` — `false` (по умолч.) — активные чаты; `true` — архив (папка «Архив», как в Telegram — чаты закрытых заявок)

```json
[
  {
    "id": 3,
    "chat_type": "cabinet",
    "cabinet_id": 5,
    "cabinet_name": "ШУ-18К",
    "cabinet_object_number": "29_099",
    "last_message_text": "Здравствуйте, помогите",
    "last_message_at": "2026-05-15T10:00:00Z",
    "unread_count": 2,
    "problem_status": "open",
    "bot_active": true,
    "operator_requested": false,
    "service_request_id": null,
    "service_request_type": null,
    "service_request_status": null,
    "service_request_description": null,
    "service_request_created_at": null,
    "archived_at": null
  }
]
```
`service_request_id`/`service_request_type`/`service_request_status`/`service_request_description`/`service_request_created_at` заполнены только для `chat_type: "service_request"` — этого достаточно, чтобы отличить в списке разные заявки одного и того же пользователя (тип, дата, текст обращения), не делая отдельный запрос к `GET /service-requests/{id}`.
`archived_at` — `null`, пока заявка не закрыта; при `status: "closed"` заполняется автоматически, при повторном открытии заявки — сбрасывается обратно в `null`. Архивный чат — read-only: `POST /chats/{chat_id}/messages` вернёт `403`, но история сообщений (`GET /chats/{chat_id}/messages`) остаётся доступна как обычно. Это только флаг состояния — сообщения физически никуда не переносятся.

## Realtime (SSE) для операторской панели

Замена поллинга (`GET /operator/chats` каждые 4с, `GET /operator/chats/{id}/messages` каждые 3с) на push через Server-Sent Events. Все мутации (отправка/редактирование/удаление сообщения, реакции, pin) остаются обычными REST-вызовами как раньше — SSE только уведомляет, что что-то изменилось.

**Почему SSE, а не WebSocket:** операторская панель ничего не шлёт по каналу, только слушает — SSE проще и не требует HTTP-апгрейда на уровне nginx.

> **Важно, если фронтенд — Next.js и ходит на бэкенд через `rewrites()` (`next.config.js`, например `/backend/:path* → API_URL/:path*`):** `rewrites()` в Next.js **не умеют стримить долгоживущие ответы** — SSE у него буферизуется целиком до закрытия соединения (в DevTools это выглядит как «EventStream появляется только после закрытия запроса, и она пустая»), а WebSocket-upgrade он не проксирует вообще никак — это давняя, задокументированная особенность Next.js, а не баг конфигурации. Решение — пускать эти конкретные пути (`/operator/events/`, `/user-events/`) **в обход фронтенда**, отдельными `location` в nginx прямо на API-контейнер, до того как запрос долетит до Next.js. Пример — в `nginx.http-fallback.conf`, server-блок `listen 8080` (там, где фронтенд отдаётся на одном порту с API через `/backend/*`): `location /backend/operator/events/` и `location /backend/user-events/` там прописаны отдельно, со снятием префикса `/backend/` через `rewrite ... break;`, и обычные (не-realtime) `/backend/*`-запросы продолжают идти через фронтендовый rewrite как раньше — трогать `next.config.js` не нужно.
>
> **Этот обход работает только когда фронтенд обслуживается через nginx** (в наших конфигах — блок `listen 8080`; блоки `listen 80`/`listen 443` проксируют `location /` прямо на `api:8000` и фронтенд не отдают вовсе, поэтому `/backend/*` там просто не при чём). Если разработчик открывает панель на `localhost:3000` — то есть напрямую на dev-сервере Next.js — **nginx в цепочке не участвует**, и никакая правка его конфига не поможет: `rewrites()` забуферит SSE у себя. Признак в DevTools: `Remote Address` указывает на `:3000`, а не на порт nginx. Варианты для локальной разработки: открывать панель через nginx (порт из `docker-compose`, а не `3000`) либо в dev-сборке подключать `EventSource` напрямую к origin API (тогда API-порт должен быть проброшен на хост, а origin дев-сервера — добавлен в `CORS_ORIGINS`).

### Авторизация: короткоживущий тикет

`EventSource` не умеет слать заголовок `Authorization`, а класть в URL сам JWT означало бы, что access-токен светится в логах nginx. Поэтому сначала обычным REST-запросом с Bearer-токеном получаем короткоживущий тикет, а он уже подставляется в query-параметр SSE-запроса.

### POST `/operator/events/ticket`
**Доступ:** `operator`, `admin`.

Ответ:
```json
{ "ticket": "kQ2f...", "expires_in": 300 }
```
Тикет живёт 5 минут и **валиден многократно** в пределах этого времени — не удаляется после первого использования. Это важно: браузерный `EventSource` при любом обрыве соединения (смена сети, сон вкладки, короткий сбой) сам переподключается **тем же URL**, с тем же тикетом. Если бы тикет становился недействителен после первого коннекта, любое автопереподключение браузера получало бы `401`, и клиент навсегда терял бы live-обновления до полной перезагрузки компонента чата. Просрочен → следующий SSE-запрос ответит `401`.

> **Тикет привязан к своему каналу.** Тикет из `POST /operator/events/ticket` работает
> только на `/operator/events/*`, тикет из `POST /user-events/ticket` — только на
> `/user-events/*`. Переиспользовать один тикет на оба вида стримов нельзя: чужой
> канал ответит `401`. Раньше хранилище тикетов было общим, и тикет обычного
> пользователя открывал операторские каналы с чужими чатами.

### GET `/operator/events/chats?ticket=...`
Глобальный канал — замена поллинга списка чатов (`chats-page.tsx`). Событие `chat.created`/`chat.updated` приходит при новом сообщении (в т.ч. от бота), новом чате, смене `bot_active`/`operator_requested`/`problem_status`.

### GET `/operator/events/chats/{chat_id}?ticket=...`
Канал открытого чата — замена поллинга сообщений (`chat-conversation.tsx`). События: `message.created`, `message.updated`, `message.deleted`, `message.reaction_changed`, `message.pinned`, `message.unpinned`, `message.read`.

Доступ к конкретному чату проверяется при каждом подключении (не только валидность тикета): роль перечитывается из БД, а личные заметки пользователя (`notes`) закрыты и от операторов. Нет доступа → `403`.

`message.read` — новое: раньше `POST /chats/{chat_id}/read` (и `/operator/chats/{chat_id}/read`) ничего не публиковали в SSE вообще, поэтому собеседник узнавал о прочтении только после ручного обновления страницы. Теперь при реальном изменении статуса (хотя бы одно сообщение действительно помечено прочитанным) публикуется:
```json
{ "type": "message.read", "chat_id": 11, "data": { "message_ids": [41, 42], "reader_id": 8 } }
```
Если помечать нечего (все сообщения уже были прочитаны) — событие не публикуется.

Формат конверта (`text/event-stream`):
```
event: message.created
data: {"type":"message.created","chat_id":11,"data":{...MessageOut...}}

```
Сразу после подключения приходит `{"type":"connected"}`, а затем каждые 20с — комментарий-пинг (`: ping`) для поддержания соединения, если реальных событий нет.

**Важно про payload `chat.updated`/`chat.created`:** `data` — best-effort снимок (`id`, `chat_type`, `cabinet_id`, `user_id`, `last_message_text`, `problem_status`, `bot_active`, `operator_requested`), **без** `unread_count` — он зависит от конкретного оператора-получателя и здесь не считается. Событие стоит трактовать как сигнал инвалидировать React Query кэш и перезапросить актуальные данные, а не как источник истины для всех полей.

**Ограничения, о которых стоит знать:**
- Доставка *at-most-once* и без буферизации на сервере: если соединение оборвалось (сон вкладки, сеть), пропущенные события не повторяются. При (пере)подключении стоит один раз перезапросить актуальные данные через обычный REST, а не полагаться только на поток.
- `DELETE /operator/chats/{chat_id}` (удаление чата целиком) событие не публикует — крайне редкое действие, обычно инициируется тем же оператором, который смотрит на список.
- Работает в рамках одного процесса api (см. `Dockerfile` — uvicorn без `--workers`). Если когда-нибудь потребуется несколько инстансов api, канал нужно будет перевести на Redis pub/sub.

Пример на фронте:
```js
const { ticket } = await fetch('/operator/events/ticket', {
  method: 'POST', headers: { Authorization: `Bearer ${token}` },
}).then(r => r.json());

const es = new EventSource(`/operator/events/chats?ticket=${ticket}`);
es.onmessage = (e) => {
  const event = JSON.parse(e.data);
  if (event.type === 'chat.updated' || event.type === 'chat.created') {
    queryClient.invalidateQueries(['operator-chats']);
  }
};
// ticket живёт 30с — если EventSource переподключается (реконнект браузера
// после разрыва), нужен свежий тикет через тот же POST /operator/events/ticket
```

## Realtime (WebSocket) для мобильного/пользовательского приложения

Тот же смысл, что и SSE у оператора (замена поллинга `GET /chats` и `GET /chats/{id}/messages`), но другой транспорт: `EventSource` нативно не поддерживается на мобильных платформах, а `WebSocket` — поддерживается везде, поэтому для обычных пользователей сделан отдельный WS-канал вместо SSE.

Формат событий (`message.created`, `message.updated`, `message.deleted`, `message.reaction_changed`, `message.pinned`, `message.unpinned`, `message.read`, `chat.created`, `chat.updated`) — **тот же самый JSON**, что и в SSE у оператора, просто доставляется через `websocket.send_text()` вместо `event:`/`data:`-конверта. Мутации (отправка сообщения, реакции, pin, mark-as-read) — по-прежнему обычные REST-вызовы, WS только уведомляет.

> Если фронтенд ходит на бэкенд через Next.js `rewrites()` — см. предупреждение в начале раздела «Realtime (SSE)» выше: WebSocket-upgrade через `rewrites()` не проксируется вообще, этот путь обязателен в обход фронтенда на уровне nginx.

### Авторизация: тот же короткоживущий тикет

Как и `EventSource`, браузерный/нативный `WebSocket` не умеет слать заголовок `Authorization` при установке соединения. Схема идентична операторской: сначала обычный REST-запрос с Bearer-токеном за тикетом, потом тикет — в query-параметре WS URL.

### POST `/user-events/ticket`
Доступен любому авторизованному пользователю.

Ответ:
```json
{ "ticket": "kQ2f...", "expires_in": 300 }
```
Тикет живёт 5 минут, валиден многократно в пределах этого времени (та же логика, что у операторского тикета — переподключение тем же URL не должно ловить 401).

---

### WS `/user-events/chats?ticket=...`
Персональный канал пользователя — приходят обновления **только по его собственным чатам** (`chat.created`/`chat.updated`), замена поллинга списка чатов. В отличие от оператора, который видит все чаты сразу через общий канал, здесь канал именно персональный — привязан к `user_id` из тикета.

### WS `/user-events/chats/{chat_id}?ticket=...`
Канал конкретного открытого чата — те же события, что и в операторской версии. Проверяется, что у пользователя реально есть доступ к этому чату (та же проверка, что и на `POST /chats/{chat_id}/messages`) — иначе соединение закрывается сразу после подключения с кодом `4403` (нет доступа) или `4401` (невалидный/просроченный тикет).

Сразу после подключения приходит `{"type": "connected"}`, затем каждые 20с — `{"type": "ping"}`, если реальных событий нет (аналог SSE-комментария-пинга, только тут это обычное сообщение, поскольку у WS нет комментариев).

Пример на клиенте:
```js
const { ticket } = await fetch('/user-events/ticket', {
  method: 'POST', headers: { Authorization: `Bearer ${token}` },
}).then(r => r.json());

const ws = new WebSocket(`wss://helper.savt.by/user-events/chats/${chatId}?ticket=${ticket}`);
ws.onmessage = (e) => {
  const event = JSON.parse(e.data);
  if (event.type === 'message.created') { /* … */ }
};
```

**Ограничения — те же, что и у SSE-версии:** доставка *at-most-once* без буферизации (пропущенные во время разрыва события не повторяются, при реконнекте стоит один раз перезапросить актуальные данные через REST), и работа в рамках одного процесса api (in-memory `event_bus`, без Redis pub/sub — если появится больше одного воркера/инстанса, каналы перестанут видеть события друг друга).

## Рут `service requests` — сервисные заявки

Типы заявок (`request_type`): `repair` (ремонт), `diagnostics` (диагностика), `remote_adjustment` (наладка удалённо), `onsite_adjustment` (наладка с выездом), `other` (другое).
Статусы: `open`, `in_progress`, `postponed`, `closed`. Переход между статусами не валидируется — администратор/оператор может установить любой статус через `PATCH /admin/service-requests/{req_id}/status` (типичный сценарий: `open → in_progress → closed`).

### POST `/service-requests`
Создать заявку. Пользователь должен быть привязан к указанному ШУ.
```json
{
  "cabinet_id": 5,
  "request_type": "repair",
  "description": "Не работает кнопка управления, при нажатии нет реакции"
}
```
`description` — минимум 10 символов.

**`client_token`** (необязательное поле, до 64 символов) — тот же принцип
идемпотентности оффлайн-очереди, что и у `POST /chats/{chat_id}/messages`:
повторная отправка с тем же токеном возвращает уже созданную заявку вместо
дубля.

При создании заявки автоматически создаётся её чат (`chat_type: "service_request"`) — виден и заявителю, и операторам/админам (`GET /chats`, `GET /operator/chats`). `chat_id` из ответа — сразу открыть чат заявки, не нужно искать его в общем списке.

После создания заявка асинхронно (в фоне, не блокируя ответ) синхронизируется с Bitrix24 — создаётся задача (`tasks.task.add`) с исполнителем (`RESPONSIBLE_ID` = `BITRIX_DEFAULT_RESPONSIBLE_ID`) и постановщиком (`CREATED_BY` = `BITRIX_DEFAULT_CREATOR_ID`, если настроен — иначе постановщиком становится технический пользователь вебхука). ID созданной задачи попадает в поле `bitrix_task_id` (появится не сразу, а чуть позже создания заявки — обнови список, чтобы увидеть). Если Bitrix не настроен или недоступен — заявка всё равно создаётся, просто `bitrix_task_id` остаётся `null`.

Заголовок задачи в Bitrix собирается из номера объекта, организации (или ФИО, если пользователь — физлицо) заявителя, назначения ШУ, рабочего кода ШУ в скобках и типа заявки — например:
```
26_001 Могилевский водоканал ПНС Вейно (П-228) ремонт
```
Части, для которых поле в ШУ не заполнено (`purpose`/`admin_internal_name`), просто пропускаются.

**Синхронизация переписки в Bitrix.** Каждое сообщение **заявителя** (не оператора и не бота) в чате заявки асинхронно дублируется комментарием в ленту Bitrix-задачи (`task.commentitem.add`) в формате:
```
Иванов Иван написал: "Не работает кнопка"
```
Вложения без текста — прямой ссылкой на файл (`/static/...`, как есть в `file_url`); если в сообщении и текст, и вложения — ссылки идут отдельными строками после текста. Синхронизация одностороннего направления (как и статус) — комментарии, оставленные прямо в Bitrix, к нам не подтягиваются. Если у заявки ещё нет `bitrix_task_id` (Bitrix не настроен/недоступен на момент создания) — сообщение просто не синхронизируется, без ошибки для отправителя.

## Рут `notifications` — уведомления

### GET `/notifications`
**История уведомлений** текущего пользователя — смены статусов заявок, гарантия, реклама. Параметры:
- `is_read=true|false`
- `type` — повторяемый: `?type=request_status&type=warranty_expiring`. Без него отдаются все типы
- `page`, `size`

История ведётся независимо от пуша: запись создаётся, даже если пуш не ушёл (выключен переключатель по типу — нет, см. ниже; но при **паузе** — да, запись будет). Сообщений в чатах здесь **нет**: они push-only, у чатов свои счётчики непрочитанного.

```json
{
  "items": [
    {
      "id": 1,
      "type": "request_status",
      "title": "Заявка одобрена",
      "body": "Ваш ШУ был успешно добавлен",
      "data": { "cabinet_id": 5 },
      "is_read": false,
      "created_at": "2026-05-15T10:00:00Z"
    }
  ],
  "total": 3, "page": 1, "size": 20, "pages": 1
}
```

Типы уведомлений (`type`), фактически отправляемые на данный момент:
- `warranty_expiring` — гарантия истекает через 30/10/1 день
- `promotional` — реклама: произвольное сообщение администратора (`broadcast`) либо заготовка из подборки (`promo/send`, в `data` будет `promo_id`)
- `chat_message` — новое сообщение от оператора или бота в чате
- `operator_requested` — пользователь запросил оператора (отправляется всем активным операторам и администраторам)
- `request_status` — решение по заявке. Отправляется заявителю при:
  - смене статуса сервисной заявки (в т.ч. когда статус приехал из Bitrix) — только при реальном изменении, плановый опрос Bitrix каждые 15 минут повторных уведомлений не шлёт;
  - одобрении/отклонении заявки на добавление ШУ и на доступ к чужому ШУ;
  - одобрении/отклонении заявки на доступ к проекту;
  - одобрении/отклонении заявки на документ;
  - смене телефона входа (см. раздел про смену номера).

### POST `/notifications/mute`
**Пауза** — заглушить все уведомления на время.
```json
{ "hours": 2 }
```
`hours` — одно из `1`, `2`, `3`, `6`, `12`, `24`, либо `null` = бессрочно. Список закрытый: это кнопки в интерфейсе, а не свободный ввод. Ответ — те же `NotificationSettingsOut`.

Срок считается от момента вызова и **не продлевается**: нажали «на час», когда до конца прошлой паузы оставалось десять минут, — значит час, а не час десять.

Что именно глушится:
- **все пуши**, независимо от переключателей по типам — включая сообщения в чатах, ответы бота и служебный сигнал операторам. Проверка стоит в `send_push`, то есть покрывает и то, что идёт мимо `NotificationService`;
- **история продолжает копиться**. Пользователь просил не беспокоить, а не выбрасывать уведомления: вернувшись, он увидит в `GET /notifications` всё, что пришло за время тишины.

### POST `/admin/notifications/promo/send`
Разослать рекламу из подборки. Только для администратора. Параметры:
- `promo_id` — конкретная заготовка. Без него берётся **случайная**
- `role` — как в `broadcast`: `null` = всем активным, либо `user` / `operator` / `admin`

```json
{ "sent_to": 42, "skipped_opted_out": 7,
  "message": { "id": "remote_diagnostics", "title": "Удалённая диагностика", "body": "…", "data": {} } }
```
Уважает переключатель `promotional`, как и обычная рассылка. В `data` уведомления кладётся `promo_id` — по нему в приложении можно понять, какую именно заготовку показали. Действие пишется в журнал.

`400` — подборка пуста или файл не читается. `404` — заготовки с таким `promo_id` нет.

#### Файл с рекламой

Подборка лежит в `savt-backend/app/data/promo_messages.json` и правится руками:
```json
{
  "messages": [
    { "id": "service_reminder",
      "title": "Плановое обслуживание",
      "body": "Регулярное ТО шкафа управления продлевает срок службы…",
      "data": { "screen": "service_request" } }
  ]
}
```
- `id` — уникальный, попадает в `data.promo_id`;
- `title` до 255 символов, `body` до 1000 — длиннее обрезается;
- `data` — произвольные ключи для клиента (например, экран для перехода), значения приводятся к строкам;
- записи без `title` или `body` пропускаются с `WARNING` в логе, остальные всё равно разошлются.

Файл внутри образа только для чтения. Чтобы править без пересборки, положите свою копию рядом и укажите путь в `PROMO_MESSAGES_FILE` — например на уже примонтированной шаре NAS (`/mnt/projects/promo_messages.json`) или отдельным томом. Отсутствующий и битый файл рассылку не роняют: она просто не находит, что отправить, и говорит об этом `400`-м.

**Автоматическая рассылка** по умолчанию выключена. Включается `PROMO_AUTO_SEND_HOUR` — час (0–23), в который раз в сутки уходит случайная заготовка всем пользователям с ролью `user`. Пусто, не число или значение вне диапазона — рассылка не регистрируется вовсе, остаётся только кнопка. Так по умолчанию сделано намеренно: реклама уходит живым людям, и включать её стоит осознанно.

## RAG-бот Ася

Виртуальный ассистент, встроенный в чаты. Отвечает на вопросы пользователей по ШУ, используя базу знаний, FAQ и документацию ШУ.

### Принцип работы

```
Пользователь пишет сообщение
        ↓
Текст запроса → Yandex Embeddings (text-search-query) → вектор запроса
        ↓
pgvector cosine search → до 5 ближайших чанков из embeddings
  (если cabinet-чат → до 4 чанков ищутся среди документов конкретного ШУ,
   остальные — по всей базе embeddings; для больших документов (десятки
   чанков) лимит стоит поднимать дальше, если бот всё ещё не находит ответ,
   который точно есть в тексте)
        ↓
История диалога (до 5 предыдущих сообщений) + текущий вопрос с найденными чанками → YandexGPT-lite
        ↓
Ответ бота + цитата из источника → сохраняется в messages (sender = "Ася")
```

Ответ генерируется в фоне (`asyncio.create_task`) — пользователь не ждёт, основной запрос возвращается мгновенно.

### Источники данных

| Тип | Метка в ответе | Индексируется |
|---|---|---|
| Записи FAQ | `[FAQ]` | При создании/изменении |
| Статьи базы знаний | `[База знаний]` | При создании/изменении/добавлении вложений |
| Документы ШУ | `[Документация ШУ]` | При загрузке |

### Поддерживаемые форматы вложений/документов

Перед индексацией любой файл нормализуется в обычный текст — дальше он чанкуется и эмбеддится одинаково, независимо от исходного формата.

| Формат | Извлечение текста |
|---|---|
| PDF с текстовым слоем | pypdf, постранично |
| PDF-скан (без текстового слоя) | автоматический fallback: встроенные изображения страницы (через pypdf, без poppler) распознаются через **Yandex Vision OCR** |
| `.docx` | python-docx — параграфы и таблицы |
| `.xlsx` | openpyxl — все листы, ячейки построчно |
| Изображения (`.jpg`, `.jpeg`, `.png`, `.webp`) | Yandex Vision OCR напрямую |
| `.doc` (Word 97-2003) | **не поддерживается** — пересохранить как `.docx` |
| `.xls` (Excel 97-2003) | **не поддерживается** — пересохранить как `.xlsx` |

OCR — тот же аккаунт/ключ Yandex Cloud, что и для YandexGPT/SpeechKit (`YANDEX_API_KEY`, `YANDEX_FOLDER_ID`), новых переменных окружения не требует. Для скана распознаётся только то, что реально не текстовое — если в PDF часть страниц с текстовым слоем, а часть — сканы, OCR прогоняется только по вторым (экономит вызовы API).

Если после индексации текст пустой — смотрите логи (`docker compose logs api | grep -i "разобрать\|извлеч.*пуст\|OCR"`): там указана точная причина (не найден файл, не удалось открыть, пустой текстовый слой, не поддерживаемый формат).

### Формат ответа бота

Бот даёт краткий ответ и добавляет цитату из найденного источника:
```
Гарантия на оборудование SAVT составляет 24 месяца с даты ввода в эксплуатацию.

> "Гарантийный срок устанавливается равным 24 месяцам со дня подписания акта ввода в эксплуатацию."
```

### Счётчик попыток и передача оператору

- Если пользователь 3 раза подряд выражает недовольство (`bot_max_attempts`) — бот предлагает оператора.
- Пользователь отвечает «да» → `operator_requested=true`, `bot_active=false`. Все активные операторы и администраторы получают push-уведомление `operator_requested` с номером чата.
- Пользователь отвечает «нет» → счётчик сбрасывается, бот продолжает.
- Оператор забирает чат: `POST /operator/chats/{chat_id}/take` → бот замолкает.
- Оператор возвращает чат боту: `POST /operator/chats/{chat_id}/return-to-bot`.

### Определение решённой проблемы

Если пользователь пишет «спасибо», «помогло», «разобрался» и т.п. — бот фиксирует `problem_status=resolved`, отправляет прощальное сообщение и прекращает follow-up цикл.

### Follow-up

Если пользователь написал и не получил решения (не отвечал дольше `BOT_FOLLOW_UP_MINUTES` минут) — бот сам пишет: «Удалось ли решить вашу проблему?». Follow-up отправляется только один раз — сбрасывается лишь когда пользователь снова выражает недовольство.

### Настройка (.env)

```env
YANDEX_FOLDER_ID=ваш_folder_id          # Folder ID из Yandex Cloud
YANDEX_API_KEY=ваш_api_key              # API-ключ сервисного аккаунта
YANDEX_GPT_MODEL=yandexgpt-lite         # Модель (yandexgpt-lite / yandexgpt)
BOT_FOLLOW_UP_MINUTES=60                # Через сколько минут бот пишет follow-up
BOT_MAX_ATTEMPTS=3                      # Сколько попыток до предложения оператора
```

> **Важно:** `YANDEX_FOLDER_ID` должен совпадать с folder сервисного аккаунта, к которому выдан `YANDEX_API_KEY`. Если это разные папки — Yandex вернёт 400.

### Первый запуск

После деплоя запустить полную индексацию (один раз):
```
POST /admin/bot/reindex?force=true
Authorization: Bearer {admin_token}
```
Ответ приходит сразу, не дожидаясь окончания (считает в фоне — иначе на большом объёме упрётесь в `504` от nginx):
```json
{ "status": "started", "message": "Индексация запущена в фоне, результат смотрите в логах" }
```
Итог смотреть в логах: `docker compose logs api --tail=50 | grep -i переиндекс`.

В дальнейшем `POST /admin/bot/reindex` (без `force`) индексирует только новые записи — уже проиндексированные пропускаются (`skipped`). Также индексация происходит автоматически при создании/изменении FAQ, KB и документов.

Если что-то было удалено в обход обычных эндпоинтов (см. `POST /admin/bot/prune` в разделе «Рут `admin: bot`» ниже) — эта ручка подчищает embeddings, оставшиеся от удалённых записей.

### Управление через БД (если нужно сбросить состояние)

```sql
-- Включить бота для всех чатов
UPDATE chats SET bot_active = true WHERE chat_type != 'notes';

-- Сбросить счётчик неудачных попыток
UPDATE chats SET bot_no_count = 0, follow_up_sent = false;

-- Посмотреть сколько чанков проиндексировано
SELECT source_type, COUNT(*) FROM embeddings GROUP BY source_type;
```

## Рут `admin: bot` — управление ботом

### POST `/admin/bot/reindex`
Индексация источников (FAQ, база знаний, документы ШУ). Только для администратора.

Параметры:
- `force=false` (по умолчанию) — индексирует только записи без существующих эмбеддингов (быстро)
- `force=true` — полная переиндексация всего (медленно, пропорционально объёму данных)

Считает в фоне — сам HTTP-запрос отвечает сразу (`202 Accepted`), не дожидаясь окончания. При заметном объёме данных `force=true` — это десятки/сотни синхронных вызовов Yandex API (эмбеддинги), что легко превышает `proxy_read_timeout` nginx, если считать синхронно внутри запроса.

Ответ:
```json
{ "status": "started", "message": "Индексация запущена в фоне, результат смотрите в логах" }
```
Итоговую статистику (`{"faq": 2, "kb_article": 0, "document": 5, "skipped": 28}`) смотреть в логах api (`docker compose logs api --tail=50 | grep -i переиндекс`) — там же видна ошибка, если фон упал.

На практике при штатной работе `skipped` почти всегда будет равен количеству всех существующих записей, а добавленных — `0`: создание и изменение записей уже индексируется автоматически в фоне (см. ниже), эта ручка нужна в основном для данных, попавших в БД в обход обычных create/update-эндпоинтов (восстановление из бэкапа, ручные правки), либо если фоновая автоиндексация когда-то не отработала.

### POST `/admin/bot/prune`
Удаляет embeddings, чей источник (FAQ/статья КБ/документ) больше не существует. Только для администратора.

Основной сценарий, когда это нужно: удаление категории каскадно сносит её статьи/вопросы на уровне БД (`ondelete=CASCADE`) — это происходит в обход сервисного `delete()`, который обычно чистит embeddings сам. С 2026-07-14 сам каскад категорий уже чистит embeddings дочерних записей заранее, так что `prune` — это подстраховка на нештатные случаи (восстановление из бэкапа, ручные правки в БД), а не единственная защита.

Ответ:
```json
{ "status": "ok", "removed": { "faq": 0, "kb_article": 3, "document": 0 } }
```

## Фоновые задачи (APScheduler)

Планировщик запускается автоматически при старте приложения.

### Уведомления об истечении гарантии

**Расписание:** каждый день в 09:00.

**Логика:**
- Находит все ШУ, у которых `warranty_ends_at` наступает ровно через 30, 10 или 1 день.
- Для каждого ШУ отправляет уведомление всем привязанным пользователям.
- Уважает настройки уведомлений пользователя — если `warranty_expiring: false`, push не приходит.
- Каждое уведомление (cabinet_id + порог в днях) отправляется **ровно один раз** — повторная отправка защищена таблицей `warranty_notif_log`.

**Пример push-уведомления:**
```
Заголовок: Гарантия истекает
Текст:     Гарантия ШУ «ШУ-18К» истекает через 30 дней
Data:      { "cabinet_id": 5, "days_left": 30 }
```

Тип уведомления в БД: `warranty_expiring`.

## Бэкапы базы данных

Скрипт `backup.sh` делает дамп PostgreSQL из Docker-контейнера, сжимает и хранит последние 5 файлов.

Гарантии скрипта:
- Дамп пишется во временный файл `.part` и переименовывается только при успехе — упавший `pg_dump` не оставит битый бэкап, который вытеснил бы хорошие при ротации.
- Пустой дамп считается ошибкой.
- Ротация: хранятся `BACKUP_KEEP_COUNT` (по умолчанию 5) последних файлов.
- Опционально копия выгружается в Yandex Object Storage (`BACKUP_S3_UPLOAD=1`) — переживёт смерть диска сервера. Использует ключи `YANDEX_STORAGE_*` из контейнера api, кладёт в `db-backups/` бакета.

Переменные окружения скрипта: `POSTGRES_DB` (умолч. `savt`), `POSTGRES_USER` (умолч. `postgres`), `BACKUP_KEEP_COUNT` (умолч. `5`), `BACKUP_S3_UPLOAD` (умолч. `0`), `BACKUP_DB_CONTAINER` / `BACKUP_API_CONTAINER` (умолч. `savt-backend-db-1` / `savt-backend-api-1`). Пароль БД не нужен — `pg_dump` внутри контейнера ходит через локальный сокет.

### Первый запуск (на сервере)

```bash
# Сделать скрипт исполняемым
chmod +x savt-backend/backup.sh

# Проверить вручную
cd savt-backend
./backup.sh
```

Бэкапы сохраняются в `savt-backend/backups/` с именем `savt_backup_YYYY-MM-DD_HH-MM-SS.sql.gz`.

### Автоматический запуск через cron

```bash
crontab -e
```

Добавить строку (запуск каждый день в 03:00, с выгрузкой в Object Storage):

```
0 3 * * * cd /path/to/savt-backend && BACKUP_S3_UPLOAD=1 ./backup.sh >> /var/log/savt-backup.log 2>&1
```

> Замените `/path/to/savt-backend` на реальный путь к директории на сервере.
> Если бакет Object Storage не настроен — уберите `BACKUP_S3_UPLOAD=1`.

### Проверить, что бэкапы реально делаются

```bash
crontab -l | grep backup            # строка на месте?
tail -n 20 /var/log/savt-backup.log # последние запуски без ошибок?
ls -lh savt-backend/backups/        # 5 файлов со свежими датами?
```

### Восстановление из бэкапа

```bash
# Распаковать и восстановить
gunzip -c backups/savt_backup_2026-05-18_03-00-00.sql.gz \
    | docker exec -i savt-backend-db-1 psql -U postgres -d savt
```

### Follow-up бота

**Расписание:** каждые 10 минут.

**Логика:**
- Находит все чаты где `bot_active=true`, `follow_up_sent=false`, и последнее сообщение пользователя старше `BOT_FOLLOW_UP_MINUTES` минут (по умолчанию 60).
- Отправляет от имени Аси: «Здравствуйте! Удалось ли решить вашу проблему? Если нет — я готов помочь.»
- Ставит `follow_up_sent=true` — повторно не пишет до нового сообщения от пользователя.

## Управление через CLI

```bash
# Создать суперадмина (только через CLI — намеренно нет API)
docker exec savt-backend-api-1 python -m app.cli create-superadmin <login> <password> [full_name]

# Создать администратора через CLI (альтернатива API POST /admin/users/admins, доступна суперадмину)
docker exec savt-backend-api-1 python -m app.cli create-admin <login> <password> [full_name]

# Создать оператора через CLI (альтернатива API POST /admin/users/operators)
docker exec savt-backend-api-1 python -m app.cli create-operator <login> <password> [full_name]
```

| Кто создаёт | Через CLI | Через API |
|---|---|---|
| Суперадмин | ✅ | ❌ только CLI |
| Администратор | ✅ | ✅ `POST /admin/users/admins` (суперадмин) |
| Оператор | ✅ | ✅ `POST /admin/users/operators` (администратор) |
