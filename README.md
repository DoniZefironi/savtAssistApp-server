# savtAssistApp-server

SAVT Assist — сервис сопровождения клиентов: мобильное приложение конечного
пользователя и админ-панель для операторов/администраторов поверх общего
FastAPI-бэкенда (PostgreSQL, Docker). Ядро — шкафы управления (ШУ) и проекты
(группы ШУ с общим доступом), вокруг них: чат с ботом/оператором, сервисные
заявки, рекламации, база знаний/FAQ, документы и телеметрия по MQTT.
Значительная часть данных (проекты, компании, задачи по рекламациям)
синхронизируется с Bitrix24 в обе стороны.

**Роли (иерархия от низшей к высшей):**
1. **Пользователь** (`user`) — добавляет ШУ, пользуется чатом поддержки, просматривает/запрашивает документацию, создаёт сервисные заявки.
2. **Оператор** (`operator`) — отвечает в чате, просматривает все данные. Создаётся через `POST /admin/users/operators` или CLI.
3. **Администратор** (`admin`) — полное управление данными, создаёт операторов. Создаётся суперадмином через API или CLI.
4. **Суперадмин** (`superadmin`) — управляет администраторами, имеет все права. Создаётся **только через CLI**.
5. **Бот** (`bot`) — системная роль для Аси, не отображается в списках пользователей.

> Иерархия: каждая роль выше автоматически имеет все права более низкой роли.

Дальше по файлу: сначала эксплуатация (переменные окружения, Docker, деплой,
вебхуки), затем сквозные конвенции API (формат ошибок, токены, PATCH,
подписанные ссылки), а основной объём — по разделам («Рут `X`»): что каждый
эндпоинт принимает и что отдаёт.

## Работа с Docker

Конфигурация разделена на прод и dev:

- `docker-compose.yml` — **продакшн**: без hot-reload, код внутри образа, nginx с HTTPS (`nginx.conf`).
- `docker-compose.dev.yml` — **локальная разработка**: `--reload`, монтирование кода, nginx без TLS (`nginx.dev.conf`).

```bash
# ЛОКАЛЬНАЯ РАЗРАБОТКА — сборка и запуск
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d --build

# ПРОД (на сервере) — сборка и запуск
# build и up НАРОЧНО отдельными командами (не "up -d --build" одной строкой):
# так старый контейнер api продолжает отвечать, пока собирается новый образ, и
# замена происходит только когда новый образ уже готов — сама замена занимает
# 1-2 секунды. Если билд и замену объединить в одну команду и сборка вдруг
# зависнет/упадёт с первой попытки, старый контейнер к этому моменту уже может
# быть остановлен — тогда простой растягивается на всё время повторной сборки.
docker compose build && docker compose up -d

# ОБЯЗАТЕЛЬНО следом, если пересоздался api: nginx резолвит имя "api" в IP
# один раз при старте своих воркеров и кэширует — новый api-контейнер получает
# новый IP в docker-сети, а nginx продолжает стучаться в старый (мёртвый) адрес
# и отдаёт 503 с "Сервис временно недоступен", даже когда api уже давно жив и
# здоров. `nginx -s reload` перезапускает воркеры без даунтайма и заставляет их
# перерезолвить api заново.
docker exec savt-backend-nginx-1 nginx -s reload

# Миграции
docker exec savt-backend-api-1 alembic upgrade head

# Создание новой миграции (после изменения моделей)
docker exec savt-backend-api-1 alembic revision --autogenerate -m "описание"

# Логи
docker compose logs api --tail=20

# Подключение к БД
docker exec -it savt-backend-db-1 psql -U postgres -d savt
# \dt — все таблицы
# \d <таблица> — структура таблицы
# \q — выход
```

> После изменения кода на проде нужен пересбор: `docker compose build && docker compose up -d` (код копируется в образ, а не монтируется). См. выше, почему не одной командой `up -d --build`.

### `telemetry-proxy` — отдельный .NET-сервис в этом же docker-compose

Слушает MQTT-брокеры контроллеров ШУ (аварии/сообщения, карта регистров —
см. «Рут `admin: telemetry`») и пересылает сообщения на `api` обычным HTTP
(`POST /webhooks/telemetry`) по внутренней docker-сети, без выхода наружу.
Исходники — `savt-backend/telemetry-proxy/` (Worker Service, .NET, `MQTTnet`),
свой `Dockerfile`, поднимается тем же `docker compose up -d --build`, что и всё
остальное — отдельно разворачивать не нужно.

**У каждого ШУ — свой брокер** (свой IP/порт, не общий на все объекты), поэтому
прокси не хранит адрес брокера у себя в конфиге вообще. Вместо этого он раз в
`Webhook:TargetsPollIntervalSeconds` (по умолч. 60с) дёргает
`GET /webhooks/telemetry/targets` и держит по отдельному MQTT-подключению на
каждый полностью настроенный ШУ (заполнены `mqtt_host`+`mqtt_port`+`mqtt_topic`,
см. `PATCH /admin/cabinets/{id}`). Появился новый ШУ с указанным брокером —
прокси сам подключится на следующем опросе, без правки своего конфига и без
передеплоя. Пропал/изменился — старое подключение закрывается.

```bash
# Логи прокси
docker compose logs telemetry-proxy --tail=50

# Пересобрать после правок в telemetry-proxy/
docker compose build telemetry-proxy && docker compose up -d telemetry-proxy
```

## Развёртывание и HTTPS (прод)

Прод-nginx (`nginx.conf`) принимает только HTTPS: порт 80 отдаёт ACME-челленджи и редиректит на 443. Без сертификата контейнер nginx **не стартует** — поэтому порядок первого развёртывания такой:

Какой конфиг nginx использовать, задаётся переменной `NGINX_CONF` в `.env` (по умолчанию `nginx.conf`):

| Конфиг | Когда использовать |
|---|---|
| `nginx.conf` (умолч.) | Прод: 443 с TLS, порт 80 — только редирект и ACME |
| `nginx.http-fallback.conf` | Переходный: порт 443 снаружи ещё не проброшен — API работает и по 80, и по 443 |
| `nginx.dev.conf` | Локальная разработка (подключается автоматически через `docker-compose.dev.yml`) |

Переходный режим (пока сеть/роутер не пробрасывает 443):

```bash
echo "NGINX_CONF=nginx.http-fallback.conf" >> .env
docker compose up -d nginx
```

После проброса 443 вернуть строгий режим: удалить строку `NGINX_CONF` из `.env` и снова `docker compose up -d nginx`.

### 1. Подготовка

```bash
# В .env выставить боевые секреты:
#   JWT_SECRET_KEY  — минимум 64 случайных символа
#   POSTGRES_PASSWORD — длинный случайный пароль
#   STATIC_LINK_SECRET — секрет подписи ссылок на файлы (обязателен!)
openssl rand -hex 48   # генератор секретов
```

> **`STATIC_LINK_SECRET` обязателен.** nginx проверяет подпись ссылок на `/static/`
> (`secure_link`), и при пустом секрете **все файлы будут отдавать `403`** — фото,
> вложения чата, документы. Значение подставляется в оба сервиса из одного места в
> `.env` (см. `environment:` у `nginx` в `docker-compose.yml`), так что разъехаться
> они не могут. Подробности — в разделе «Подписанные ссылки на файлы».
>
> Конфиг nginx монтируется **как шаблон** (`/etc/nginx/templates/nginx.conf.template`),
> из которого штатный энтрипойнт образа собирает итоговый `/etc/nginx/nginx.conf` с
> подставленным секретом. Поэтому после обновления нужен пересоздающий `docker compose up -d`,
> а не только `nginx -s reload`. Проверить, что секрет подставился:
> ```bash
> docker exec savt-backend-nginx-1 grep secure_link_md5 /etc/nginx/nginx.conf
> ```

> Если меняете `POSTGRES_PASSWORD` на уже работающей БД, одного .env мало — пароль хранится в самой БД:
> ```bash
> docker exec -it savt-backend-db-1 psql -U postgres -c "ALTER USER postgres PASSWORD 'новый_пароль';"
> # затем обновить POSTGRES_PASSWORD и DATABASE_URL в .env и перезапустить api
> ```

### 2. Получить сертификат (первый раз — standalone, порт 80 должен быть свободен)

```bash
sudo apt install certbot            # если ещё не установлен
docker compose stop nginx           # освободить порт 80
sudo certbot certonly --standalone -d helper.savt.by
mkdir -p certbot-www                # webroot для последующих продлений
docker compose up -d                # nginx стартует уже с сертификатом
```

### 3. Автопродление сертификата

`crontab -e`, добавить:

```
0 4 * * 1 certbot renew --webroot -w /path/to/savt-backend/certbot-www --deploy-hook "docker exec savt-backend-nginx-1 nginx -s reload" >> /var/log/certbot-renew.log 2>&1
```

### 4. Проверка

```bash
curl -I http://helper.savt.by/health    # → 301 на https (в переходном режиме — 200)
curl https://helper.savt.by/health      # → {"app":"ok","db":true}
```

## Вебхуки внешних интеграций

Эти эндпоинты не вызываются фронтендом — их дёргают внешние сервисы (Bitrix24, Telegram). Настройка — на стороне соответствующего сервиса, не в коде.

### POST `/webhooks/bitrix/task-comment`
Исходящий вебхук Bitrix24 на событие `ONTASKCOMMENTADD` (добавление комментария к задаче). Пересылает в чат заявки в приложении только комментарии, начинающиеся с префикса `_FORWARD_PREFIX` (см. `app/services/bitrix_webhook_service.py`, сейчас `/sa`) — остальная переписка в задаче остаётся только в Bitrix. Сам вебхук несёт только `data[FIELDS_AFTER][TASK_ID]`/`[MESSAGE_ID]` (без текста и без автора).

> **Новая карточка задачи Bitrix**: комментарии физически хранятся в чате (IM-модуль), а не в классической ленте комментариев. Методы `task.commentitem.get`/`task.commentitem.add` в этой конфигурации не работают (стабильно возвращают `ITEM_NOT_FOUND_OR_NOT_ACCESSIBLE`). Текст сообщения дотягивается через `tasks.task.get` (получить `chatId`) → `im.dialog.messages.get` (получить сообщение по ID из `MESSAGE_ID`), см. `bitrix_service.get_task_chat_id`/`get_dialog_message`. Префикс тоже стоит выбирать так, чтобы он не совпадал со слэш-командами/упоминаниями чата (например, `/all` — команда «уведомить всех» — не долетает до вебхука как обычный текст).

Настройка в Bitrix24: Приложения → Разработчикам → Другое → **Исходящий вебхук** → событие "Добавление комментария к задаче" → обработчик `https://<домен>/webhooks/bitrix/task-comment` → полученный `application_token` добавить в `BITRIX_INCOMING_WEBHOOK_TOKENS` (через запятую, если там уже есть токен от другого правила — например, от вебхука сделок ниже). Дополнительно у **входящего** вебхука (`BITRIX_WEBHOOK_URL`) нужна область **«Чат и звонки» / IM** — без неё `im.dialog.messages.get` вернёт `401 insufficient_scope`.

Пересланное сообщение в чате приложения отображается от лица «Ася» (см. `bitrix_service._INCOMING_USER_NAME`) — визуально как ответ бота, но сам текст сообщения явно начинается с «Ответ от оператора {имя}:», чтобы не создавалось впечатление, будто это настоящий ИИ-ответ.

Обратное направление уже работает всегда: сообщения из чата заявки в приложении (от заявителя **и** от оператора/админа/суперадмина) дублируются в чат Bitrix-задачи через `tasks.task.chat.message.send` (актуальная замена устаревшего `task.commentitem.add`) — это не требует отдельной настройки, работает через уже существующий `BITRIX_WEBHOOK_URL`.

### POST `/webhooks/bitrix/deal`
Исходящий вебхук Bitrix24 на события `ONCRMDEALADD` и `ONCRMDEALUPDATE` — один и тот же обработчик на оба (`handle_deal_event` → `upsert_project_from_deal`). Событие несёт только `ID` сделки, сама сделка дотягивается отдельным запросом (`crm.deal.get`). Это единственный способ завести или изменить проект — **ручного создания и переименования в приложении нет** (см. «Рут `admin: projects`»).

Настройка в Bitrix24: Приложения → Разработчикам → Другое → **Исходящий вебхук** → события "Сделка добавлена" (`ONCRMDEALADD`) и "Сделка изменена" (`ONCRMDEALUPDATE`) → обработчик `https://<домен>/webhooks/bitrix/deal` → полученный `application_token` добавить в `BITRIX_INCOMING_WEBHOOK_TOKENS`. У **входящего** вебхука (`BITRIX_WEBHOOK_URL`) нужна область **CRM**.

> **Событие удаления сделки (`ONCRMDEALDELETE`) не обрабатывается вообще.** Удаление сделки в Bitrix никак не влияет на проект в приложении — он останется в последнем синхронизированном виде. Единственный способ убрать проект — `DELETE /admin/projects/{id}` в самом приложении, и то не навсегда: `production_number` уникален в БД, и если по этой же сделке позже прилетит `ONCRMDEALUPDATE`, мягко удалённый проект **воскресает** автоматически (`deleted_at` снимается) вместо попытки создать дубль — см. подробности в «Рут `admin: projects`».

### Поля сделки в карточке проекта

Из карточки сделки CRM в проект приезжают: **номер в производство**, **планируемая
и фактическая даты отгрузки**, **компания-заказчик** и **контактные лица**.
Обновляются на каждом `ONCRMDEALADD`/`ONCRMDEALUPDATE`, поэтому в админке доступны
**только для чтения** — правки всё равно затрутся при следующем изменении сделки.

Файлы («Документация», «Счёт/договор») из сделки **не импортируются**: на портале
эти поля не заполняются. Внутренние документы загружаются в приложение вручную —
см. `is_internal` в разделе `admin: documents`.

**Гарантия — исключение: её в CRM нет**, даты ставит администратор через
`PATCH /admin/projects/{id}`. По `warranty_ends_at` проекта решается, попадёт ли он
в ночную синхронизацию папок на NAS: если она задана — решает она, если нет —
крайняя дата среди гарантий ШУ проекта, а если нет и того —
синхронизируем (не блокируем свежий проект).

**Контактные лица видны только операторам и админам.** В пользовательских ответах
(`GET /projects`, `GET /projects/{id}`) их нет: это персональные данные сотрудников
заказчика, а доступ к проекту выдаётся по QR-коду. Компанию и даты пользователь видит.

Набор контактов синхронизируется с заменой — убранный из сделки контакт удаляется
и у нас. Если Bitrix в этот момент недоступен, набор не трогается вовсе: иначе
разовый сетевой сбой стирал бы все контакты проекта.

#### Как найти коды пользовательских полей

Коды вида `UF_CRM_1730705809359` свои у каждого портала, поэтому задаются в `.env`,
а не в коде. Получить список:

```bash
cd savt-backend
WEBHOOK=$(grep -m1 '^BITRIX_WEBHOOK_URL=' .env | cut -d= -f2- | tr -d '"' | sed 's:/*$::')
curl -s "$WEBHOOK/crm.deal.fields.json" > /tmp/deal_fields.json
python3 - <<'PY'
import json
res = json.load(open('/tmp/deal_fields.json')).get('result') or {}
for k, v in sorted(res.items()):
    if k.startswith('UF_'):
        print(f"{k:30} {v.get('formLabel') or v.get('title') or ''} [{v.get('type')}]")
PY
```

> `BITRIX_FIELD_SHIPMENT_ACTUAL` принимает **несколько кодов через запятую** и берёт
> первое непустое. Это на случай, когда в портале живут два поля одновременно —
> старое и новое, — и часть сделок заполнена по-старому. Когда переезд завершится,
> лишний код убирается из строки.

#### Номер проекта: поле, потом название

Номер (`26_138`) берётся из `BITRIX_FIELD_PRODUCTION_NUMBER`, а если поле пустое —
из начала названия сделки (менее надёжно: название правят руками, опечатка в начале
означает, что проект не создастся или не найдётся, поэтому выделенное поле — основной путь).

Принимается любой двузначный год в номере, ограничить список можно через
`BITRIX_PRODUCTION_YEARS` — это стоит сделать **перед разовым импортом**, иначе
в базу приедут проекты за все годы, какие есть в портале.

### POST `/webhooks/bitrix/task-update`
Исходящий вебхук Bitrix24 на событие `ONTASKUPDATE` (любое изменение задачи, включая смену статуса). ID задачи несёт просто как `data[FIELDS_AFTER][ID]` (не `TASK_ID`, как в `ONTASKCOMMENTADD`) — само событие не говорит, какое именно поле изменилось, поэтому по срабатыванию просто перепроверяется текущий `STATUS` этой задачи (`tasks.task.list`) и применяется к заявке, если отличается от сохранённого. Даёт мгновенную синхронизацию статуса вместо ожидания планового опроса (см. ниже) — но сам опрос при этом никуда не делся и продолжает работать как подстраховка (например, если этот вебхук не настроен или Bitrix недоступен в момент события).

Настройка в Bitrix24: Приложения → Разработчикам → Другое → **Исходящий вебхук** → событие "Обновление задачи" (`ONTASKUPDATE`) → обработчик `https://<домен>/webhooks/bitrix/task-update` → полученный `application_token` добавить в `BITRIX_INCOMING_WEBHOOK_TOKENS` (через запятую вместе с остальными).

> Плановый опрос статусов задач (`sync_statuses_from_bitrix`, каждые 15 минут) работает независимо от этого вебхука и подстраховывает его — например, если вебхук не настроен или Bitrix недоступен в момент события.

### POST `/webhooks/bitrix/reclamation`
Исходящий вебхук Bitrix24 на событие `ONCRMDYNAMICITEMUPDATE` — изменение элемента смарт-процесса «Журнал рекламаций и претензий». Событие несёт только ID элемента, сам элемент дотягивается через `crm.item.get`. Отсюда приезжают смена стадии (→ наш `status`) и правка дедлайна.

> **Событие общее на все смарт-процессы портала, а не только на рекламации** — проверено вживую, первые реальные срабатывания пришли с `ENTITY_TYPE_ID=1118` («Закупка»). Поэтому обработчик первым делом фильтрует по `ENTITY_TYPE_ID`, сверяя его с `BITRIX_RECLAMATION_ENTITY_TYPE_ID`. Без фильтра приложение реагировало бы на чужие процессы.

Настройка в Bitrix24: Приложения → Разработчикам → Другое → **Исходящий вебхук** → событие обновления элемента смарт-процесса (`ONCRMDYNAMICITEMUPDATE`) → обработчик `https://<домен>/webhooks/bitrix/reclamation` → полученный `application_token` добавить в `BITRIX_INCOMING_WEBHOOK_TOKENS`.

### POST `/webhooks/bitrix/reclamation-delete`
Исходящий вебхук на событие `ONCRMDYNAMICITEMDELETE` — карточку рекламации удалили в Bitrix. Фильтрует `ENTITY_TYPE_ID` так же, как и вебхук выше.

Заявка при этом **не удаляется**: у неё обнуляется `bitrix_item_id`, проставляется `bitrix_deleted_at`, снимаются все недоставленные операции из очереди, и она попадает в `GET /admin/reclamations/bitrix-detached` — заводить карточку заново или закрывать заявку, решает админ. Заново в Bitrix она сама не уедет: карточку удалили осознанно, и воскрешать её против воли того, кто удалил, приложение не должно.

Настройка — как и у остальных: событие удаления элемента смарт-процесса → обработчик `https://<домен>/webhooks/bitrix/reclamation-delete` → `application_token` в `BITRIX_INCOMING_WEBHOOK_TOKENS`.

> Вебхук — не единственный способ узнать об удалении. Если его не настроить (или если карточку удалили, пока приложение лежало), то же самое вскроется при первой же отправке: Bitrix ответит `NOT_FOUND`, и рекламация отвяжется точно так же. Вебхук нужен, чтобы узнавать сразу, а не при следующей попытке синхронизации.

### POST `/webhooks/telemetry`
Не от самого ПЛК — от промежуточного прокси на C#, который слушает MQTT-топик
контроллера ШУ и пересылает сюда обычным HTTP. Авторизация — общий секрет в
заголовке (не в теле), сверяется через `hmac.compare_digest`:
```
X-Telemetry-Secret: <TELEMETRY_WEBHOOK_SECRET из .env>
```
Тело:
```json
{
  "topic": "26_001/1/data",
  "registers": { "500": 9, "501": 5732, "502": 18 },
  "timestamp": "2026-08-13T10:00:00Z"
}
```
- `topic` — топик контроллера как есть, по нему ищем ШУ через `Cabinet.mqtt_topic` (см. `PATCH /admin/cabinets/{id}`). Если топик ни к одному ШУ не привязан — `404`.
- `registers` — сырые пары «адрес регистра → значение», без ограничения по количеству за раз. Расшифровка в человекочитаемый вид — на чтение, через карту регистров (см. «Рут `admin: telemetry`»), не здесь.
- `timestamp` — необязателен; если не прислан, временем события считается момент получения на сервере.

При приёме, если относительно предыдущего сообщения появилась новая (взведённая и названная в карте) авария — всем участникам проекта этого ШУ уходит push-уведомление типа `cabinet_alarm` (см. «Рут `notifications`»). На снятие аварии и на регистры без названия push не шлётся.

Успех — `204 No Content`.

### GET `/webhooks/telemetry/targets`
Тоже только для прокси, тот же заголовок `X-Telemetry-Secret`. Список брокеров,
к которым прокси должен быть подключён прямо сейчас — свой у **каждого** ШУ,

```json
[
  {
    "cabinet_id": 56,
    "host": "192.168.1.240",
    "port": 1883,
    "topic": "LicOS_PUBM",
    "username": null,
    "password": null
  }

```
Прокси дёргает эту ручку периодически (не хранит список статично в своём
конфиге) — появился ШУ с указанным брокером, прокси сам подключится на
следующем опросе, без передеплоя. Пропал/поменялся — старое подключение
закрывается.

## Конвенции API

### Формат ошибок и лимиты запросов

Все ошибки API — единый JSON `{ "detail": "<текст для показа пользователю>" }`,
код ответа — `400`/`401`/`403`/`404`/`409`/`429`. Исключение — `422` (тело запроса
не прошло валидацию): там `detail` не строка, а **массив** объектов
`{loc, msg, type}` от pydantic — это единственный случай, когда `detail` нельзя
показывать пользователю как есть.

> **`502`/`503`/`504` (api недоступен — контейнер упал/перезапускается/деплой) —
> тоже JSON**, `{"detail": "Сервис временно недоступен, попробуйте ещё раз через
> минуту"}`, код `503`. Без этого nginx на разрыв соединения с апстримом
> по умолчанию отдаёт свою HTML-страницу ошибки — на неё `Content-Type` не
> `application/json`, клиент, ожидающий JSON (например, парсер Flutter-приложения),
> падает на попытке распарсить HTML как JSON вместо того, чтобы показать
> нормальную ошибку. Настроено через `error_page 502 503 504 = @api_unavailable`
> в `nginx.conf`/`nginx.http-fallback.conf`/`nginx.dev.conf`, на все location,
> которые проксируют на `api:8000` (кроме `location /` во внутреннем порту 8080,
> который проксирует фронтенд — туда HTML-ошибки уместны, `error_page` там
> объявлен только внутри `/backend/*`, не на уровне всего `server`).

> До недавнего времени `429` от превышения лимита запросов (`@limiter.limit`)
> отдавался библиотекой slowapi в своём формате — `{"error": "..."}`, другим
> ключом, чем всё остальное API. Если где-то в старом клиентском коде обработка
> ошибок написана под `{"error": ...}` — это относится только к `429` и теперь
> не актуально, формат унифицирован.

Лимиты на auth-эндпоинтах (по IP):

| Эндпоинт | Лимит |
|---|---|
| `POST /auth/register/start` | 5/мин |
| `POST /auth/register/complete` | 10/мин |
| `POST /auth/register/resend` | 3/мин |
| `GET /auth/register/status` | 60/мин |
| `POST /auth/login` | 10/мин |
| `POST /auth/admin-login` | 5/мин |
| `POST /auth/refresh` | 20/мин |
| `POST /auth/guest` | 30/мин |
| `POST /auth/password-reset/start` | 5/мин |
| `POST /auth/password-reset/complete` | 5/мин |
| `POST /auth/change-phone/request` | 5/мин |
| `GET /admin/cabinets/{id}/telemetry` и `.../telemetry/history` | 1200/мин |
| `POST /webhooks/telemetry` | 3000/мин |
| Всё остальное | 200/мин (общий лимит по умолчанию) |

> Повышенные лимиты на телеметрии — лимит считается **по IP**, а несколько
> десятков операторов за одним внешним адресом (офис/VPN) делят один и тот же
> бюджет: панели с открытой карточкой ШУ может хватить, чтобы упереться в
> общий 200/мин на всех сразу. По той же причине (лимит по IP) под дефолтный
> лимит может уйти и `telemetry-proxy` — он шлёт `POST /webhooks/telemetry`
> суммарно по всем подключённым ШУ с одного фиксированного внутреннего адреса
> контейнера, и с ростом числа настроенных брокеров это ожидаемо превышает
> 200/мин безо всякой атаки (сам вебхук и так закрыт отдельным секретом в
> заголовке, см. «Вебхуки внешних интеграций»). Realtime-сигнал на телеметрии
> публикуется только при реальном изменении состояния, не на каждое
> периодическое повторение (см. «Рут `admin: telemetry`»), но сами лимиты
> всё равно оставлены выше дефолтного — все три ручки закрыты ролью/секретом,
> не публичные, риск ниже, чем у auth-эндпоинтов.

На `429` бессмысленно ретраить немедленно — почти всегда это или экран с паролем,
который человек вводит не быстрее раза в секунду, или баг в клиенте (например,
`/auth/refresh` вызван параллельно из нескольких мест, см. ниже).

### Токены: обновление сессии, «запомнить меня», гость

`access_token` живёт `JWT_ACCESS_TOKEN_TTL_MINUTES` (по умолчанию 30 минут),
`refresh_token` — `JWT_REFRESH_TOKEN_TTL_DAYS` (по умолчанию 60 дней) и
**одноразовый**: `POST /auth/refresh` отзывает переданный и выдаёт новую пару.
Повторное использование уже отозванного `refresh_token` трактуется как
компрометация — обрываются **все** сессии пользователя на всех устройствах, и
следующий `/auth/refresh` вернёт `401`.

```
1. Каждый запрос — Authorization: Bearer <access_token>
2. Ответ 401 →
   a. POST /auth/refresh { refresh_token }
   b. Успех → сохранить НОВУЮ пару, повторить исходный запрос
   c. 401 от /auth/refresh → сессия невосстановима, разлогинить
3. Несколько параллельных 401 — обновлять ОДИН раз (single-flight/мьютекс),
   не запускать /auth/refresh из каждого запроса отдельно: второй вызов
   придёт с уже отозванным refresh_token и попадёт под защиту от
   компрометации, разлогинив пользователя без причины
```

У одного пользователя одновременно живо не больше 5 `refresh`-сессий: при входе
на 6-м устройстве самая старая тихо отзывается (`trim_sessions`). Держащий
`refresh_token` неактивным месяцами клиент («запомнить меня») может быть
вытеснен просто тем, что пользователь много раз входил с других устройств.

Отдельного серверного флага «запомнить меня» нет — это решается местом
хранения `refresh_token` на клиенте (переживёт перезапуск приложения или
только в памяти до закрытия). `access_token` в обоих случаях достаточно
держать в памяти — он короткоживущий. При логауте — всегда
`POST /auth/logout { refresh_token }`, чтобы токен отозвался и на сервере.

Гостевой токен (`POST /auth/guest`, без пароля и без пользователя — см. «Рут
`auth`») не поддерживает `/auth/refresh`: у гостя нет `refresh_token`. При 401
на гостевом токене просто запросить новый через `/auth/guest`, без редиректа
на экран входа — гость и не должен был логиниться.

---

### PATCH-запросы — как редактировать

```
1. Сначала GET → получить текущие данные → предзаполнить форму
2. Пользователь меняет нужные поля
3. PATCH → отправить ТОЛЬКО изменённые поля

Если поле не отправить → оно не изменится.
Если отправить null → значение сбросится (если поле nullable).

Пример редактирования ШУ:
1. GET /cabinets/{id}           → { custom_name: "Старое название", custom_comment: null }
2. PATCH /cabinets/{id}         → { custom_name: "Новое название" }
   ← custom_comment не трогали → не меняется
```

### Подписанные ссылки на файлы

**Что это значит на практике — в большинстве случаев ничего особенного.** Правило простое:

> Используй URL ровно в том виде, в каком он пришёл от API, и не собирай его руками
> из имени файла. Отправлять обратно можно как есть — сервер сам отбросит подпись.

Подробности:

- Все ссылки в ответах API приходят с хвостом `?md5=...&expires=...` — это касается
  `file_url` вложений, `url` фото, `file_url` документов и вложений базы знаний,
  `wallpaper_url`, `photo_url` в заявках, а также `url` из `/upload/*`.
- Ссылка живёт **сутки** (`STATIC_LINK_TTL_SECONDS`). Экран, открытый дольше суток,
  должен перезапросить данные — после рефетча ссылки снова свежие. Просроченная
  ссылка отдаёт `410`, ссылка без подписи или с испорченной подписью — `403`.
- **Отправлять URL обратно можно прямо с подписью** (`POST /chats/{id}/messages`,
  `POST /cabinets/add-by-photo`, `PATCH /chats/{id}/wallpaper`, `POST /upload/transcribe`) —
  сервер снимает подпись перед сохранением, в БД лежит голый путь.
- Ссылки, которые сервер сам отправляет в комментарии Bitrix-задач, подписываются
  на **90 дней** — их открывают сотрудники без сессии в нашем API.
- Кешировать файл по URL можно, но помни, что после истечения срока тот же URL
  перестанет работать — кешируй **содержимое**, а не ссылку.

> **Документы с ограниченным доступом** (`requires_approval: true`) прямой ссылки не
> получают **вообще** — у них `file_url: null` даже после одобрения доступа. Скачивать
> только через `GET /documents/{id}/download`: подписанную ссылку можно переслать
> третьему лицу, а download-эндпоинт проверяет права на каждое скачивание.

## Рут `auth` — авторизация и аккаунт

### POST `/auth/guest`
**Гостевой доступ** — без регистрации, для экранов, явно открытым без входа: сейчас это
`GET /kb/*`, `GET /faq/*` и `GET /tags` (см. врезку ниже). Тело не нужно.
```json
{ "access_token": "eyJ...", "token_type": "bearer", "expires_in": 1800 }
```
`expires_in` — секунды, совпадает с `JWT_ACCESS_TOKEN_TTL_MINUTES`. **`refresh_token` не выдаётся**: выпуск гостевого токена не обращается к БД вообще (нет ни пользователя, ни сессии, которую можно было бы продлить), поэтому при истечении клиент просто зовёт `/auth/guest` заново — это так же дёшево, как обновить токен.

Гостевой токен принимается **только** на роутах, явно на это рассчитанных (`get_current_user_or_guest`). На любом обычном эндпоинте (`get_current_user`) он отвергается с `401 "Неверный тип токена"` — гость не может выдать себя за пользователя ни при каких обстоятельствах, проверка на уровне JWT-claim `type`, а не роли.

> **Что открыто гостю:** список и содержимое статей базы знаний, вложения к ним, список вопросов FAQ, список тегов. Всё остальное — чаты, заявки, проекты, ШУ, уведомления — требует полноценного входа.
>
> Анонимного доступа совсем без токена нет намеренно: гостевой JWT ничего не стоит выдать (не трогает БД), а клиентский код при этом не разветвляется на «с токеном» / «без токена» — заголовок `Authorization` есть всегда, просто с одним из двух типов токена внутри.
>
> На 401 с гостевым токеном клиент не должен пытаться `POST /auth/refresh` (у гостя нет `refresh_token`) и не должен редиректить на экран входа — просто очистить токен и запросить новый через `/auth/guest`.

### POST `/auth/register/start`
Начало регистрации. **Номер телефона здесь не передаётся** — он придёт из контакта
Telegram.
```json
{
  "password": "minLength8",
  "password_confirm": "minLength8",
  "full_name": "Иванов Иван Иванович",
  "user_type": "individual",
  "organization_name": null,
  "contact_phone": "+375291110000"
}
```
- `password` — минимум 8 символов
- `password_confirm` — должен совпадать с `password`
- `user_type` — `individual` или `organization`
- `organization_name` — обязателен если `user_type = organization`
- `contact_phone` — **необязательный** рабочий номер. Не подтверждается, на вход не
  влияет, виден операторам, правится через `PATCH /auth/me`. Номером аккаунта
  (логином) не становится

Ответ:
```json
{
  "message": "Откройте Telegram и подтвердите номер",
  "registration_token": "kQ2f...",
  "deep_link": "https://t.me/<bot>?start=kQ2f...",
  "resend_after_seconds": 60
}
```
- `registration_token` — **сохранить**: им идентифицируются `/register/complete` и
  `/register/resend`. Телефон для этого не годится — клиент его ещё не знает
- `deep_link` — всегда непустая: подтвердить номер можно только в Telegram

**Откуда берётся номер аккаунта.** Открыть ссылку недостаточно — она лишь начинает
диалог. Дальше бот показывает кнопку «Отправить мой номер» (`request_contact`), и
номер из этого контакта становится номером аккаунта. Telegram проверил его при
регистрации аккаунта и подставляет сам — ввести произвольный в боте невозможно.

Единственная проверка на нашей стороне: **контакт принадлежит отправителю**
(`contact.user_id == message.from.id`). Telegram разрешает переслать боту **любой**
контакт из адресной книги — без этой проверки достаточно было бы отправить карточку
жертвы, и её номер стал бы номером чужого аккаунта. Сверять номер с чем-то ещё не
нужно и не с чем: в форме его больше не спрашивают.

Пока номер не подтверждён, ни пользователя, ни кода не существует — данные формы
лежат в `pending_registrations` и протухают вместе с токеном (TTL —
`MESSENGER_LINK_REQUEST_TTL_MINUTES` + `SMS_CODE_TTL_MINUTES`, по умолчанию 25 минут).

> Ранее номер вводился в форме и не сверялся ни с чем: код улетал любому, кто открыл
> ссылку. Занять можно было любой незарегистрированный номер, не имея к нему доступа —
> владелец после этого не мог зарегистрироваться сам.

#### Один Telegram — один аккаунт

Номер аккаунта берётся из Telegram, а `users.phone` уникален. Значит с одного
Telegram-аккаунта можно завести ровно один аккаунт в приложении. Три следствия,
которые надо понимать и обрабатывать на клиенте.

**1. Повторная регистрация с того же Telegram — отказ.**

Человек уже зарегистрирован, но снова проходит регистрацию (частый случай: хочет
поменять рабочий номер и по привычке лезет регистрироваться вместо того, чтобы
войти и отредактировать `contact_phone`). Контакт отдаёт тот же номер, находится
существующий подтверждённый аккаунт — и бот отвечает в Telegram:

> Номер +375XXXXXXXXX уже зарегистрирован. Войдите в приложение по этому номеру,
> а если забыли пароль — воспользуйтесь восстановлением.

Новый аккаунт не создаётся, код не отправляется. **Существующий аккаунт при этом
не изменяется вообще** — ни пароль, ни ФИО, ни организация. Это принципиально:
иначе «повторная регистрация» была бы способом переписать пароль чужого аккаунта.

Объяснение приходит **в Telegram**, а приложение в этот момент ждёт код. Чтобы оно
не ждало вечно, есть `GET /auth/register/status` — он вернёт `status: "failed"` и
`reason: "phone_already_registered"`. Поллить его, пока пользователь в Telegram, и
на `failed` показывать нормальный экран с кнопкой «Войти».

> Проверка идёт **по самому Telegram-аккаунту**, а не только по номеру. Если
> человек сменил номер телефона входа (`PATCH /users/me/phone`), его аккаунт уже
> не совпадёт с тем, что отдаст кнопка «Отправить мой номер» — и проверка «такой
> номер занят» пропустила бы его, заведя второй аккаунт с того же Telegram.
> Поэтому первым делом ищется существующая привязка чата: она даёт
> `reason: "telegram_already_linked"`, и в сообщении называется тот номер, под
> которым человек на самом деле входит.

**2. Брошенная регистрация — можно начать заново.**

Если код так и не был введён, аккаунт остался неподтверждённым. Повторная
регистрация с того же Telegram пройдёт нормально: данные неподтверждённого аккаунта
перезапишутся новыми из формы, придёт код, регистрация завершится. Дубликата не
возникнет.

**3. Пользователь сменил номер в самом Telegram — появится второй аккаунт.**

Telegram позволяет менять номер аккаунта. После этого контакт отдаст уже другой
номер, пользователя с таким номером в системе нет — и заведётся **второй** аккаунт.
Старый останется со старым номером.

Дополнительно: `messenger_links` уникальна по `(user_id, channel)`, но **не** по
`external_chat_id`, поэтому оба аккаунта окажутся привязаны к одному чату Telegram.
Дырой это не является (человек тот же), но восстановление пароля для обоих будет
приходить в один чат, и различать их придётся по тексту сообщения. Правильный выход
для такого пользователя — заявка на смену номера (`POST /auth/change-phone/request`),
а не вторая регистрация.

---

### POST `/auth/register/complete`
Завершение регистрации кодом из Telegram. Опознаётся по `registration_token`, а не по
телефону: клиент номера не знает — он пришёл из контакта Telegram.
```json
{
  "registration_token": "kQ2f...",
  "code": "123456"
}
```
Ответ: `201 Created`
```json
{
  "access_token": "eyJ...",
  "refresh_token": "abc123...",
  "token_type": "bearer"
}
```
Номер аккаунта можно прочитать из `GET /auth/me` (поле `phone`).

Ошибки:
- `404` — регистрация не найдена или истекла, начинать заново
- `400` — номер ещё не подтверждён: пользователь не нажал «Отправить мой номер» в Telegram
- `400` — неверный код / превышено число попыток

---

### GET `/auth/register/status?registration_token=...`
Где сейчас находится незавершённая регистрация. Без авторизации (её ещё нет),
доступ по токену. Лимит — 60 запросов в минуту, рассчитан на поллинг.

**Зачем.** Номер подтверждается в Telegram, и об отказе бот сообщает там же —
приложение об этом иначе не узнает. По одному лишь `/register/resend` отличить
«ещё не нажал кнопку» от «отказано» невозможно: в обоих случаях вернётся непустой
`deep_link`, и клиент будет гонять человека в Telegram по кругу.

```json
{ "status": "waiting_contact", "reason": null }
```

| `status` | Что значит | Что показать |
|---|---|---|
| `waiting_contact` | ждём нажатия «Отправить мой номер» | «Подтвердите номер в Telegram» |
| `code_sent` | номер подтверждён, код отправлен | экран ввода кода |
| `failed` | бот отказал, кода не будет — см. `reason` | см. ниже |
| `expired` | истекли 25 минут | «Начните регистрацию заново» |
| `completed` | регистрация по этому токену уже завершена | перейти ко входу |

`reason` заполняется только при `failed`:

| `reason` | Причина | Что показать |
|---|---|---|
| `phone_already_registered` | под этим номером уже есть подтверждённый аккаунт | «Войдите по этому номеру» + кнопки «Войти» / «Забыли пароль» |
| `telegram_already_linked` | этот Telegram уже привязан к аккаунту (возможно, с другим номером входа — его человек и сменил) | то же самое; номер входа назван в сообщении бота |
| `foreign_contact` | переслал чужой контакт вместо кнопки | «Нажмите кнопку "Отправить мой номер"», вернуть в Telegram |
| `bad_phone` | номер не разобрался | «Обратитесь в поддержку» |

`404` — токен не найден вообще.

> `failed` по причинам `foreign_contact` и `bad_phone` **не закрывает регистрацию**:
> пользователь может вернуться в Telegram и нажать кнопку правильно, отметка
> снимется сама. При `phone_already_registered` и `telegram_already_linked` повтор
> не поможет — Telegram отдаст тот же контакт.

### POST `/auth/register/resend`
Повторная отправка кода.
```json
{ "registration_token": "kQ2f..." }
```
Ответ:
```json
{ "message": "Код отправлен повторно", "resend_after_seconds": 60, "deep_link": null }
```
- `deep_link != null` — номер ещё не подтверждён, кода не существует: вернуть
  пользователя в Telegram нажать «Отправить мой номер»
- `deep_link == null` — номер подтверждён, отправлен новый код

```json
{
```
```json
  "refresh_token": "abc123..."
```

### GET `/auth/me`
Данные текущего авторизованного пользователя (требует Bearer-токен).
```json
{
  "id": 1,
  "phone": "+375291234567",
  "contact_phone": "+375291110000",
  "email": null,
  "user_type": "individual",
  "organization_name": null,
  "full_name": "Иванов Иван",
  "role": "user",
  "is_phone_verified": true,
  "is_verified": false
}
```
- `phone` — **подтверждённый номер из Telegram, он же логин.** Пользователь его не
  меняет: только через заявку с одобрением админа (`POST /auth/change-phone/request`)
- `contact_phone` — рабочий номер, необязательный. Не подтверждается, на вход не
  влияет, меняется свободно через `PATCH /auth/me`. Именно его стоит показывать
  как «телефон для связи»
- `is_verified` — подтверждён ли аккаунт администратором

---

### DELETE `/auth/me`
Удаление собственного аккаунта (доступно всем авторизованным пользователям). Отзывает все refresh-токены и удаляет аккаунт безвозвратно.

Ответ: `204 No Content`.

---

### POST `/auth/password-reset/start`
Запрос кода для сброса пароля (доставка в Telegram, см. `/register/start`).
```json
{ "phone": "+375291234567", "channel": "telegram" }
```
Ответ:
```json
{
  "message": "На телефон отправлен код",
  "resend_after_seconds": 60,
  "deep_link": null
}
```
Если телефон не найден/не подтверждён/деактивирован — ответ тот же (`deep_link: null`,
код никуда не уходит), чтобы нельзя было по ответу узнать, существует ли номер в системе.

> **`deep_link` здесь всегда `null`.** Код уходит только в уже подтверждённый
> Telegram владельца аккаунта; если связки нет — не уходит никуда, и пользователь
> сам пароль не сбросит (только через администратора). Этот эндпоинт новых связок
> не создаёт — они заводятся исключительно при регистрации, где номер подтверждается
> контактом Telegram. Так эндпоинт, открытый без авторизации, не может стать путём
> захвата чужого аккаунта через подключение стороннего канала.

---

### POST `/auth/password-reset/complete`
Установка нового пароля после подтверждения кода.
```json
{
  "phone": "+375291234567",
  "code": "123456",
  "new_password": "newPassword8",
  "new_password_confirm": "newPassword8"
}
```
Ответ: `204 No Content`. Все сессии инвалидируются.

---

### POST `/auth/password-change`
Смена пароля для авторизованного пользователя (требует Bearer-токен).
```json
{
  "password": "oldPassword",
  "new_password": "newPassword8",
  "new_password_confirm": "newPassword8"
}
```
Ответ: `200 OK` с сообщением об успехе. Закрывает все сессии пользователя; у сотрудника с `must_change_password` снимает этот флаг.

---

### DELETE `/auth/me/email`
Очистить почту в профиле. `200`, ответ — профиль в том же виде, что у `GET /auth/me`.
Отдельная ручка нужна потому, что в `PATCH /auth/me` `email: null` означает «не менять».

---

### PATCH `/auth/me`
Редактирование личных данных авторизованного пользователя. Передавать только изменённые поля.
```json
{
  "full_name": "Иванов Иван Иванович",
  "email": "ivan@example.com",
  "organization_name": "ООО Ромашка",
  "contact_phone": "+375291110000"
}
```
Ответ: обновлённый профиль (аналогично `GET /auth/me`).

`contact_phone` — рабочий номер для связи, меняется свободно. Номер-логин (`phone`)
этим эндпоинтом **не меняется**: он подтверждён контактом из Telegram, и сменить его
можно только через заявку с одобрением админа.

---

### POST `/auth/change-phone/request`
Заявка на смену номера телефона. Лимит — 5 запросов в минуту.

> Самостоятельной смены номера нет — только через заявку с решением
> администратора. Автоматически подтвердить владение новым номером нечем: SMS
> отключены, а код в мессенджер уходил бы самому заявителю (доставка привязана
> к `user_id`, а не к номеру) и ничего бы не доказывал. Администратор
> подтверждает владение вне системы (звонок, документы), заявка хранит след решения.

```json
{ "new_phone": "+375291234568", "user_comment": "Сменил оператора связи" }
```
`user_comment` необязателен (до 1000 символов) — обоснование для администратора.

Ответ `201 Created`:
```json
{
  "id": 12,
  "user_id": 5,
  "new_phone": "+375291234568",
  "old_phone": "+375291234567",
  "user_comment": "Сменил оператора связи",
  "status": "pending",
  "admin_response": null,
  "resolved_by_admin_id": null,
  "created_at": "2026-07-31T10:00:00Z",
  "resolved_at": null
}
```

Ошибки:
- `409` — это уже ваш текущий номер
- `409` — номер уже занят другим пользователем
- `409` — у вас уже есть необработанная заявка

---

### GET `/auth/change-phone/request`
Своя активная заявка. Ответ — `PhoneChangeRequestOut` либо `null`, если активной нет.

---

### DELETE `/auth/change-phone/request`
Отозвать свою необработанную заявку (например, ошибся номером). Ответ: `204 No Content`.
Если активной заявки нет — `404`.

---

### POST `/auth/admin-login`
Вход для администратора и оператора — по логину, не по телефону.
```json
{
  "login": "operator1",
  "password": "P@ssword8"
}
```
Ответ: пара токенов (`access_token`, `refresh_token`) и `must_change_password`. Доступен только для ролей `operator`, `admin` и `superadmin` — обычный пользователь получит `401`.

Логином сотрудника, заведённого из Bitrix (см. «Рут `admin: staff`»), служит его номер телефона. Вводить можно как угодно — `+375291112233`, `+375 (29) 111-22-33`, `375291112233`, `80291112233`, `291112233`.

**`must_change_password: true`** — пароль задан не самим человеком (общий начальный пароль). Пока он не сменён, любой запрос, кроме `POST /auth/password-change`, `POST /auth/logout` и `GET /auth/me`, получает `403 "Необходимо сменить пароль"`. Фронт должен после входа сразу показать экран смены пароля. После `POST /auth/password-change` все сессии закрываются — войти нужно заново уже с новым паролем.

## Рут `admin: staff` — сотрудники из Bitrix (только суперадмин)

Операторы, администраторы и суперадмины заводятся из сотрудников Bitrix и не создаются руками. Источник правды — Bitrix.

**Роль по отделам** (ID отдела портала → роль; `app/core/staff_departments.py`): Директор, Главный инженер, Заместитель главного инженера по производству — `superadmin`; Сектор разработки ПО, Заместитель директора по коммерческим вопросам, Помощник директора — `admin`; остальные рабочие отделы (бухгалтерия, наладка, проектирование, производство, конструкторы, механика, коммерческий сектор, снабжение, склад, персонал) — `operator`. «Отпуск по уходу за ребёнком» роли не даёт. Если сотрудник в нескольких отделах — берётся высшая роль. Для отдельных людей роль задана вручную (`USER_ROLE_OVERRIDES` в том же файле, по ID сотрудника в Bitrix) и важнее отдела; `None` — человека в систему не заводят.

**Правила:**
- заводятся только активные сотрудники (`employee`); внешние (`extranet`) — нет;
- логин — номер телефона (рабочий, а если нет — личный мобильный) в формате `+375…`, `phone` у такой учётки пустой;
- начальный пароль у всех один — `BITRIX_STAFF_INITIAL_PASSWORD` из `.env`, при первом входе обязательна смена (`must_change_password`). Пароль пустой — новых сотрудников не заводим;
- уволенный, неактивный, ушедший в отдел без роли или удалённый из Bitrix **деактивируется** (не удаляется — на него ссылается история), все его сессии закрываются; вернулся — активируется снова;
- сотрудник без телефона, с нераспознанным телефоном или с телефоном, который указан у нескольких сотрудников, не заводится — попадает в отчёт;
- если номер сотрудника есть и в обычном аккаунте мобильного приложения — это не конфликт: заводится отдельная учётка для входа в админку (логин — номер), мобильный аккаунт не меняется. Конфликт — номер уже привязан к другому сотруднику или логин с этим номером занят не сотрудником (причина пишется в отчёте);
- если номер совпал с уже существующим вручную заведённым оператором/админом — учётка привязывается к сотруднику; роль при этом только повышается, не понижается;
- меняются и деактивируются только учётки, которые завела или привязала синхронизация (`bitrix_user_id`). Остальные не трогаются;
- роль у привязанных следует за отделом в обе стороны; сменили номер в Bitrix — меняется и логин.

Запускается раз в час фоновой задачей и по запросу:

С сервера, без токена: `docker exec savt-backend-api-1 python -m app.cli sync-bitrix-staff` — печатает тот же отчёт текстом (кого завели, кого деактивировали, кого и почему пропустили).

### POST `/admin/staff/bitrix-sync`
Запустить синхронизацию сейчас (`superadmin`), например после приёма человека на работу. `502`, если Bitrix недоступен или не настроен (в этом случае никого не деактивируем).

```json
              "skipped_no_phone": 3, "skipped_invalid_phone": 0, "skipped_duplicate_phone": 2,

  "created": [ { "bitrix_user_id": 7, "full_name": "Иванов Иван Иванович", "role": "operator", "login": "+375291112233" } ],
```

Остальные списки (`linked`, `role_changed`, `reactivated`, `skipped_invalid_phone`, `skipped_conflict`, `skipped_no_password`) устроены так же. Каждый запуск пишется в журнал действий (`staff.bitrix_sync`).

## Рут `upload` — загрузка файлов

Все эндпоинты требуют Bearer-токен. Принимают `multipart/form-data`.

### POST `/upload/attachment`
Загрузка вложения. Принимает **любой MIME-тип** — лимитов по формату нет. Лимит размера — 500 МБ.

Директория сохранения определяется по MIME-типу:
- `image/*` → `/static/photos/`
- `video/*` → `/static/videos/`
- `audio/*` → `/static/voices/`
- всё остальное → `/static/files/`

Ответ:
```json
{ "url": "/static/photos/abc123.jpg" }
```

Ошибки:
- `413` — файл превышает 500 МБ

---

### POST `/upload/voice`
Загрузка голосового сообщения.

| Форматы | Лимит |
|---|---|
| ogg, mp3, m4a, wav, webm, aac | 25 МБ |

`audio/webm` и `video/webm` (Chrome/Firefox запись) поддерживаются напрямую.

Ответ:
```json
{ "url": "/static/voices/abc123.ogg" }
```

Ошибки:
- `415` — неподдерживаемый MIME-тип файла
- `413` — файл превышает лимит размера

---

### GET `/upload/download?url={file_url}`
Скачать любой файл (фото, документ, видео, голосовое) с заголовком `Content-Disposition: attachment`. Требует Bearer-токен.

Параметр `url` — значение поля `file_url` из вложения или `url` из фото, например `/static/photos/abc123.jpg`.

- `400` — URL не указывает на загруженный файл
- `404` — файл не найден на диске

---

### POST `/upload/transcribe`
Распознать голосовое сообщение в текст через Yandex SpeechKit. Требует настроенных `YANDEX_FOLDER_ID` и `YANDEX_API_KEY`.

Тело запроса (JSON):
```json
{ "file_url": "/static/voices/abc123.ogg" }
```

Ответ:
```json
{ "text": "распознанный текст сообщения" }
```

Принимает любой формат, который умеет читать `ffmpeg` (`ogg/opus`, `webm`, `mp3`, `m4a`, `aac`, `wav` и т.д.) — сервер сам перекодирует файл в OGG/Opus перед отправкой в Yandex, поэтому реальный контейнер/кодек присланного файла значения не имеет. Файл должен быть предварительно загружен через `POST /upload/voice`.

**Размер файла (после перекодирования) обрабатывается гибридно:**
- **≤ 1 МБ** (примерно 30-60 сек записи) — синхронное распознавание (`stt:recognize`), ответ обычно за 1-3 секунды.
- **> 1 МБ** — асинхронное распознавание (`longRunningRecognize`): файл временно загружается в Yandex Object Storage (бакет приватный, доступ для Yandex через presigned URL на 1 час), сервер сам дожидается результата (поллинг, до ~100 сек) и удаляет файл из Object Storage по завершении. Для фронта это прозрачно — ответ остаётся `{ text }`, просто запрос может идти дольше. Требует дополнительно настроенных `YANDEX_STORAGE_BUCKET`, `YANDEX_STORAGE_ACCESS_KEY_ID`, `YANDEX_STORAGE_SECRET_ACCESS_KEY`.

Эндпоинт **stateless**: ничего не сохраняет в БД, не привязан к чату/сообщению — принимает любой `file_url` из `/static/voices/...` и просто возвращает текст. Повторный вызов — повторное распознавание.

Ошибки:
- `400` — некорректный URL, либо файл не распознан как аудио (ffmpeg не смог его обработать)
- `404` — файл не найден
- `503` — Yandex SpeechKit/Object Storage недоступны, не настроены, вернули ошибку, либо распознавание не уложилось в таймаут (для очень длинных записей)

## Рут `admin: cabinets` — управление ШУ (только админ)

### POST `/admin/cabinets`
Создание нового ШУ. **`project_id` обязателен** — ничейных ШУ больше не заводится,
каждый ШУ создаётся сразу внутри проекта. `404`, если проект не найден или удалён.
```json
{
  "project_id": 3,
  "type": "вентиляционная установка",
  "object_number": "29_099",
  "description": "Описание",
  "warranty_starts_at": "2025-01-01T00:00:00Z",
  "warranty_ends_at": "2027-01-01T00:00:00Z",
  "admin_internal_name": "ШУ-18К",
  "admin_comment": "Комментарий для внутреннего использования",
  "purpose": "Вентиляция",
  "latitude": 53.9045,
  "longitude": 27.5615
}
```
`latitude` (-90…90) и `longitude` (-180…180) — необязательны, геолокация ШУ на карте.
`warranty_starts_at`/`warranty_ends_at` — тоже необязательны (можно не указывать вообще, если у ШУ нет гарантии); если заданы оба — `warranty_ends_at` должен быть позже `warranty_starts_at`.

При создании — то же самое, что делает `PATCH /admin/cabinets/{id}/project` при
привязке уже существующего ШУ: участники проекта сразу получают доступ (без
заявок), и на NAS заводятся его подпапки (`Фото`, `Переписка`, `_Маркировка`,
`_Руководство` — см. раздел «admin: projects» про структуру папок).

> Позже отвязать ШУ от проекта (`PATCH .../project` с `{ "project_id": null }`)
> по-прежнему можно — ограничение только на создание, не на дальнейшее управление.

**Поле `type`:**
- Приводится к нижнему регистру автоматически (`"Вентиляция"` = `"вентиляция"`)
- Если тип новый — создаётся тег `scope="cabinet_type"` автоматически
- На фронте: получить список готовых типов через `GET /tags?scope=cabinet_type` и показать выпадающий список

Ответ — полная информация о созданном ШУ включая `tags`.

---

### GET `/admin/cabinets`
Список всех ШУ. Доступно оператору и администратору.

> Фильтра `has_project` нет: каждый ШУ создаётся внутри проекта
> (`POST /admin/cabinets` требует `project_id`), «ШУ без проекта» —
> не обычное состояние, а редкая историческая запись, фильтровать почти нечего.

Параметры:
- `search` — поиск по типу, номеру объекта, названию, назначению, описанию, комментарию
- `tag_ids` — фильтр по тегам (`?tag_ids=1&tag_ids=2`)
- `has_documents` — `true` / `false` — есть ли документы
- `has_photos` — `true` / `false` — есть ли фото
- `has_users` — `true` / `false` — есть ли привязанный пользователь
- `has_service_requests` — `true` / `false` — есть ли сервисные заявки
- `warranty_status` — `active` (действует, срок > 30 дней) / `expiring_soon` (истекает в течение 30 дней) / `expired` (истекла) / `none` (гарантия не указана вообще)
- `project_id` — точная привязка к конкретному проекту (`?project_id=3`) — например, для отображения карточек ШУ на странице проекта (полноценных, с гарантией/тегами/т.п.), в отличие от урезанного `cabinets[]` из `GET /admin/projects/{id}`
- `sort_by` — `type`, `warranty_ends_at`, `object_number`, `admin_internal_name`, `purpose`, `created_at`
- `sort_order` — `asc`, `desc`
- `page`, `size` — пагинация (по умолч. `1` / `20`, максимум `100`)

Каждый элемент содержит:
```json
{
  "id": 1,
  "type": "Вентиляционная установка",
  "object_number": "29_099",
  "purpose": "Вентиляция",
  "warranty_starts_at": "2025-01-01T00:00:00Z",
  "warranty_ends_at": "2027-01-01T00:00:00Z",
  "warranty_status": "active",
  "admin_internal_name": "ШУ-18К",
  "admin_comment": "Внутренний комментарий",
  "tags": [{ "id": 2, "name": "Электрика", "scope": "cabinet" }],
  "project_id": 3,
  "project_name": "Бизнес-центр Космос",
  "created_at": "2026-05-01T10:00:00Z"
}
```
`warranty_status`: `active`, `expiring_soon` (≤30 дней), `expired`, `none` (гарантия не указана — `warranty_starts_at`/`warranty_ends_at` оба `null`).
`warranty_starts_at`/`warranty_ends_at` в самом ШУ — `null`, если гарантия не указана.
`project_id`/`project_name` — `null`, если ШУ не привязан ни к одному проекту.

### GET `/admin/cabinets/geo`
Лёгкий endpoint для карты — возвращает **все** ШУ одним запросом без пагинации. Параметры (фильтры под легенду меток на карте):
- `warranty_status` — `active` / `expiring_soon` / `expired` / `none` (те же 4 состояния, что и в `GET /admin/cabinets`)
- `has_open_requests` — `true` / `false` — есть ли новая (открытая) сервисная заявка

Ответ (`list[CabinetGeoItem]`):
```json
[
  {
    "id": 3,
    "object_number": "29_099",
    "admin_internal_name": "Главная подстанция",
    "warranty_status": "active",
    "latitude": 53.9,
    "longitude": 27.56,
    "has_open_requests": true
  }
]
```

`warranty_status`: `active` | `expiring_soon` | `expired` | `none`.
`has_open_requests`: есть ли хотя бы одна сервисная заявка со статусом `open`.  
ШУ без координат тоже включены (`latitude`/`longitude` = `null`) — фронт фильтрует сам.

---

### GET `/admin/cabinets/{cabinet_id}`
Детальная информация о ШУ с тегами. Ответ (`CabinetOut`) включает `project_id`/`project_name` (оба `null`, если ШУ не привязан к проекту) — это единственный источник истины для отображения проекта в карточке ШУ, независимо от того, откуда её открыли (из общего списка или со страницы проекта).

`sim_id`/`sim` — см. блок про SIM-карту в описании `PATCH` ниже. `sim` **не хранится у нас** — запрашивается заново из внешнего приложения при каждом открытии карточки ШУ; если `sim_id` задан, но внешний сервис недоступен, `sim` будет `null`, а не ошибка — сама карточка ШУ всё равно откроется.

---

### PATCH `/admin/cabinets/{cabinet_id}`
Обновление данных ШУ (все поля опциональны, в т.ч. `latitude` и `longitude`). Возвращает обновлённый ШУ с тегами.

Поля под MQTT-телеметрию этого ШУ (все опциональны, см. раздел «Рут `admin: telemetry`» ниже):
- `mqtt_topic` — топик контроллера (например `"26_001/1/data"`). Уникален — попытка привязать уже занятый другим ШУ топик вернёт `409`.
- `mqtt_host` / `mqtt_port` — адрес брокера **именно этого** ШУ. Общего брокера на все объекты нет — у каждого контроллера свой.
- `mqtt_username` / `mqtt_password` — опциональные логин/пароль, если на брокере включена аутентификация. `mqtt_password` — write-only: принимается в `PATCH`, но никогда не возвращается обратно ни в одном ответе.

> **Ловушка с `mqtt_password` для фронта.** Общее правило PATCH (см. «9. PATCH-запросы») — не отправлять поле, если его не меняли, иначе `null` его сбросит. С обычными полями это заметно (в форме видно старое значение), а с `mqtt_password` — нет: `GET` никогда не отдаёт пароль обратно, поле в форме редактирования всегда будет пустым, даже если пароль на самом деле сохранён. Если при сохранении слать `mqtt_password: null`/`""` каждый раз, когда это поле пусто в форме — уже сохранённый пароль сотрётся, даже если админ просто поправил, например, комментарий. Ключ `mqtt_password` нужно включать в тело `PATCH` **только** если админ реально ввёл в это поле новое значение — как обычно делают со сменой пароля пользователя.

Пока не заполнены все три — `mqtt_host`, `mqtt_port`, `mqtt_topic` — прокси не подключится к брокеру этого ШУ вообще (см. `GET /webhooks/telemetry/targets`).

**Поле `sim_id`** — привязка ШУ к SIM-карте из отдельного стороннего приложения (`http://10.1.0.67:5000`, не наш код — управление самими SIM-картами, включая их создание/активацию, там же, у нас только связь). `null` — отвязать. Одну и ту же SIM можно привязать сразу к нескольким ШУ — уникальности здесь нет (осознанно, в отличие от `mqtt_topic` выше). Для поиска SIM при привязке — `GET /admin/sim` (см. ниже).

### PUT `/admin/cabinets/{cabinet_id}/tags`
Привязать теги к ШУ (полная замена). Только для администратора.
```json
{ "tag_ids": [1, 2] }
```
Пустой список снимает все теги. `204 No Content`.

> Рекомендуется привязывать теги со `scope="cabinet"` (на фронте — выбирать из `GET /tags?scope=cabinet`), но сервер не проверяет `scope` тега при сохранении.

---

### PATCH `/admin/cabinets/{cabinet_id}/project`
Привязать или отвязать ШУ к проекту. Только для администратора.
```json
{ "project_id": 3 }
```
Отвязка — `{ "project_id": null }`. `204 No Content`.

Единственный побочный эффект: если у проекта уже есть участники, каждый из них сразу получает доступ к привязываемому шкафу (доступ вычисляется через членство в проекте, `user_cabinets` как таковых больше нет) — без дополнительных заявок, само админское действие достаточно. Чаты по этому ШУ при этом **не** заводятся — их создаёт только сам пользователь, открыв ШУ и нажав на чат (см. `GET /cabinets/{id}/chat`). См. подробности в разделе «Рут `admin: projects`».

---

### DELETE `/admin/cabinets/{cabinet_id}`
Удаление ШУ. `204 No Content`.

**Soft-delete**: запись не стирается из БД, а помечается `deleted_at`. Удалённый ШУ:
- пропадает из `GET /admin/cabinets`, `GET /admin/cabinets/geo` и общего поиска;
- нельзя привязать через одобрение заявки на добавление по фото (`POST /admin/cabinet-requests/additions/{id}/approve` вернёт 404, даже если заявка была создана до удаления);
- не участвует в проверке истечения гарантии (warranty-уведомления не шлются);
- **все чаты этого ШУ (у всех пользователей) архивируются** (`archived_at` проставляется, событие `chat.updated` уходит каждому владельцу чата) — переписываться по удалённому ШУ становится невозможно (см. `send_message`: архивный чат отклоняет новые сообщения).

Заявки на обслуживание по удалённому ШУ не затрагиваются — данные и история сохраняются, меняется только доступность чатов.

---

### GET `/admin/cabinets/{cabinet_id}/users`
Пользователи с доступом к ШУ. Доступно оператору и админу. Это объединение двух
независимых путей доступа — участники проекта, которому принадлежит шкаф
(`added_at` в этом случае — дата вступления в проект, одинаковая у всех ШУ
этого проекта), и те, кто добавил именно этот ШУ отдельно по его собственному
QR, в обход проекта (`added_at` — дата именно этой привязки). Пользователь,
дошедший обоими путями разом, в списке один раз.
```json
[
  {
    "user_id": 1,
    "full_name": "Иванов Иван",
    "phone": "+375291234567",
    "user_type": "individual",
    "custom_name": "Мой шкаф",
    "added_at": "2026-05-12T10:00:00Z"
  }
]
```

### DELETE `/admin/cabinets/{cabinet_id}/users/{user_id}`
Отвязать ШУ, который пользователь добавил отдельно по его QR (в обход проекта).
Только для админа. Логируется в `audit_log`.
```json
{ "reason": "Причина отвязки" }
```
Ответ: `204 No Content`. Заодно архивируются чаты этого пользователя по этому ШУ
(чат ШУ и чаты заявок по нему) — чатов других пользователей это не касается.
Пользователю приходит уведомление `request_status` «Доступ к ШУ отозван»
(причина из запроса ему не показывается, она только для аудита).

- `404` — ШУ нет, либо у пользователя нет прямой привязки к нему.
- `409` — доступ к ШУ у пользователя идёт через проект: точечно из одного ШУ
  внутри проекта выйти нельзя, убирать нужно из проекта целиком — см.
  `DELETE /admin/projects/{project_id}/users/{user_id}` (раздел `admin: projects`).

### GET `/admin/sim`
Поиск/список SIM-карт во внешнем приложении управления SIM-картами — для выбора SIM при привязке к ШУ (`PATCH /admin/cabinets/{id}`, поле `sim_id`). Доступно оператору и администратору.

Параметры:
- `page`, `size` — пагинация (по умолч. `1` / `20`, максимум `100`)
- `name`, `phone`, `serial_number`, `ip` — все опциональны, поиск по подстроке (в т.ч. по `name`, хотя само название в ответе не отдаётся — см. ниже); если ни один не передан — просто постраничный список всех SIM

Ответ (`PageOut[SimInfoOut]`) — намеренно только то, что нужно показать фронту, плюс `id` (не для показа, а чтобы сослаться на конкретную SIM при привязке через `PATCH /admin/cabinets/{id}`):
```json
{
  "items": [
    {
      "id": "08de85b2-4a79-4875-856b-35140ccaede2",
      "serial_number": "1337228675242",
      "phone": "375291343223",
      "ip": "192.168.1.111",
      "sim_url": "http://10.1.0.67:3000/admin/cards"
    }
  ],
  "total": 1,
  "page": 1,
  "size": 20,
  "pages": 1
}
```
> `id` — GUID-строка (так устроено в SimApi), не число.

> **`sim_url` — не ссылка на конкретную SIM**, а на список карт целиком (`SIM_SERVICE_FRONTEND_URL` в `.env`, по умолч. `http://10.1.0.67:3000/admin/cards`). Выбор конкретной SIM в веб-интерфейсе SimApi открывает модалку без отражения в URL — deep-link на одну запись там не поддерживается. Так что клик по SIM-блоку приведёт в нужное приложение, но не сразу к нужной записи — искать её там придётся вручную.

> Это живой запрос к стороннему приложению на каждый вызов (данные у нас не хранятся и не кэшируются) — если оно недоступно, ручка отдаёт пустой список (`items: [], total: 0`), а не ошибку 5xx.

## Рут `admin: telemetry` — карта регистров и телеметрия ШУ (админ/оператор — просмотр, только админ — правка)

Аварии/сообщения с MQTT-контроллеров ШУ приходят не напрямую с ПЛК, а через
промежуточный прокси на C#, который слушает MQTT и шлёт сюда уже обычным HTTP
(см. `POST /webhooks/telemetry` в разделе «Вебхуки внешних интеграций»).
Сырые данные — пары «адрес регистра → значение»; каждое значение — 16-битное
слово, и смысл несёт не число целиком, а отдельные его биты (0-15) — каждый
бит потенциально своя авария, но не обязательно каждый бит вообще что-то
значит. Расшифровка в человекочитаемый вид делается на чтение через карту
регистров, описанную здесь: карта — это не address→название, а
**address+bit→название**.

Карта двухуровневая: **стандартная** (`RegisterDefinition`, общая для всех ШУ)
и **добавки/переопределения** на конкретный ШУ (`CabinetRegisterOverride`) —
для (адрес, бит), которых нет в стандартной карте, или чтобы для этого ШУ
конкретный бит значил что-то своё. При расшифровке сначала смотрится override,
и только если для этого ШУ и пары (адрес, бит) его нет — берётся стандартное
значение.

### GET `/admin/register-definitions`
Стандартная карта регистров целиком (без пагинации — обычно это десятки строк).
```json
[
  { "id": 1, "address": 501, "bit": 2, "name": "Авария насоса 1", "description": null,
    "created_at": "2026-08-14T00:00:00Z", "updated_at": "2026-08-14T00:00:00Z" }
]
```

### POST `/admin/register-definitions`
Только администратор.
```json
{ "address": 501, "bit": 2, "name": "Авария насоса 1", "description": null }
```
`bit` — `0..15`. Пара (`address`, `bit`) уникальна — повторное создание на
занятую пару вернёт `409`.

### PATCH `/admin/register-definitions/{definition_id}`
Только администратор. Передавать только те поля, которые нужно поменять —
как везде в проекте (см. «PATCH-запросы»).
```json
{ "name": "Авария насоса 1 (уточнено)" }
```
Можно менять и `address`/`bit` — если новая пара уже занята другой записью,
`409` (как и при создании). `description: null` сбрасывает описание.

### DELETE `/admin/register-definitions/{definition_id}`
Только администратор. `204 No Content`.

### GET `/admin/register-definitions/export`
Стандартная карта в виде `.xlsx`-файла (`admin`/`operator`) — колонки «Адрес,
Бит, Название, Описание», отсортировано по адресу и биту. Визуал (шрифты,
заливка шапки, ширина колонок) собирает сервер целиком через `openpyxl` —
фронту достаточно скачать файл по ссылке, дополнительно ничего оформлять не
нужно. `Content-Type: application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`,
`Content-Disposition: attachment; filename=register_definitions.xlsx`.

---

### GET `/admin/cabinets/{cabinet_id}/register-overrides`
Добавки/переопределения карты для конкретного ШУ.

### POST `/admin/cabinets/{cabinet_id}/register-overrides`
Только администратор.
```json
{ "address": 501, "bit": 5, "name": "Своё название для этого ШУ", "description": null }
```
Пара (`cabinet_id`, `address`, `bit`) уникальна — повтор вернёт `409`.

### PATCH `/admin/cabinets/{cabinet_id}/register-overrides/{override_id}`
Только администратор. Та же логика, что и у `PATCH .../register-definitions/{id}`
выше — частичное обновление, конфликт по (`cabinet_id`, `address`, `bit`) — `409`.

### DELETE `/admin/cabinets/{cabinet_id}/register-overrides/{override_id}`
Только администратор. `204 No Content`.

### GET `/admin/cabinets/{cabinet_id}/register-map/export`
Действующая карта ЭТОГО ШУ целиком в `.xlsx` (`admin`/`operator`) — не то же
самое, что список выше (там только сами переопределения): здесь стандартная
карта с уже применёнными override поверх, той же логикой приоритета
(override важнее). Колонки «Адрес, Бит, Название, Описание, Источник» —
последняя показывает, откуда строка: «Стандартная карта» или «Переопределено
для этого ШУ». Название листа — `admin_internal_name` ШУ, если задано, иначе
`object_number`. `404`, если ШУ не найден.

---

### GET `/admin/cabinets/{cabinet_id}/telemetry`
То же текущее состояние, что и у пользователя (`GET /cabinets/{cabinet_id}/telemetry`,
см. раздел `cabinets`), но без проверки членства в проекте — доступна оператору
и админу по одной лишь роли, для любого ШУ. Формат ответа идентичен
(`TelemetryCurrentStateOut`, без пагинации). Нужен, потому что оператор/админ,
разбирающий аварию, не обязательно сам состоит в проекте этого ШУ.

### GET `/admin/cabinets/{cabinet_id}/telemetry/history`
**Сырая история сообщений** — в отличие от эндпоинта выше (текущее состояние,
одна строка на бит), здесь каждое входящее MQTT-сообщение — своя запись,
для разбора задним числом ("когда началась авария", "что было до и после").
Только оператор/админ, без проверки членства в проекте. Пагинация — `page`/`size`
(как везде, см. «PATCH-запросы» → `PageOut`).
```json
{
  "items": [
    {
      "id": 42,
      "received_at": "2026-08-13T10:00:00Z",
      "registers": [
        { "address": 501, "bit": 2, "name": "Авария насоса 1", "value": 1 }
      ]
    }
  ],
  "total": 6, "page": 1, "size": 20, "pages": 1
}
```
`value` здесь — состояние самого бита (`0` или `1`), не сырое число регистра.
Фильтрация та же, что и у основной ленты: по умолчанию
(`include_unnamed=false`) в ответ попадают только биты, которые взведены
(`value: 1`) **и** названы в карте — сообщения, где таких бит не нашлось,
в ответе не появляются вообще; `total`/`pages` считаются по сырым событиям в
БД, до фильтрации — реально показанных элементов на странице может быть
меньше `size`. `include_unnamed=true` — показать все 16 бит каждого регистра
как есть (взведён/нет, назван или нет) — нужно для настройки самой карты.

> **Хранится не вечно.** Старше `TELEMETRY_HISTORY_RETENTION_DAYS` (по умолчанию
> 14 дней) удаляется фоновой задачей раз в сутки. Текущее состояние
> (`GET /admin/cabinets/{cabinet_id}/telemetry` выше) от этого не зависит — оно
> не история, а один снимок "что сейчас", не растёт и не чистится по возрасту.

## Рут `admin: cabinet requests` — заявки по ШУ (просмотр — оператор/админ, одобрение/отклонение — только админ)

> **Заявок на доступ к отдельному ШУ (`.../shares`) нет.** Доступ не
> эксклюзивен ни на уровне шкафа, ни на уровне проекта — сколько угодно
> пользователей получает его сразу, без чьего-либо одобрения: либо вступлением
> в проект (`POST /projects/add-by-qr`), либо напрямую по QR самого ШУ
> (`POST /cabinets/add-by-qr`), см. разделы `projects` и `cabinets` ниже.
> Здесь, в `admin: cabinet requests`, речь о другом — ШУ, которого в системе
> ещё вообще нет (новое оборудование, которое надо завести).

### GET `/admin/cabinet-requests/additions`
Заявки на добавление ШУ через фото — теперь означают "в моём проекте не
хватает шкафа, вот фото", а не "дайте мне доступ к неизвестному ШУ": заявитель
уже должен состоять в указанном `project_id` на момент подачи. Параметры:
- `status` — `pending` / `approved` / `rejected`
- `resolved_by_admin_id` — заявки, обработанные конкретным администратором
- `search` — поиск по ФИО, телефону, организации пользователя, комментарию пользователя и ответу администратора
- `sort_by` — `created_at` (по умолч.), `resolved_at`, `status`, `user_full_name`
- `sort_order` — `asc` / `desc`
- `page`, `size`

```json
{
  "items": [
    {
      "id": 1,
      "user_id": 8,
      "user_full_name": "Иванов Иван",
      "user_phone": "+375291234567",
      "user_type": "individual",
      "organization_name": null,
      "user_is_verified": false,
      "user_registered_at": "2026-04-01T10:00:00Z",
      "project_id": 3,
      "project_name": "Бизнес-центр Космос",
      "photo_url": "/static/photos/abc.jpg",
      "user_comment": "Шкаф на заводе",
      "status": "pending",
      "cabinet_id": null,
      "admin_response": null,
      "resolved_by_admin_id": null,
      "created_at": "2026-05-12T08:00:00Z",
      "resolved_at": null
    }
  ],
  "total": 1, "page": 1, "size": 20, "pages": 1
}
```
`cabinet_id` — `null` пока заявка не одобрена. `project_id`/`project_name` —
`null` у старых заявок, поданных до перехода на проектную модель.

---

### POST `/admin/cabinet-requests/additions/{request_id}/approve`
Одобрение заявки: администратор находит по фото подходящий ШУ (уже существующий
в системе — заведённый заранее через `POST /admin/cabinets`, либо ничейный/не
в том проекте) и указывает его ID.
```json
{
  "cabinet_id": 5,
  "admin_response": "Шкаф добавлен"
}
```
Ответ: `204 No Content`.

Если у заявки указан `project_id`, этим же действием чинится и принадлежность
шкафа:
- ШУ ничей (`project_id IS NULL`) → привязывается к проекту заявки, все
  участники проекта сразу получают доступ (чат по этому ШУ при этом не
  заводится никому — заводит только сам пользователь, открыв ШУ и нажав на
  чат, см. `GET /cabinets/{id}/chat`);
- ШУ уже принадлежит **другому** проекту → `409`, сначала отвязать вручную
  (`PATCH /admin/cabinets/{id}/project`);
- ШУ уже в этом же проекте → ничего не меняется, просто фиксируется
  `cabinet_id` в заявке.

---

### POST `/admin/cabinet-requests/additions/{request_id}/reject`
Отклонение заявки.
```json
{ "admin_response": "Фото нечёткое, повторите попытку" }
```
Ответ: `204 No Content`.

## Рут `admin: users` — управление пользователями (админ/оператор)

> Список **не показывает** пользователей с ролями `admin` и `bot` (системные аккаунты). Только `user` и `operator`.

### POST `/admin/users/admins`
Создать администратора. Только для **суперадмина**. Логируется в `audit_log`.
```json
{
  "login": "admin2",
  "password": "securePass8",
  "full_name": "Сидоров Сидор"
}
```
Ответ: созданный пользователь (`AdminUserListOut`), `201 Created`.

---

### POST `/admin/users/operators`
Создать оператора. Только для администратора. Логируется в `audit_log`.
```json
{
  "login": "operator2",
  "password": "securePass8",
  "full_name": "Иванов Иван"
}
```
- `login` — минимум 3 символа, без пробелов, приводится к нижнему регистру, должен быть уникальным
- `password` — минимум 8 символов
- `full_name` — необязателен

Ответ: созданный пользователь (`AdminUserListOut`), `201 Created`.

> Создание **администратора** — через API (только суперадмин) или CLI:
> ```bash
> docker exec savt-backend-api-1 python -m app.cli create-admin <login> <password> [full_name]
> ```

---

### DELETE `/admin/users/operators/{user_id}`
Удалить оператора. Только для администратора. Логируется в `audit_log`.

Что происходит:
- Все сессии оператора немедленно отзываются (принудительный logout)
- Аккаунт деактивируется и анонимизируется
- Переписка в чатах сохраняется
- Оператор исчезает из всех списков

Ответ: `204 No Content`.

---

### GET `/admin/users`
Только пользователи (`role=user`). Параметры:
- `search` — поиск по ФИО, телефону, логину, email, организации
- `is_active` — `true` / `false`
- `is_verified` — `true` / `false` — верификация аккаунта администратором
- `is_phone_verified` — `true` / `false` — подтверждённый номер телефона
- `user_type` — `individual` / `organization`
- `sort_by` — `created_at` (по умолч.), `full_name`, `phone`, `email`, `login`, `organization_name`, `role`
- `sort_order` — `asc` / `desc`
- `page`, `size` — пагинация (по умолч. `page=1`, `size=20`, максимум `100`)

---

### GET `/admin/operators`
Только операторы (`role=operator`). Параметры: аналогично `/admin/users` (без значения `role` в `sort_by`), включая `is_verified` и `is_phone_verified`.

> **Служебные учётки в списках не показываются.** Это учётная запись бота «Ася» и
> учётная запись интеграции с Bitrix, от лица которой в чаты заявок попадают
> комментарии из задач. Вторая заведена с ролью `operator` намеренно — иначе
> `ChatService` не пустил бы её в чужой чат заявки, — и до недавнего времени
> висела в списке операторов под именем «Ася», хотя сотрудником не является и
> управлять ею нельзя. Обе скрыты по логину (см. `SYSTEM_USER_LOGINS`).

### GET `/admin/admins`
Только администраторы (`role=admin`). **Только для суперадмина.** Параметры: аналогично `/admin/users` (без значения `role` в `sort_by`), включая `is_verified` и `is_phone_verified`.

Детальная информация об администраторе. **Только для суперадмина.**

Создать администратора (короткий alias для `POST /admin/users/admins`). **Только для суперадмина.**

### DELETE `/admin/admins/{user_id}`
Удалить администратора. **Только для суперадмина.** Логируется в `audit_log`
(`user.delete_admin`).

Механика та же, что у удаления оператора: сессии немедленно отзываются, аккаунт
деактивируется и обезличивается, но **из базы не стирается** — на него ссылаются
журнал действий и обработанные заявки (`resolved_by_admin_id`). Переписка в чатах
сохраняется, из всех списков администратор исчезает.

- `403` — попытка удалить собственную учётную запись
- `403` — цель не администратор (операторов удаляют через `/admin/users/operators/{id}`,

  удаление легко оставило бы систему без владельца)
- `404` — пользователь не найден

## Рут `cabinets` — ШУ пользователя

Доступ к ШУ даёт любой из двух независимых путей: членство в проекте, которому
принадлежит шкаф (`Cabinet.project_id` + `UserProject`, см. «Рут `projects`»
ниже — даёт доступ сразу ко всем шкафам проекта разом), либо прямая привязка
к этому конкретному ШУ в обход проекта (`UserCabinet`, заводится через
`POST /cabinets/add-by-qr` ниже, по собственному QR-коду ШУ). Пользователь
может дойти до одного и того же ШУ обоими путями по отдельности, но не разом —
если доступ уже есть через проект, прямая привязка не создаётся и не нужна
(см. `POST /cabinets/add-by-qr`).

Выйти из проекта можно только целиком — `DELETE /projects/{project_id}` —
отдельной ручки выхода для одного ШУ внутри проекта нет. Прямую привязку к ШУ
(`UserCabinet`) можно снять отдельно — `DELETE /cabinets/{cabinet_id}` ниже.

### POST `/cabinets/{cabinet_id}/pin` и DELETE `/cabinets/{cabinet_id}/pin`
Закрепить ШУ наверху своего списка / открепить. `204 No Content`. Закрепление
личное — у других пользователей того же проекта шкаф остаётся на своём месте.
Работает и для ШУ из проекта, и для добавленных отдельно. `404`, если у
пользователя нет доступа к ШУ. `is_pinned` приходит в `GET /cabinets` и
`GET /cabinets/{cabinet_id}`.

### DELETE `/cabinets/{cabinet_id}`
Убрать ШУ, который пользователь сам добавил по его QR (`POST /cabinets/add-by-qr`).
`204 No Content`. Заодно архивируются чаты пользователя по этому ШУ (чат ШУ и
чаты заявок по нему) — иначе он мог бы продолжать писать в уже открытые чаты,
хоть доступа больше нет.

- `404` — у пользователя нет такого ШУ.
- `409` — ШУ доступен ему через проект: убрать его отсюда нельзя, только выйдя
  из проекта целиком (`DELETE /projects/{project_id}`).

---

### POST `/cabinets/add-by-qr`
Добавить ШУ напрямую по его собственному QR-коду, в обход проекта.
```json
{ "qr_data": "savt://cabinet/AbCdEf123456" }
```
`qr_data` — то, что реально считал сканер: либо `savt://cabinet/{код}` (скан
внутри приложения), либо адрес публичной страницы вида
`https://.../add/cabinet/{код}` (скан обычной камерой телефона — см. раздел
`qr` ниже), либо голый код. Код всегда достаётся из последнего сегмента,
независимо от формата.
```json
{ "status": "linked", "message": "ШУ успешно добавлен" }
```
`404` — код не найден. `409` — доступ к этому ШУ уже есть (неважно каким
путём: раньше добавлен так же напрямую, или достаётся через проект, в котором
пользователь уже состоит) — повторной привязки не происходит.

> Если позже пользователь добавит проект, которому принадлежит этот же ШУ
> (`POST /projects/add-by-qr`) — прямая привязка (`UserCabinet`) автоматически
> снимается, доступ дальше идёт только через членство в проекте. Чат ШУ и вся
> история по нему (сервисные заявки, рекламации) никуда не переносятся и не
> теряются — они привязаны к самому ШУ, а не к пути доступа. Пользователю
> приходит уведомление о переносе.

---

### POST `/cabinets/add-by-photo`
Заявка на добавление ШУ через фото (предварительно загрузить через `/upload/attachment`).
Не "дайте мне доступ к неизвестному ШУ", а "в моём проекте не хватает шкафа, вот
фото" — заявитель должен уже состоять в указанном `project_id`.
```json
{
  "project_id": 3,
  "photo_url": "/static/photos/abc123.jpg",
  "user_comment": "Шкаф на заводе, цех 3"
}
```
Ответ:
```json
{
  "request_id": 1,
  "message": "Заявка отправлена на рассмотрение"
}
```
`403` — пользователь не состоит в указанном проекте.

При одобрении (`POST /admin/cabinet-requests/additions/{id}/approve`) админ
находит подходящий ШУ; если он ничей — админское действие само привязывает его
к `project_id` заявки, и весь проект сразу получает доступ, без отдельных
шагов (см. раздел `admin: cabinet requests`).

> Пока предыдущая заявка пользователя не рассмотрена, повторный вызов отвечает
> `409` («уже есть необработанная заявка») — так же трактовать как
> «уже синхронизировано» в оффлайн-очереди. Отдельного `client_token` здесь
> нет: после того как заявку одобрят/отклонят, эта защита снимается, и очень
> позднему ретраю (клиент был оффлайн дольше, чем админ рассматривал заявку)
> в теории может создать вторую — на практике окно слишком узкое, чтобы того
> стоила отдельная миграция схемы.

### GET `/cabinets/{cabinet_id}/telemetry`
**Текущее состояние** регистров ШУ — то, что показывается в подробностях ШУ.
Значение каждого регистра — 16-битное слово, смысл несут отдельные биты (0-15),
не число целиком (см. «Рут `admin: telemetry`»): каждый бит — потенциальная
авария, названная в карте регистров. Новое сообщение с контроллера
**перезаписывает** значение своего адреса целиком (все 16 бит разом), а не
добавляет новую запись в ленту — не история и не растёт бесконечно. Без
пагинации. Та же проверка доступа, что и у остальных эндпоинтов ШУ (`403`,
если пользователь не состоит в проекте этого ШУ).

**По умолчанию (`include_unnamed=false`) в ответ попадают только те биты,
которые СЕЙЧАС взведены (`value: 1`) И названы в карте** — то есть реально
активные аварии. Контроллер обычно шлёт ~20 регистров по 16 бит каждый, и без
фильтра аварию в этом шуме не найти.
```json
{
  "registers": [
    { "address": 501, "bit": 2, "name": "Авария насоса 1", "value": 1, "updated_at": "2026-08-14T10:00:00Z" }
  ]
}
```
Как только бит сбрасывается в `0` (авария ушла) или гаснет — он пропадает из
этого ответа сам (не приходит отдельным событием "авария снята", просто
перестаёт быть в списке при следующем запросе/пуше).

> У каждой строки свой `updated_at` — наследуется от времени последнего
> сообщения по этому адресу; разные регистры обновляются с разной частотой.

`include_unnamed=true` — показать все 16 бит каждого регистра как есть,
включая взведённые в `0` и без названия (`name: null`). Нужно для настройки
самой карты — чтобы понять, что означает ещё не названный бит, его сначала
нужно увидеть меняющимся.

> Сырая история сообщений (та же расшифровка по битам) доступна отдельно —
> `GET /admin/cabinets/{cabinet_id}/telemetry/history`, только админу/оператору,
> см. «Рут `admin: telemetry`».

## Рут `projects` — проекты пользователя

Проект — группа шкафов с общим QR-кодом. Сколько угодно пользователей состоит в
одном проекте разом, без очередности и без чьего-либо одобрения — отсканировал
QR, сразу внутри. Доступ ко всем шкафам проекта у всех участников одинаковый —
в отличие от самого проекта, у отдельного шкафа внутри него владения/
эксклюзивности нет.

### GET `/projects`
Список проектов текущего пользователя.
```json
[
  {
    "project_id": 3, "name": "Бизнес-центр Космос", "is_pinned": true,
    "cabinet_count": 5, "company_name": "ООО Ромашка", "warranty_status": "active"
  }
]
```
`cabinet_count` — сколько шкафов вообще привязано к проекту. Доступ к шкафам не
хранится по-шкафно — раз пользователь состоит в проекте (есть в списке `GET /projects`),
у него есть доступ ко всем этим шкафам, без исключений.
`warranty_status` — `active` / `expiring_soon` (≤30 дней) / `expired` / `none` (гарантия не задана).
`is_pinned` — закреплён ли проект пользователем наверх списка, см. `POST /projects/{id}/pin`
ниже. Сортировка списка уже учитывает закреп — закреплённые проекты всегда идут
первыми, дополнительно сортировать на клиенте не нужно.

---

### GET `/projects/{project_id}`
Подробности проекта — `cabinets` содержит **все** шкафы проекта (не только часть:
доступ к ним у участника проекта одинаковый и не выбирается по-шкафно, см. врезку
выше про добавление проекта).
```json
{
  "project_id": 3,
  "name": "Бизнес-центр Космос",
  "is_pinned": true,
  "cabinets": [
    { "id": 5, "type": "Вентиляционная установка", "object_number": "29_099", "admin_internal_name": "ШУ-18К" }
  ],
  "company_name": "ООО Ромашка",
  "shipment_planned_at": "2026-08-24T12:26:00+03:00",
  "shipment_actual_at": null,
  "warranty_starts_at": "2026-08-24T00:00:00Z",
  "warranty_ends_at": "2028-08-24T00:00:00Z",
  "warranty_status": "active"
}
```

Компания и даты отгрузки приезжают из сделки Bitrix, гарантию ставит администратор
(см. «Поля сделки в карточке проекта»). `shipment_actual_at` заполняется по факту
отгрузки — пока её нет, показывайте `shipment_planned_at` как ожидаемую.

> **Контактных лиц заказчика здесь нет и не будет** — это персональные данные, а
> доступ к проекту выдаётся по QR-коду. Они отдаются только в админских ответах.

---

### POST `/projects/add-by-qr`
Привязка проекта через QR-код — сразу, без чьего-либо одобрения.
```json
{ "qr_data": "savt://project/A3F7BC1254E8D9F0" }
```
`qr_data` — то, что реально считал сканер: либо `savt://project/{код}` (скан
внутри приложения), либо адрес публичной страницы вида
`https://.../add/project/{код}` (скан обычной камерой телефона — см. раздел
`qr` ниже), либо голый код. Код всегда достаётся из последнего сегмента,
независимо от формата.

Логика:
- Проект не найден → `404`
- Уже привязан → `409`
- Иначе — мгновенная привязка (`status: "linked"`), доступ ко **всем** шкафам
  проекта появляется сразу же самим членством.

Ответ:
```json
{ "status": "linked", "message": "Проект успешно привязан" }
```

> Фронту стоит обновить и `GET /cabinets` после ответа — в аккаунт могли
> добавиться новые шкафы, помимо самого проекта.

Заодно сразу заводится чат проекта (см. `GET /projects/{id}/chat` в разделе
`projects` мобильного гайда) — чаты самих ШУ при этом не трогаются, они
по-прежнему заводятся только пользователем вручную.

> **Слияние с ранее добавленными ШУ.** Если среди шкафов этого проекта есть
> такие, которые пользователь уже добавлял отдельно по собственному QR ШУ
> (`POST /cabinets/add-by-qr`) — эта прямая привязка автоматически снимается,
> доступ к ним дальше идёт через членство в проекте. Чат и история по этим ШУ
> не переносятся и не теряются — остаются как были. Приходит уведомление
> (`request_status`) о каждом перенесённом ШУ.

---

### DELETE `/projects/{project_id}`
Покинуть проект. `204 No Content`. Теряет доступ **разом ко всем** шкафам этого
проекта — точечно выйти из одного ШУ нельзя (см. врезку в начале раздела
`cabinets` выше).

Заодно **архивируются чаты этого пользователя** по проекту и по его шкафам (и
их заявкам) — иначе он мог бы продолжать писать в уже открытые чаты, хоть
доступа к проекту у него больше нет. Чатов остальных участников проекта это
не касается.

Если проект был закреплён (см. ниже) — закреп пропадает вместе с выходом
автоматически, отдельно откреплять не нужно.

## Рут `admin: projects` — управление проектами (только админ)

> **Ручного создания проекта больше нет.** `POST /admin/projects` убран — проект
> заводится **только** сделкой Bitrix (`ONCRMDEALADD`/`ONCRMDEALUPDATE`, см.
> `bitrix_webhook_service.upsert_project_from_deal`, либо разовый импорт
> `app/cli.py import-bitrix-deals`). Переименование сделки в Bitrix переименовывает
> и проект — `name` больше не принимается и через `PATCH` (см. ниже).
>
> **Удаление в приложении не окончательно, пока жива сделка.** `DELETE
> /admin/projects/{id}` — soft-delete как обычно, но если по этому же
> `production_number` позже прилетит `ONCRMDEALUPDATE` (почти любое изменение
> сделки), проект **воскрешается** автоматически: `deleted_at` снимается, папка
> пересинхронизируется. Привязки пользователей (`user_projects`) нигде не
> терялись — их soft-delete проекта не трогает, так что доступ участников
> восстанавливается вместе с проектом.
>
> **Шкафы и чаты — нет.** Удаление проекта каскадно удаляет (тем же soft-delete)
> его ШУ и архивирует их чаты и чаты самого проекта (см. `DELETE
> /admin/projects/{project_id}` ниже) — это **не** отменяется автоматически при
> воскрешении: `deleted_at` снимается только с самого проекта. Если проект
> воскрес, а его шкафы нужны обратно — их придётся восстановить/переподвязать
> вручную (администратор per-ШУ функционала восстановления сейчас не имеет —
> обратитесь к БД или обсудите отдельный эндпоинт, если это станет частым
> сценарием).
>
> Единственный способ удалить проект насовсем — закрыть/удалить и саму сделку в
> Bitrix (после чего в приложении её уже никто не тронет — обратной синхронизации
> удаления из Bitrix нет, см. ниже).
>
> **Пока проект в удалённом состоянии, участнику он не виден** — `UserProjectRepository.list_for_user`/`get_with_project`
> (используются `GET /projects` и `GET /projects/{id}`) фильтруют `deleted_at`
> так же, как и админский список. Строки `user_projects` при этом не трогаются
> (см. выше) — как только проект воскреснет, доступ участника вернётся сам,
> без повторного приглашения. До этого фикса фильтра не было: soft-delete
> убирал проект из `GET /admin/projects`, но не из `GET /projects` того, кто
> в нём состоял — участник продолжал видеть «удалённый» для админов проект
> (уже без шкафов — их soft-delete удаляет по-настоящему).

При создании (в том числе через Bitrix-вебхук) сервер автоматически заводит на NAS (если настроен `PROJECT_FOLDERS_ROOT`, см. переменные окружения) папку с шаблонной структурой — внутри **годовой папки**, как разложено в Bitrix:
```
📁 !2026/                             ← год проекта; в корне лежат только такие папки
└── 📁 Название_проекта/              ← корень проекта, основная документация
    ├── 📁 _Проект/                   ← схемы, ТЗ на сборку — только проектный уровень
    ├── 📁 _Программа/                ← ПО, сетевые настройки — только проектный уровень
    │   ├── 📁 SCADA/
    │   ├── 📁 ПЛК/
    │   └── 📁 HMI/
    ├── 📁 _Маркировка/
    │   ├── 🖼️ QR.png                 ← QR-код проекта (адрес публичной страницы /add/project/{unique_code}), для печати и наклейки на объект
    │   └── 📁 {ШУ}/                  ← появляется, когда шкаф привязан к проекту
    │       ├── 📁 Облако/
    │       ├── 📁 Coral/
    │       └── 📁 Wago/
    ├── 📁 _Руководство/               ← документы проекта — прямо здесь, документы ШУ — в подпапке
    │   └── 📁 {ШУ}/                  ← появляется, когда шкаф привязан к проекту
    ├── 📁 Фото/                      ← фото проекта — прямо здесь, фото шкафа — в подпапке
    │   └── 📁 {ШУ}/
    ├── 📁 _Доп.информация/           ← только проектный уровень
    └── 📁 Переписка/                 ← переписка проекта — прямо здесь, переписка по шкафу — в подпапке
        └── 📁 {ШУ}/
```

**Единой папки-дубликата шаблона на ШУ нет** — раньше у каждого шкафа была своя
папка с полной копией всей структуры, теперь его подпапки разбросаны по четырём
категориям (`_Маркировка`, `_Руководство`, `Фото`, `Переписка`), по одной штуке в
каждой, с именем шкафа (`{ШУ}`, например «29_099 ШУ-18К»). `_Проект`, `_Программа`
и `_Доп.информация` подпапок по ШУ никогда не получают — это общее пространство на
весь проект. Пока в проекте нет ни одного шкафа, все четыре категории пустуют.

> **Миграция со старой схемы — только вручную, автоматики нет.** До этого редизайна
> `Coral`/`Облако`/`Wago` создавались **в корне** `_Маркировка` (на уровне всего
> проекта), а не внутри `_Маркировка/{ШУ}`. У проектов, папка которых уже была
> создана до перехода, эти три папки в корне `_Маркировка` остаются лежать как
> есть — синхронизация только досоздаёт недостающее по новому шаблону
> (`_ensure_structure`/`_ensure_cabinet_structure`), но ничего не удаляет и не
> переносит. Если внутри уже что-то лежит по старой схеме — переносить в
> `_Маркировка/{ШУ}/...` и убирать пустые папки-остатки нужно руками.

**Год берётся из производственного номера**: `26_170` → `!2026`, `25_003` → `!2025`. У проектов без номера (сейчас это только исторические записи, заведённые ещё когда ручное создание существовало) берётся год создания записи, чтобы в корне не появлялось исключений и он оставался только из годовых папок. Восклицательный знак — чтобы годовые папки всплывали над остальным при сортировке по имени.

> **В самом имени папки проекта год не дублируется.** Название сделки в
> Bitrix обычно начинается с того же префикса («`26_170 Промжилстрой`») — раз
> он и так есть в годовой папке уровнем выше, при формировании имени папки
> проекта (`sanitize_folder_name` + `_strip_year_prefix`) он отрезается:
> `26_170 Промжилстрой` → `170 Промжилстрой`. Отрезается только сам префикс
> (ровно две цифры и `_` в самом начале) — если номера нет, дефис вместо
> подчёркивания или год не двузначный, название остаётся как есть.

Вложенный проект (`parent_project_id` задан) получает свою полную папку-шаблон **внутри** папки родителя, а не отдельной папкой верхнего уровня. Годовую папку ему определяет **корень ветки**: даже если номера разошлись, вложенный проект не уезжает в другой год отдельно от родителя.

Создание папки — фоновая, best-effort операция: сбой сети/NAS не роняет создание проекта, недостающее досоздаст ближайший ночной прогон синхронизации (см. ниже), включая сам файл `QR.png`, если он был случайно удалён с диска.

> **Переезд существующих папок.** Проекты, заведённые до появления годовых папок, лежат плоско в корне. Их папки переезжают сами — на ближайшей ночной сверке или по кнопке `POST /admin/projects/{id}/sync-folder`. В пределах одной шары это переименование: запись каталога перемещается, файлы не копируются, ссылки внутри не рвутся. Переименование проекта и переезд выполняются **одним** движением, иначе переименованный до переезда проект не нашёлся бы ни по старому пути, ни по новому.
>
> На проекты с истёкшей гарантией ограничение `is_sync_eligible` **не распространяется**: сверка им не нужна, но папка всё равно переедет в свою годовую — иначе основная часть архива навсегда осталась бы в корне. Пустых папок при этом не создаётся: нет папки на диске — нечего и переносить.
>
> Единственный случай, когда перенос не делается автоматически: **два активных проекта с одинаковым `folder_name`**. По имени не определить, чья папка в корне, и достаться она могла бы любому — вместе с чужими файлами. Такой проект пропускается с `WARNING` в логе, папку переносят руками.

### GET `/admin/projects`
Список всех проектов. Доступно оператору и администратору.

**Поиск** — `search`. Ищет по карточке проекта и по контактным лицам заказчика: название, производственный номер, компания, ФИО и должность контакта, его телефоны и почты. Нечёткий (`pg_trgm`), как и остальные поиски в проекте: опечатки и разные разделители переживает.

> **На запросах короче 4 символов нечёткость (`similarity`) отключается** —
> остаётся только точное вхождение подстроки (см. `fuzzy_condition` в
> `app/utils/db.py`, общая для всех поисков в проекте). У совсем коротких
> строк вроде «100» триграмм почти нет, и стандартный порог pg_trgm (0.3)
> почти всегда перепрыгивается чем попало — запрос «100» находил случайные
> совпадения по номеру телефона контакта вместо ожидаемого проекта.

**Пока указан `search`, выдача сортируется по релевантности** (`app/utils/db.py`
→ `match_score`), а не по `sort_by` — тот решает порядок только между
одинаково релевантными строками, не перебивает саму релевантность. Уровни
совпадения по каждому полю: точное (вес × 1.0) → с начала строки (× 0.8) →
подстрокой (× 0.5) → нечёткое, только если запрос ≥ 4 символов (× 0.2). Поля
взвешены не поровну — у проекта берётся максимум из:
```
name / production_number   × 1.0
company_name                × 0.6
контакты (ФИО, телефон...)  × 0.3
```
То есть на «100» проект с таким номером в названии/`production_number` встанет
выше проекта, у которого «100» просто затесалось в номере телефона контакта.
Без `search` (список без запроса) релевантность не считается вовсе, сортировка —
чисто по `sort_by`.

> **Под все поисковые колонки заведены GIN-индексы** (`pg_trgm`, миграция
> `d3f8b2c6a915`) — по выражению `normalize_search_text(колонка)`, ровно тому
> же, что строит сам поиск. До этой миграции ни у одного из 8 мест, где
> используется `fuzzy_condition`/`match_score` (проекты, ШУ, заявки,
> документы, FAQ, БЗ, пользователи), индекса не было вовсе — каждый поиск был
> последовательным сканированием таблицы целиком; на небольшом объёме данных
> незаметно, дальше — деградирует линейно с ростом таблицы.

**Фильтры по самому проекту:**

| Параметр | Что отбирает |
|---|---|
| `year` | год проекта: из производственного номера (`26_170` → 2026), у заведённых вручную — по дате создания. Тот же год, по которому разложены папки на NAS |
| `company` | компания-заказчик (нечётко) |
| `shipped` | `true` — отгружённые (заполнена фактическая дата), `false` — ещё нет |
| `shipment_planned_from` / `shipment_planned_to` | диапазон плановой даты отгрузки |
| `shipment_actual_from` / `shipment_actual_to` | диапазон фактической даты отгрузки |
| | *формат — календарная дата `YYYY-MM-DD`, ровно то, что даёт `input[type=date]`. Обе границы **включающие**: `...to=2026-08-15` забирает весь день 15-го. Время не принимается — сутки трактуются по UTC* |
| `has_project_documents` | есть ли документы, привязанные к проекту напрямую (не к его ШУ) |
| `has_project_photos` | есть ли фотографии проекта |
| `has_project_users` | есть ли участники проекта |
| `has_contacts` | подтянулись ли из сделки контактные лица |
| `warranty_status` | по гарантии **самого проекта**: `active` / `expiring_soon` (≤30 дней) / `expired` / `none` |

**Фильтры по шкафам проекта** — проект попадает в выдачу, если условиям соответствует **хотя бы один** его шкаф: `tag_ids`, `has_documents`, `has_photos`, `has_users`, `has_service_requests`, `cabinet_warranty_status` (те же, что в `GET /admin/cabinets`).

Заданные вместе, оба набора складываются по И: `?year=2026&has_service_requests=true` — проекты 2026 года, у которых хотя бы по одному шкафу заводили заявку.

> **Изменение поведения.** Раньше `warranty_status` фильтровал по гарантии **шкафов**, хотя одноимённое поле в ответе показывало гарантию **проекта** — фильтр и колонка расходились. Теперь `warranty_status` относится к проекту и совпадает с тем, что видно в списке, а прежнее поведение доступно как `cabinet_warranty_status`.

**Сортировка** — `sort_by`: `name`, `created_at` (по умолч.), `production_number`, `year`, `company_name`, `shipment_planned_at`, `shipment_actual_at`, `warranty_ends_at`, `cabinet_count`. `sort_order` — `asc` / `desc`.

> Сортировка **всегда по полям проекта** — эндпоинт возвращает проекты, а не шкафы, поэтому строку упорядочить больше нечем. В частности `warranty_ends_at` — это гарантия самого проекта и при включённом `cabinet_warranty_status` тоже: фильтр отбирает проекты по шкафам, но сортируются отобранные всё равно по своей гарантии. У проекта много шкафов с разными датами, одной «гарантии по шкафам» у строки просто нет. Пустые значения всегда уходят в конец в обе стороны: проект без даты отгрузки не занимает верх списка, отсортированного по ней. При равных значениях порядок стабильный (по `id`), поэтому строки не «прыгают» между страницами.

`page`, `size` — постранично.

```json
{
  "items": [
    {
      "id": 3, "name": "Бизнес-центр Космос", "unique_code": "A3F7BC1254E8D9F0",
      "production_number": "26_170", "year": 2026,
      "cabinet_count": 5, "created_at": "2026-05-01T10:00:00Z",
      "company_name": "ООО Ромашка",
      "shipment_planned_at": "2026-08-15T00:00:00Z",
      "shipment_actual_at": null,
      "warranty_ends_at": "2028-08-24T00:00:00Z",
      "warranty_status": "active"
    }
  ],
  "total": 1, "page": 1, "size": 20, "pages": 1
}
```
`cabinet_count` — общее число шкафов в проекте, **не зависит** от переданных фильтров (фильтры влияют только на то, попадёт ли сам проект в выдачу).
`year` считается по тому же правилу, что и годовая папка на NAS, — фильтр, выдача и раскладка на диске не расходятся.

### GET `/admin/projects/{project_id}`
Подробности проекта (без ограничений по владению — админский вид). Параметры:
- `tag_ids`, `has_documents`, `has_photos`, `has_users`, `has_service_requests`, `warranty_status` — те же фильтры, что и в `GET /admin/cabinets` — но здесь фильтруют, какие шкафы попадут в поле `cabinets` ответа (сам проект находится всегда по ID, независимо от фильтров)

```json
    {
```

`cabinets` — уже отфильтрован сервером переданными параметрами (без параметров — все шкафы проекта).

сделки — исчезнет и здесь.

**Наше, редактируется:** `warranty_starts_at`, `warranty_ends_at` — см. `PATCH` ниже.

### POST `/admin/projects/{project_id}/sync-folder`
Синхронизировать папку проекта на NAS прямо сейчас — то же, что делает ночной прогон,
но по кнопке. Доступно оператору и администратору.

Ответ — `SyncFolderResultOut`, **не** `ProjectOut`: кнопку нажимают, чтобы узнать, что
именно сделалось, а карточка проекта от сверки не меняется. `message` — готовая фраза
для тоста, собрана на сервере, чтобы клиенты не составляли её каждый по-своему.

```json
{ "synced_at": "2026-08-03T14:22:00Z", "imported_documents": 2,
  "message": "Подхвачено новых файлов из папки: 2" }
```

Что делает: досоздаёт недостающие подпапки шаблона, переименовывает корневую папку
если разошлось название, переносит её в годовую папку если она ещё в корне,
докладывает зеркала документов и фото — и **подхватывает файлы, положенные в папку
напрямую** (документы из «_Руководство», фото из подпапки «Фото» — см. ниже).

В отличие от ночного прогона **не смотрит на гарантию**: раз администратор нажал
кнопку осознанно, синхронизируется даже проект с истёкшей гарантией.

`404` — проект не найден либо не настроен `PROJECT_FOLDERS_ROOT`.

#### Что оказывается в папке проекта

Синхронизация раскладывает по шаблонным подпапкам не только документы:

```
!2026/170 Промжилстрой/
  _Проект/  _Программа/  _Доп.информация/
  Фото/
    001 Фасад щита.jpg           ← фотографии проекта, номер держит порядок
    002 Фото 2.jpg
    003 Со стройки.jpg           ← или подхвачено обратно с диска (см. ниже)
    29_099 ШУ-18К/               ← подпапка шкафа — только его фотографии
      001 Щит в сборе.jpg
  Переписка/
    Чат проекта — Иванов Иван.txt
    вложения/
      2_Схема.pdf                ← префикс = id сообщения
    29_099 ШУ-18К/               ← подпапка шкафа — только его переписка
      Чат ШУ — Иванов Иван.txt
      Заявка 12 — Иванов Иван.txt
  _Маркировка/
    QR.png
    29_099 ШУ-18К/
      Облако/  Coral/  Wago/
  _Руководство/
    Схема проекта.pdf            ← документы проекта (Document.project_id)
    29_099 ШУ-18К/
      Паспорт ШУ.pdf             ← документы этого ШУ (Document.cabinet_id)
```

**Подпапки шкафа** — по одной внутри `Фото`, `Переписка`, `_Маркировка` и
`_Руководство` (имя как у шкафа, например «29_099 ШУ-18К») — заводятся сразу при
привязке шкафа к проекту (`PATCH /admin/cabinets/{id}/project`) и досоздаются на
каждой синхронизации. `_Проект`, `_Программа` и `_Доп.информация` подпапок по
шкафу не получают — это общее пространство на весь проект. При отвязке или
переносе шкафа в другой проект старые подпапки **не переносятся и не удаляются** —
в них могут лежать файлы, положенные вручную; новые просто создаются на новом
месте. Так же, как со сменой родителя у проекта.

**Стенограммы переписки** — по файлу на чат, в формате «дата, автор, текст»:

```
Чат проекта — Иванов Иван
Выгружено: 03.08.2026 13:21 UTC

[01.08.2026 10:15] Иванов Иван: Не работает вентилятор
[01.08.2026 10:16] Ася: Посмотрите схему
    [вложение: Схема.pdf]
[01.08.2026 10:20] Иванов Иван: (сообщение удалено)
```

Стенограммы **перезаписываются** на каждой сверке: переписка растёт, и собрать файл
заново проще и надёжнее, чем дописывать хвост. Вложения и фотографии наоборот
копируются **один раз** — уже лежащий на NAS файл не трогается, чтобы не затирать
то, что могли переименовать или дополнить вручную.

> Имя фото на NAS (`cabinet_photos.nas_filename`) запоминается один раз при
> первом экспорте, а не пересчитывается из подписи на каждой сверке. Смена
> подписи в приложении **не** переименовывает и не дублирует файл на диске —
> старая копия просто продолжает использоваться под прежним именем.

Перезаписываются, впрочем, не все: чат пропускается, если после прошлой сверки
(`projects.folder_synced_at`) в нём никто не писал **и** файл стенограммы уже лежит
на месте. Удалили файл руками — соберётся заново. На проекте с десятками чатов это
и есть основная экономия: читается только то, что изменилось.

**Заявка выгружается сразу при закрытии.** Закрытие архивирует чат заявки (он
становится read-only), поэтому ждать ночной сверки незачем — стенограмма
`Заявка {id} — {ФИО}.txt` пишется в `Переписка/{ШУ}` или в `Переписка` проекта (для
чата без ШУ) в тот же момент. На ближайшей сверке этот чат будет пропущен как
неизменившийся.

Личные заметки (`notes`) в выгрузку не попадают: они не привязаны ни к проекту, ни
к ШУ, и это приватное пространство пользователя.

#### Файл положили в папку напрямую

Файл, положенный в `_Руководство/` мимо приложения, при следующей синхронизации
(ночной или по кнопке) заводится как документ **проекта**: копия кладётся в
`/uploads`, `doc_type`/`mime_type` определяются сами, название берётся из имени
файла. Файл в `_Руководство/{ШУ}/` — так же, но документом этого **ШУ**
(`Document.cabinet_id`), не проекта.

Сканируется **только сама папка `_Руководство`**, на обоих уровнях. Остальные
подпапки шаблона (`_Проект`, `_Программа`, `Переписка` и т.п.) не трогаются:
файлы там разложены осмысленно вручную, и сваливать их в плоский список
документов означало бы потерять эту структуру. Временные файлы Office (`~$…`)
пропускаются.

> **Заводится закрытым (`is_internal: true`) — пользователям не виден вообще.**
> Файл попал в приложение в обход админской формы загрузки, где уровень доступа
> (`requires_approval`/`is_internal`) выбирают осознанно — значит, для файла,
> подхваченного напрямую с диска, никто такого решения не принимал, и по умолчанию
> он должен быть закрыт максимально, а не просто «виден, но без доступа». В
> `GET /admin/documents` он при этом виден сразу (админам ограничение не
> действует) — администратор должен вручную проверить и открыть его через
> `PATCH /admin/documents/{id}` (см. ниже), если он предназначен пользователям.

> Подхваченный документ запоминает **фактическое имя файла** в папке
> (`documents.nas_filename`). Без этого сверка была бы неустойчивой: имя зеркала
> вычисляется из названия документа, и файл с длинным или «неудобным» именем не
> совпал бы сам с собой — и забирался бы заново при каждом прогоне.

**Папка `Фото`** — та же логика, что у `_Руководство`, только для фотографий:
файлы, положенные напрямую (в `Фото/` — для проекта, в `Фото/{ШУ}/` — для
конкретного шкафа), на той же сверке заводятся как `CabinetPhoto` — появляются
в `GET /cabinets/{id}/photos`.
Название без числового префикса и расширения становится подписью (`caption`).
Не-изображения (по mime-типу) в `Фото` пропускаются молча — не заводится ничего.
Как и у документов, реальное имя файла запоминается (`cabinet_photos.nas_filename`),
так что подхваченный файл не заводится повторно на следующей сверке, а смена
подписи в приложении задним числом файл на диске не переименовывает.

**Удаление фото — двустороннее** (в отличие от документов, где пропавший
зеркальный файл просто восстанавливается копией из `/uploads`):
- **Удалили фото в приложении** (`DELETE /admin/photos/{photo_id}`) — файл
  убирается и из `Фото` на NAS, фоново, тем же запросом.
- **Удалили файл из `Фото` на диске** — на следующей сверке (ночной или по
  кнопке) `CabinetPhoto` удаляется и в приложении, а не восстанавливается.
  Действует только для уже синхронизированных фото (`nas_filename` заполнен);
  на итоговое поведение это не влияет — для только что добавленных, ещё ни
  разу не попадавших на NAS, восстанавливать пока и нечего.

**Редактирование:**
- **Подпись/порядок в приложении** (`PATCH /admin/photos/{photo_id}`) —
  правится только в БД. Имя файла на NAS не меняется вслед за новой подписью
  (см. выше про `nas_filename`) — это осознанно, не баг.
- **Заменили содержимое файла на диске под тем же именем** — подхватывается:
  сверка сравнивает mtime файла с сохранённым (`cabinet_photos.nas_mtime`), и
  при расхождении перезаливает новое содержимое в `/uploads`, обновляя `url`
  фото. `caption`/`sort_order` при этом не трогаются — это поля приложения, не
  диска. Разница меньше 2 секунд не считается изменением (запас на грубость
  mtime у сетевых шар).

### GET `/admin/projects/{project_id}/qr`
Генерирует QR-код проекта в формате PNG. ШУ тоже можно добавить отдельно по
собственному QR — см. `GET /admin/cabinets/{cabinet_id}/qr` в разделе `qr` ниже.

QR кодирует адрес публичной страницы: `{PUBLIC_BASE_URL}/add/project/{unique_code}`
(см. раздел `qr` ниже про саму эту страницу и зачем это https, а не кастомная
схема `savt://`).

Ответ: бинарный PNG (`image/png`).

---

### PATCH `/admin/projects/{project_id}`
Смена родителя и гарантия. Все поля опциональны — передавать только изменённые.
```json
{
  "parent_project_id": null,
  "warranty_starts_at": "2026-08-24T00:00:00Z",
  "warranty_ends_at": "2028-08-24T00:00:00Z"
}
```
> **`name` сюда не принимается.** Название — из Bitrix (title сделки), правится
> только там; здесь правка молча затёрлась бы на ближайшем `ONCRMDEALUPDATE`. Папка
> на NAS переименовывается автоматически вслед за сделкой, фоново.

- Смена `parent_project_id` — `404`, если родитель не найден; `409`, если это создаст цикл (проект не может быть вложен сам в себя, в т.ч. через цепочку). **Папка на NAS при смене родителя не переносится автоматически** — если она уже была создана, её нужно перенести на диске вручную, сервер только меняет связь в БД (и пишет предупреждение в лог).
- **Гарантия** — единственное, что администратор реально задаёт руками: в CRM такого поля нет.

> ⚠️ **`warranty_ends_at` управляет ночной синхронизацией папок на NAS.** Если она
> задана и уже истекла (плюс неделя запаса) — папка проекта перестаёт
> синхронизироваться. Пока поле пустое, отбор идёт по крайней дате
> среди гарантий ШУ проекта. Подробности — в разделе «Поля сделки в карточке проекта».

Поля из Bitrix (`shipment_*`, `company_name`, `production_number`, `contacts`) этот
эндпоинт **не принимает**: они перезаписываются на каждом изменении сделки, и любая
правка была бы молча потеряна.

### POST `/admin/projects/sync-folders`
Синхронизировать папки **всех** активных проектов одним запросом — то же самое,
что делает ночной прогон, но по кнопке, без ожидания до 2:00 и без похода в
каждый проект отдельно. Доступно оператору и администратору.

В отличие от `POST /admin/projects/{project_id}/sync-folder` (один конкретный
проект) ограничение по гарантии здесь **сохраняется** — иначе на большом
архиве кнопка запускала бы полную сверку сотен давно закрытых проектов зря.
Проекты с истёкшей гарантией только переезжают в свою годовую папку, без
полной сверки (как и в ночном прогоне).

```json
{
  "total_projects": 42,
  "synced_projects": 38,
  "relocated_projects": 3,
  "failed_projects": 1,
  "message": "Проектов всего: 42 — синхронизировано: 38, перенесено без полной сверки (гарантия истекла): 3, с ошибкой: 1"
}
```

Ошибка на одном проекте (например, недоступна сеть до NAS) не останавливает
прогон остальных — считается в `failed_projects`, дальше обработка продолжается.
`404` — не настроен `PROJECT_FOLDERS_ROOT`.

### Автоматическая синхронизация папок

Ручной запуск — `POST /admin/projects/{project_id}/sync-folder` (один проект) или
`POST /admin/projects/sync-folders` (все проекты разом), описаны выше.

> **Автоматическая синхронизация** дополнительно прогоняется раз в сутки ночью — но только для проектов, у которых гарантия ещё актуальна: берётся крайняя (`MAX`) дата окончания гарантии среди ШУ проекта, плюс неделя запаса после истечения. Если гарантию продлить позже — синхронизация возобновится сама при ближайшем ночном прогоне, никакого отдельного действия не требуется. У проекта без ШУ/без указанной гарантии синхронизация не блокируется.
>
> Исключение — **раскладка по годам**: она делается и для проектов с истёкшей гарантией. Сверять там нечего, но папка переезжает в свою годовую, иначе весь архив остался бы в корне.

### DELETE `/admin/projects/{project_id}`
Удаление проекта. `204 No Content`. **Soft-delete**: `unique_code` больше не может быть переиспользован, проект пропадает из списков и поиска.

**Каскадно, тем же soft-delete/архивацией:**
- все ещё живые **ШУ проекта** удаляются (как при поштучном `DELETE /admin/cabinets/{id}` — каждый со своей записью в аудите);
- **чаты этих ШУ** (и их заявок) и **собственные чаты проекта** — архивируются у всех участников.

Привязки пользователей к проекту (`user_projects`) не трогаются — участники формально остаются в проекте, просто он и все его ШУ теперь недоступны/архивны. См. врезку про воскрешение проекта из Bitrix выше — она **не** каскадная в обратную сторону.

оператору и админу.

```json
[
  {
    "user_id": 1,
    "full_name": "Иванов Иван",
    "phone": "+375291234567",
    "user_type": "individual",
    "added_at": "2026-05-12T10:00:00Z"

```

### DELETE `/admin/projects/{project_id}/users/{user_id}`
Убрать пользователя из проекта — теряет доступ разом ко всем его шкафам. Заодно
архивируются его чаты по этому проекту и его шкафам (и заявкам) — иначе он мог
бы продолжать писать в уже открытые чаты, хоть доступа к проекту больше нет.
Чатов остальных участников проекта это не касается. Только для админа.
Логируется в `audit_log`. Пользователю приходит уведомление `request_status`
«Доступ к проекту отозван» (причина из запроса ему не показывается, она только
для аудита).
```json
{ "reason": "Причина удаления" }
```
Ответ: `204 No Content`.

## Рут `qr` — генерация QR-кодов и добавление вне приложения

Вступление в проект и добавление ШУ теперь не требуют ничьего одобрения (см.
разделы `projects`/`cabinets` выше) — заявок на доступ к уже занятому проекту
или к отдельному ШУ в системе больше нет.

### POST `/qr/generate`
Генерация QR-кода с произвольными данными. Доступно для админа и оператора.
```json
{ "data": "любой текст, URL, JSON-строка" }
```
Ответ: PNG-изображение (`image/png`). QR содержит логотип SAVT если файл `app/assets/savt_logo.png` существует.

---

### GET `/admin/cabinets/{cabinet_id}/qr`
Генерирует QR-код ШУ для самостоятельного добавления в обход проекта (см.
`POST /cabinets/add-by-qr` в разделе `cabinets`). Доступно админу и оператору.

QR кодирует адрес публичной страницы: `{PUBLIC_BASE_URL}/add/cabinet/{unique_code}`

Ответ: бинарный PNG (`image/png`). `404`, если ШУ не найден.

---

### GET `/add/project/{unique_code}` и GET `/add/cabinet/{unique_code}`
Публичные страницы (без авторизации) — то, что реально зашито в QR-коды проекта
и ШУ (`GET /admin/projects/{id}/qr`, `GET /admin/cabinets/{id}/qr` выше, а
также напечатанный QR в `_Маркировка/QR.png` на NAS). Нужны потому, что скан
QR-кода **внутри приложения** и сканирование **обычной камерой телефона** —
разные сценарии: камера телефона открывает кастомную схему `savt://...`
далеко не на всех устройствах, а обычную `https`-ссылку — всегда.

Логика страницы:
- Код не найден → показывает "не найден", без попытки открыть приложение.
- Код найден → пытается открыть приложение через `intent://` (если в `.env`
  задан `ANDROID_PACKAGE_NAME` — иначе этот шаг просто пропускается), и
  показывает кнопку скачать APK со ссылки из `APK_DOWNLOAD_URL` (пока нет
  публикации в Google Play). Если `APK_DOWNLOAD_URL` не задан — вместо кнопки
  текст "приложение пока не опубликовано".

Если приложение уже установлено и для `PUBLIC_BASE_URL` настроен Android App
Link (отдельная настройка на стороне мобильного приложения + домена,
`assetlinks.json`) — Android перехватывает переход на эту страницу сам, до
того как она вообще открывается, и сразу ведёт в приложение.

Сканирование **внутри** приложения в этот сценарий не попадает вовсе — оно
идёт напрямую через `POST /projects/add-by-qr`/`POST /cabinets/add-by-qr`,
даже если `qr_data` окажется ссылкой на эту же страницу (см. `parse_unique_code`
у обеих ручек — код достаётся из последнего сегмента независимо от формата).

## Рут `admin: phone change requests` — заявки на смену номера (просмотр — оператор/админ, решение — только админ)

Смена номера телефона идёт только так — самостоятельной больше нет, см.
`POST /auth/change-phone/request`.

> **Ответственность на администраторе.** Система подтвердить владение номером не
> может: SMS отключены, а мессенджер-связка привязана к `user_id`, а не к номеру.
> Перед одобрением нужно убедиться во владении вне системы — позвонить на новый
> номер, сверить документы организации и т.п. Одобрение меняет номер немедленно,
> а номер — это логин пользователя.

### GET `/admin/phone-change-requests`
Список заявок. Параметры: `status` (`pending`/`approved`/`rejected`/`cancelled`),
`resolved_by_admin_id`, `search` (по ФИО, текущему телефону, запрошенному номеру,
организации), `sort_by` (`created_at`/`resolved_at`/`status`/`user_full_name`),
`sort_order`, `page`, `size`.

Элемент списка — поля заявки плюс данные заявителя и `pending_rivals`:
```json
{
  "id": 12,
  "user_id": 5,
  "new_phone": "+375291234568",
  "old_phone": "+375291234567",
  "user_comment": "Сменил оператора связи",
  "status": "pending",
  "admin_response": null,
  "resolved_by_admin_id": null,
  "created_at": "2026-07-31T10:00:00Z",
  "resolved_at": null,
  "user_full_name": "Иванов Иван",
  "user_type": "individual",
  "organization_name": null,
  "user_is_verified": true,
  "user_registered_at": "2026-01-15T08:00:00Z",
  "pending_rivals": 1
}
```
`pending_rivals` — сколько всего необработанных заявок на **этот же номер**, включая
текущую. Значение `> 1` означает, что на номер претендует несколько аккаунтов —
повод разобраться, а не одобрять первую попавшуюся. На фронте стоит подсветить.

### POST `/admin/phone-change-requests/{request_id}/approve`
Одобрить — номер меняется сразу. Только админ.
```json
{ "admin_response": "Проверено звонком" }
```
`admin_response` необязателен. Ответ: `204 No Content`.

Занятость номера перепроверяется **на момент одобрения**, а не только подачи:
владелец мог сам зарегистрироваться, пока заявка ждала → `409`.

Пользователю уходит уведомление (тип `request_status`) о том, что вход теперь по
новому номеру. Сессии при этом не отзываются: номер — идентификатор входа, а не
пароль, выданные токены остаются валидными.

### POST `/admin/phone-change-requests/{request_id}/reject`
Отклонить. Только админ. `admin_response` обязателен (1–1000 символов) — причина
уходит пользователю в уведомлении.
```json
{ "admin_response": "Не удалось подтвердить владение номером" }
```
Ответ: `204 No Content`.

Оба действия пишутся в журнал (`admin: audit`) как `phone_change_request.approve` /
`phone_change_request.reject` со старым и новым номером.

## Рут `admin: documents` — документы и фото ШУ (админ/оператор)

Документ привязан либо к ШУ, либо к проекту в целом (документация, общая для всего
проекта, не для конкретного шкафа) — ровно к одному из двух.

### POST `/admin/documents`
Загрузка документа. `multipart/form-data`.

| Поле | Тип | Обязательно |
|---|---|---|
| `file` | файл | ✅ |
| `cabinet_id` | int | ровно одно из `cabinet_id`/`project_id` |
| `project_id` | int | ровно одно из `cabinet_id`/`project_id` |
| `title` | string | нет (берётся имя файла) |
| `requires_approval` | bool | нет (по умолчанию `false`) |
| `is_internal` | bool | нет (по умолчанию `false`) |

`doc_type`, `mime_type`, `file_size_bytes` извлекаются автоматически. Если передать оба
поля или ни одного — `422`.

**`requires_approval` и `is_internal` — разные вещи, не путать:**

| | Виден пользователю в списке | Можно запросить доступ | Скачивание |
|---|---|---|---|
| обычный | ✅ | — | ✅ |
| `requires_approval` | ✅ (без ссылки) | ✅ | после одобрения |
| `is_internal` | ❌ **не виден вовсе** | ❌ | ❌ |

Служебный документ (счёт, договор, внутренняя переписка) пользователю не показывается
ни в одном ответе: он отсекается прямо в SQL-выборке, а `GET /documents/{id}/download`
и `POST /documents/{id}/request-access` отвечают `404` — как на несуществующий, чтобы
по коду ответа нельзя было узнать, что документ есть. Операторам и админам он виден
в `GET /admin/documents` как обычно.

Если настроен `PROJECT_FOLDERS_ROOT` — файл дополнительно (фоново, best-effort)
зеркалится в подпапку **`_Руководство`** на NAS: в её корень — если задан
`project_id`, в `_Руководство/{ШУ}` — если задан `cabinet_id` (см. «Рут
`admin: projects`»). Источник истины для скачивания через API остаётся
`/code/uploads` — копия на NAS только для тех, кто открывает файлы напрямую с шары.
Удаление документа (`DELETE /admin/documents/{doc_id}`) аналогично убирает
зеркальную копию из `_Руководство`.

---

### GET `/admin/documents`
Список документов. Параметры: `cabinet_id`, `project_id`, `doc_type`, `requires_approval`, `tag_ids`, `sort_by`, `sort_order`, `page`, `size`.

`sort_by`: `title`, `doc_type`, `file_size_bytes`, `created_at`.

### PATCH `/admin/documents/{doc_id}`
Изменить уровень доступа. Единственное, что через этот эндпоинт можно поменять —
оба поля опциональны, передавать только изменённые:
```json
{ "requires_approval": true, "is_internal": false }
```
Только админ. Логируется в `audit_log` (`document.update`).

Основной сценарий — открыть документ, который синхронизация подхватила прямо с
NAS-папки: такие всегда заводятся с `is_internal: true` (см. «Файл положили в
папку напрямую» выше), и без этого эндпоинта их некому было бы вручную
разблокировать для пользователей.

Смена `is_internal` в любую сторону фоново переиндексирует документ для бота
(см. «RAG-бот Ася»): открыли — станет находиться поиском, закрыли — эмбеддинги
удаляются, чтобы бот не мог процитировать то, что только что спрятали.

## Рут `chats` — чаты

Пять типов чатов:
- `cabinet` — заводится только пользователем, открывшим конкретный ШУ (`GET /cabinets/{id}/chat`), никогда не создаётся заранее/пачкой
- `project` — при получении доступа к проекту (первый/основной владелец через QR, либо одобренная заявка на доступ) — один на пару пользователь + проект, независимо от числа ШУ внутри
- `support` — при регистрации (общая поддержка с ботом)
- `notes` — при регистрации (личные заметки, видны только самому пользователю)
- `service_request` — автоматически при создании сервисной заявки (`POST /service-requests`), виден и пользователю, и операторам/админам. Бот (Ася) в чатах заявок не участвует — ни отвечает на сообщения, ни шлёт follow-up (`bot_active: false` по умолчанию, `chat_type` жёстко исключён из логики бота независимо от значения `bot_active`); ведёт переписку человек, сообщения заявителя дублируются в Bitrix (см. «Рут `service requests`»). Привязан к ШУ либо к проекту в целом — ровно как сама заявка (`cabinet_id`/`project_id`)

### GET `/chats`
Список чатов текущего пользователя. Параметры:
- `chat_type` — `cabinet` / `project` / `support` / `notes` / `service_request`, без параметра — все типы
- `archived` — `false` (по умолч.) — активные чаты; `true` — архив (папка «Архив», как в Telegram — чаты закрытых заявок)

```json
[
  {
    "id": 3,
    "chat_type": "cabinet",
    "cabinet_id": 5,
    "cabinet_name": "ШУ-18К",
    "cabinet_object_number": "29_099",
    "project_id": null,
    "project_name": null,
    "last_message_text": "Здравствуйте, помогите",
    "last_message_at": "2026-05-15T10:00:00Z",
    "unread_count": 2,
    "problem_status": "open",
    "bot_active": true,
    "operator_requested": false,
    "service_request_id": null,
    "service_request_type": null,
    "service_request_status": null,
    "service_request_description": null,
    "service_request_created_at": null,
    "archived_at": null,
    "is_pinned": false
  }
]
```
`cabinet_id`/`cabinet_name`/`cabinet_object_number` заполнены для чатов ШУ и для чатов заявок по ШУ; `project_id`/`project_name` — для чатов проекта и для чатов заявок по проекту. У чата ровно одна из двух пар не `null` (кроме `support`/`notes`, где обе `null`).
`service_request_id`/`service_request_type`/`service_request_status`/`service_request_description`/`service_request_created_at` заполнены только для `chat_type: "service_request"` — этого достаточно, чтобы отличить в списке разные заявки одного и того же пользователя (тип, дата, текст обращения), не делая отдельный запрос к `GET /service-requests/{id}`.
`archived_at` — `null`, пока заявка не закрыта; при `status: "closed"` заполняется автоматически, при повторном открытии заявки — сбрасывается обратно в `null`. Архивный чат — read-only: `POST /chats/{chat_id}/messages` вернёт `403`, но история сообщений (`GET /chats/{chat_id}/messages`) остаётся доступна как обычно. Это только флаг состояния — сообщения физически никуда не переносятся.
`is_pinned` — **личное**: закреплено ли у ТЕКУЩЕГО вызывающего (см. `PUT /chats/{chat_id}/pin-chat` ниже), не у чата вообще. Тот же чат может быть закреплён у пользователя и не закреплён у оператора, который его же обрабатывает, и наоборот. Список отсортирован закреплёнными чатами наверх (дальше — как обычно, по дате последнего сообщения).

---

### PUT `/chats/{chat_id}/pin-chat`
Закрепить чат в СВОЁМ списке — `204` без тела. Идемпотентно (повторный вызов ничего не ломает). Личное действие: не видно ни другой стороне переписки, ни (для чатов, доступных операторам) другим операторам — у каждого своё состояние. Не путать с закреплением отдельных сообщений внутри чата (`PUT /chats/{chat_id}/pin/{msg_id}` ниже) — это про сам чат целиком, в общем списке.

### DELETE `/chats/{chat_id}/pin-chat`
Открепить — `204` без тела.

### GET `/cabinets/{cabinet_id}/chat`
Получить или создать чат для конкретного ШУ. Чат создаётся автоматически если его ещё нет.

> **Единственный способ завести чат ШУ.** Он никогда не создаётся заранее/пачкой
> (ни при вступлении в проект, ни при привязке ШУ к проекту, ни при одобрении
> заявок) — только этим запросом, когда пользователь сам открывает конкретный
> ШУ и нажимает на чат. Так проект с сотней ШУ не заводит сотню чатов сразу —
> заводятся только те, что реально понадобились. Контраст с чатом проекта (см.
> `GET /projects/{project_id}/chat` и врезки ниже) — тот заводится сразу, один
> на проект, и не масштабируется с числом ШУ.

> Требует, чтобы пользователь имел доступ к ШУ — то есть состоял в проекте, к которому привязан этот ШУ (`user_projects`). Pending-заявка доступа не даёт — вернёт `403`.

### GET `/chats/{chat_id}/messages`
История сообщений. Параметры:
- `before_id` — ID сообщения, загрузить более старые (cursor pagination для бесконечного скролла)

возвращает уже созданное сообщение с тем же `id` — `201`, а не ошибка. Без

## Realtime (SSE) для операторской панели

Замена поллинга (`GET /operator/chats` каждые 4с, `GET /operator/chats/{id}/messages` каждые 3с) на push через Server-Sent Events. Все мутации (отправка/редактирование/удаление сообщения, реакции, pin) остаются обычными REST-вызовами как раньше — SSE только уведомляет, что что-то изменилось.

**Почему SSE, а не WebSocket:** операторская панель ничего не шлёт по каналу, только слушает — SSE проще и не требует HTTP-апгрейда на уровне nginx.

> **Важно, если фронтенд — Next.js и ходит на бэкенд через `rewrites()` (`next.config.js`, например `/backend/:path* → API_URL/:path*`):** `rewrites()` в Next.js **не умеют стримить долгоживущие ответы** — SSE у него буферизуется целиком до закрытия соединения (в DevTools это выглядит как «EventStream появляется только после закрытия запроса, и она пустая»), а WebSocket-upgrade он не проксирует вообще никак — это давняя, задокументированная особенность Next.js, а не баг конфигурации. Решение — пускать эти конкретные пути (`/operator/events/`, `/user-events/`) **в обход фронтенда**, отдельными `location` в nginx прямо на API-контейнер, до того как запрос долетит до Next.js. Пример — в `nginx.http-fallback.conf`, server-блок `listen 8080` (там, где фронтенд отдаётся на одном порту с API через `/backend/*`): `location /backend/operator/events/` и `location /backend/user-events/` там прописаны отдельно, со снятием префикса `/backend/` через `rewrite ... break;`, и обычные (не-realtime) `/backend/*`-запросы продолжают идти через фронтендовый rewrite как раньше — трогать `next.config.js` не нужно.
>
> **Этот обход работает только когда фронтенд обслуживается через nginx** (в наших конфигах — блок `listen 8080`; блоки `listen 80`/`listen 443` проксируют `location /` прямо на `api:8000` и фронтенд не отдают вовсе, поэтому `/backend/*` там просто не при чём). Если разработчик открывает панель на `localhost:3000` — то есть напрямую на dev-сервере Next.js — **nginx в цепочке не участвует**, и никакая правка его конфига не поможет: `rewrites()` забуферит SSE у себя. Признак в DevTools: `Remote Address` указывает на `:3000`, а не на порт nginx. Варианты для локальной разработки: открывать панель через nginx (порт из `docker-compose`, а не `3000`) либо в dev-сборке подключать `EventSource` напрямую к origin API (тогда API-порт должен быть проброшен на хост, а origin дев-сервера — добавлен в `CORS_ORIGINS`).

### Авторизация: короткоживущий тикет

`EventSource` не умеет слать заголовок `Authorization`, а класть в URL сам JWT означало бы, что access-токен светится в логах nginx. Поэтому сначала обычным REST-запросом с Bearer-токеном получаем короткоживущий тикет, а он уже подставляется в query-параметр SSE-запроса.

### POST `/operator/events/ticket`
**Доступ:** `operator`, `admin`.

Ответ:
```json
{ "ticket": "kQ2f...", "expires_in": 300 }
```
Тикет живёт 5 минут и **валиден многократно** в пределах этого времени — не удаляется после первого использования. Это важно: браузерный `EventSource` при любом обрыве соединения (смена сети, сон вкладки, короткий сбой) сам переподключается **тем же URL**, с тем же тикетом. Если бы тикет становился недействителен после первого коннекта, любое автопереподключение браузера получало бы `401`, и клиент навсегда терял бы live-обновления до полной перезагрузки компонента чата. Просрочен → следующий SSE-запрос ответит `401`.

> **Тикет привязан к своему каналу.** Тикет из `POST /operator/events/ticket` работает
> только на `/operator/events/*`, тикет из `POST /user-events/ticket` — только на
> `/user-events/*`. Переиспользовать один тикет на оба вида стримов нельзя: чужой
> канал ответит `401`. Раньше хранилище тикетов было общим, и тикет обычного
> пользователя открывал операторские каналы с чужими чатами.

### GET `/operator/events/chats?ticket=...`
Глобальный канал — замена поллинга списка чатов (`chats-page.tsx`). Событие `chat.created`/`chat.updated` приходит при новом сообщении (в т.ч. от бота), новом чате, смене `bot_active`/`operator_requested`/`problem_status`.

### GET `/operator/events/chats/{chat_id}?ticket=...`
Канал открытого чата — замена поллинга сообщений (`chat-conversation.tsx`). События: `message.created`, `message.updated`, `message.deleted`, `message.reaction_changed`, `message.pinned`, `message.unpinned`, `message.read`.

Доступ к конкретному чату проверяется при каждом подключении (не только валидность тикета): роль перечитывается из БД, а личные заметки пользователя (`notes`) закрыты и от операторов. Нет доступа → `403`.

`POST /chats/{chat_id}/read` (и `/operator/chats/{chat_id}/read`) публикует `message.read` при реальном изменении статуса — хотя бы одно сообщение действительно помечено прочитанным:
```json
{ "type": "message.read", "chat_id": 11, "data": { "message_ids": [41, 42], "reader_id": 8 } }
```
Если помечать нечего (все сообщения уже были прочитаны) — событие не публикуется.

### GET `/operator/events/cabinets/{cabinet_id}/telemetry?ticket=...`
Канал открытого ШУ — замена поллинга `GET /admin/cabinets/{cabinet_id}/telemetry`. Событие: `{"type": "telemetry.created", "cabinet_id": ..., "event_id": ...}`. Приходит, только если в сообщении реально **переключился** хотя бы один названный в карте бит (см. «Рут `admin: telemetry`») относительно предыдущего сообщения — 0→1 (новая авария) или 1→0 (авария снята). Контроллер обычно шлёт текущее состояние периодически, а не только по факту изменения — на повтор уже известного значения (даже если в нём есть взведённый названный бит) сигнала не будет, чтобы не заваливать фронт пушами ни о чём (и рикошетом — самого себя рейт-лимитом на рефетч). В отличие от чата — без проверки доступа к конкретному ШУ (только валидность тикета): оператор/админ видит телеметрию любого ШУ, как и в самом REST-эндпоинте.

Формат конверта (`text/event-stream`):
```
event: message.created
data: {"type":"message.created","chat_id":11,"data":{...MessageOut...}}

```
Сразу после подключения приходит `{"type":"connected"}`, а затем каждые 20с — комментарий-пинг (`: ping`) для поддержания соединения, если реальных событий нет.

**Важно про payload `chat.updated`/`chat.created`:** `data` — best-effort снимок (`id`, `chat_type`, `cabinet_id`, `user_id`, `last_message_text`, `problem_status`, `bot_active`, `operator_requested`), **без** `unread_count` — он зависит от конкретного оператора-получателя и здесь не считается. Событие стоит трактовать как сигнал инвалидировать React Query кэш и перезапросить актуальные данные, а не как источник истины для всех полей.

**Ограничения, о которых стоит знать:**
- Доставка *at-most-once* и без буферизации на сервере: если соединение оборвалось (сон вкладки, сеть), пропущенные события не повторяются. При (пере)подключении стоит один раз перезапросить актуальные данные через обычный REST, а не полагаться только на поток.
- `DELETE /operator/chats/{chat_id}` (удаление чата целиком) событие не публикует — крайне редкое действие, обычно инициируется тем же оператором, который смотрит на список.
- Работает в рамках одного процесса api (см. `Dockerfile` — uvicorn без `--workers`). Если когда-нибудь потребуется несколько инстансов api, канал нужно будет перевести на Redis pub/sub.

Пример на фронте:
```js
const { ticket } = await fetch('/operator/events/ticket', {
  method: 'POST', headers: { Authorization: `Bearer ${token}` },
}).then(r => r.json());

const es = new EventSource(`/operator/events/chats?ticket=${ticket}`);
es.onmessage = (e) => {
  const event = JSON.parse(e.data);
  if (event.type === 'chat.updated' || event.type === 'chat.created') {
    queryClient.invalidateQueries(['operator-chats']);
  }
};
// ticket живёт 30с — если EventSource переподключается (реконнект браузера
// после разрыва), нужен свежий тикет через тот же POST /operator/events/ticket
```

## Realtime (WebSocket) для мобильного/пользовательского приложения

Тот же смысл, что и SSE у оператора (замена поллинга `GET /chats` и `GET /chats/{id}/messages`), но другой транспорт: `EventSource` нативно не поддерживается на мобильных платформах, а `WebSocket` — поддерживается везде, поэтому для обычных пользователей сделан отдельный WS-канал вместо SSE.

Формат событий (`message.created`, `message.updated`, `message.deleted`, `message.reaction_changed`, `message.pinned`, `message.unpinned`, `message.read`, `chat.created`, `chat.updated`) — **тот же самый JSON**, что и в SSE у оператора, просто доставляется через `websocket.send_text()` вместо `event:`/`data:`-конверта. Мутации (отправка сообщения, реакции, pin, mark-as-read) — по-прежнему обычные REST-вызовы, WS только уведомляет.

> Если фронтенд ходит на бэкенд через Next.js `rewrites()` — см. предупреждение в начале раздела «Realtime (SSE)» выше: WebSocket-upgrade через `rewrites()` не проксируется вообще, этот путь обязателен в обход фронтенда на уровне nginx.

### Авторизация: тот же короткоживущий тикет

Как и `EventSource`, браузерный/нативный `WebSocket` не умеет слать заголовок `Authorization` при установке соединения. Схема идентична операторской: сначала обычный REST-запрос с Bearer-токеном за тикетом, потом тикет — в query-параметре WS URL.

### POST `/user-events/ticket`
Доступен любому авторизованному пользователю.

Ответ:
```json
{ "ticket": "kQ2f...", "expires_in": 300 }
```
Тикет живёт 5 минут, валиден многократно в пределах этого времени (та же логика, что у операторского тикета — переподключение тем же URL не должно ловить 401).

---

### WS `/user-events/chats?ticket=...`
Персональный канал пользователя — приходят обновления **только по его собственным чатам** (`chat.created`/`chat.updated`), замена поллинга списка чатов. В отличие от оператора, который видит все чаты сразу через общий канал, здесь канал именно персональный — привязан к `user_id` из тикета.

### WS `/user-events/chats/{chat_id}?ticket=...`
Канал конкретного открытого чата — те же события, что и в операторской версии. Проверяется, что у пользователя реально есть доступ к этому чату (та же проверка, что и на `POST /chats/{chat_id}/messages`) — иначе соединение закрывается сразу после подключения с кодом `4403` (нет доступа) или `4401` (невалидный/просроченный тикет).

Сразу после подключения приходит `{"type": "connected"}`, затем каждые 20с — `{"type": "ping"}`, если реальных событий нет (аналог SSE-комментария-пинга, только тут это обычное сообщение, поскольку у WS нет комментариев).

Пример на клиенте:
```js
const { ticket } = await fetch('/user-events/ticket', {
  method: 'POST', headers: { Authorization: `Bearer ${token}` },
}).then(r => r.json());

const ws = new WebSocket(`wss://helper.savt.by/user-events/chats/${chatId}?ticket=${ticket}`);
ws.onmessage = (e) => {
  const event = JSON.parse(e.data);
  if (event.type === 'message.created') { /* … */ }
};
```

**Ограничения — те же, что и у SSE-версии:** доставка *at-most-once* без буферизации (пропущенные во время разрыва события не повторяются, при реконнекте стоит один раз перезапросить актуальные данные через REST), и работа в рамках одного процесса api (in-memory `event_bus`, без Redis pub/sub — если появится больше одного воркера/инстанса, каналы перестанут видеть события друг друга).

### WS `/user-events/cabinets?ticket=...`
Персональный канал: приходит `{"type": "cabinet.created", "cabinet_id": ..., "project_id": ...}`, когда в одном из проектов пользователя появляется новый ШУ (участникам проекта доступ выводится из членства в проекте, см. раздел `cabinets`, — то есть новый ШУ виден сразу всем, но клиент об этом иначе не узнает без REST-поллинга). Событие не несёт сам объект ШУ — он персонален (custom_name, unread_count), поэтому по этому сигналу нужно перезапросить `GET /cabinets` (или `GET /cabinets/{cabinet_id}`).

> Если список ШУ в приложении кэшируется локально — именно этот канал нужен, чтобы инвалидировать кэш при появлении нового ШУ. Без него единственный способ увидеть новый ШУ — самостоятельный периодический рефетч `GET /cabinets` (или полная переустановка приложения, если кэш переживает даже перезапуск).

### WS `/user-events/cabinets/{cabinet_id}/telemetry?ticket=...`
Канал конкретного открытого ШУ: приходит `{"type": "telemetry.created", "cabinet_id": ..., "event_id": ...}`, когда в базу легло новое событие телеметрии. Проверяется доступ к ШУ (членство в проекте) — как и у чата, `4403`/`4401` при отказе. Событие не несёт сами регистры (список персонален — фильтр по `include_unnamed` и т.п.), по сигналу нужно перезапросить `GET /cabinets/{cabinet_id}/telemetry`.

**Сигнал шлётся не на каждое сырое MQTT-сообщение** — только если в нём хотя бы один названный в карте бит (см. «Рут `admin: telemetry`») реально переключился относительно предыдущего сообщения (0→1 — новая авария, 1→0 — авария снята). Контроллер обычно шлёт текущее состояние периодически, а не только по факту изменения — повтор уже известного значения сигнала не вызывает, даже если в нём есть взведённый названный бит: иначе на активной, но не меняющейся аварии пуши сыпались бы непрерывно, а каждый пуш — это полный рефетч на фронте.

## Рут `admin/dashboard` — дашборд

Единый endpoint для главного экрана администратора/оператора. Возвращает все счётчики одним запросом-набором и последние 10 действий по всем типам заявок разом.

**Доступ:** `operator`, `admin`.

Ответ (`DashboardOut`):
```json
{
  "stats": {
    "unread_chats": 2,
    "open_service_requests": 5,
    "pending_document_requests": 3,
    "pending_addition_requests": 4,
    "pending_phone_change_requests": 0,
    "pending_registration_requests": 2,
    "pending_password_reset_requests": 0,

  },
  "recent_activity": [
```

Поле `type`: `service` | `document` | `addition` | `phone_change` |

рассмотрение, как и `open_service_requests` у сервисных заявок.

## Рут `service requests` — сервисные заявки

Типы заявок (`request_type`): `repair` (ремонт), `diagnostics` (диагностика), `remote_adjustment` (наладка удалённо), `onsite_adjustment` (наладка с выездом), `other` (другое).
Статусы: `open`, `in_progress`, `postponed`, `closed`. Переход между статусами не валидируется — администратор/оператор может установить любой статус через `PATCH /admin/service-requests/{req_id}/status` (типичный сценарий: `open → in_progress → closed`).

### POST `/service-requests`
Создать заявку — по конкретному ШУ либо по проекту в целом. Ровно одно из
`cabinet_id`/`project_id`, второе не передавать (`422`, если задано и то, и
другое, либо ни одного). Пользователь должен быть привязан к указанному ШУ
(состоять в его проекте) либо, для заявки по проекту, состоять в самом проекте.
```json
{
  "cabinet_id": 5,
  "request_type": "repair",
  "description": "Не работает кнопка управления, при нажатии нет реакции"
}
```
Заявка по проекту в целом — то же самое, но `{ "project_id": 3, ... }` вместо
`cabinet_id`.

`request_type` — это **вид работ** (ремонт/диагностика/наладка), не гарантия.
Гарантийность — отдельная ось, платно или бесплатно будет обслуживание:
сервер сам вычисляет и сохраняет `is_under_warranty` по фактическому статусу
гарантии ШУ (или проекта — для заявки по `project_id`) **на момент создания
заявки** и больше никогда не пересчитывает это значение задним числом — если
администратор потом продлит гарантию, уже созданная заявка не станет от этого
гарантийной. На создание заявки гарантия никак не влияет — открыть её можно и
с истёкшей гарантией, ограничений по гарантии на входе нет ни для ШУ, ни для
проекта, только на результат (`is_under_warranty: false`).

`description` — минимум 10 символов.

**`client_token`** (необязательное поле, до 64 символов) — тот же принцип
идемпотентности оффлайн-очереди, что и у `POST /chats/{chat_id}/messages`:
повторная отправка с тем же токеном возвращает уже созданную заявку вместо
дубля.

При создании заявки автоматически создаётся её чат (`chat_type: "service_request"`) — виден и заявителю, и операторам/админам (`GET /chats`, `GET /operator/chats`). `chat_id` из ответа — сразу открыть чат заявки, не нужно искать его в общем списке.

После создания заявка асинхронно (в фоне, не блокируя ответ) синхронизируется с Bitrix24 — создаётся задача (`tasks.task.add`) с исполнителем (`RESPONSIBLE_ID` = `BITRIX_DEFAULT_RESPONSIBLE_ID`) и постановщиком (`CREATED_BY` = `BITRIX_DEFAULT_CREATOR_ID`, если настроен — иначе постановщиком становится технический пользователь вебхука). ID созданной задачи попадает в поле `bitrix_task_id` (появится не сразу, а чуть позже создания заявки — обнови список, чтобы увидеть). Если Bitrix не настроен или недоступен — заявка всё равно создаётся, просто `bitrix_task_id` остаётся `null`.

Заголовок задачи в Bitrix для заявки по ШУ собирается из пометки гарантии, номера объекта, организации (или ФИО, если пользователь — физлицо) заявителя, назначения ШУ, рабочего кода ШУ в скобках и типа заявки — например:
```
[Гарантия] 26_001 Могилевский водоканал ПНС Вейно (П-228) ремонт
[ПЛАТНО] 26_001 Могилевский водоканал ПНС Вейно (П-228) ремонт
```
Пометка `[Гарантия]`/`[ПЛАТНО]` — это и есть `is_under_warranty`, вынесена в начало заголовка нарочно: от неё зависит, платное обслуживание или нет, и это не должно теряться где-то в описании задачи. Та же информация дублируется отдельной строкой `Гарантия: да/нет` в теле задачи. Части, для которых поле в ШУ не заполнено (`purpose`/`admin_internal_name`), просто пропускаются. Для заявки по проекту вместо номера объекта и назначения ШУ — производственный номер и название проекта (`purpose`/`admin_internal_name` у проекта нет, эти части в заголовке не участвуют).

**Синхронизация переписки в Bitrix.** Каждое сообщение **заявителя** (не оператора и не бота) в чате заявки асинхронно дублируется комментарием в ленту Bitrix-задачи (`task.commentitem.add`) в формате:
```
Иванов Иван написал: "Не работает кнопка"
```
Вложения без текста — прямой ссылкой на файл (`/static/...`, как есть в `file_url`); если в сообщении и текст, и вложения — ссылки идут отдельными строками после текста. Синхронизация одностороннего направления (как и статус) — комментарии, оставленные прямо в Bitrix, к нам не подтягиваются. Если у заявки ещё нет `bitrix_task_id` (Bitrix не настроен/недоступен на момент создания) — сообщение просто не синхронизируется, без ошибки для отправителя.

### PATCH `/admin/service-requests/{req_id}/status`
Изменить статус заявки.
```json
{ "status": "in_progress" }
```
Если у заявки есть `bitrix_task_id`, статус асинхронно (в фоне) прокидывается и в задачу Bitrix24: `open` → "Ждёт выполнения", `in_progress` → "Выполняется", `closed` → "Завершена". Направление одностороннее — изменение статуса задачи прямо в Bitrix24 к нам не возвращается.

При переходе в `closed` чат заявки архивируется (`archived_at` заполняется) — пропадает из активного списка чатов, становится read-only. При переходе обратно в `open`/`in_progress` — разархивируется автоматически.

## Рут `reclamations` — рекламации (гарантийные/негарантийные претензии)

Оформление претензии по ШУ, автоматической линии, покупному комплектующему
изделию (ПКИ), ПО или документации. Заявитель подаёт её у нас; вся дальнейшая
обработка — статус, гарантия, ответственный, срок, подтверждающий документ —
происходит только в Bitrix24 (смарт-процесс «Журнал рекламаций и претензий»).
Изменения оттуда приходят к нам вебхуком и видны в ответе API сами; в обратную
сторону, от админки в Bitrix, ничего не уходит — у админки нет ни одной ручки,
которая меняла бы состояние рекламации. Единственное, что она может сделать —
отправить рекламацию в Bitrix повторно, если та не доехала туда вообще (см.
`bitrix-outbox` ниже).

`object_type`: `cabinet` (ШУ) / `line` (автоматическая линия) / `component` (ПКИ) /
`software` (ПО) / `documentation` (документация). Рекламация ни к какому ШУ или
проекту в системе не привязывается — никакой выбор «своего» объекта из списка в
форме подачи не предусмотрен.
Статусы (`status`): `new` (новая) → `review` (на рассмотрении) → `in_progress`
(в работе) → `resolved` (исполнено) / `rejected` (отклонена) / `invalid`
(оформлена некорректно). Новая рекламация заводится в `new`.
`warranty_classification` — гарантийный случай или нет (`true`/`false`/`null` — ещё
не классифицирован), отдельное поле от статуса — выставляет специалист в Bitrix,
к нам приходит вебхуком.

### POST `/reclamations`
Подать рекламацию.
```json
{
  "object_type": "cabinet",
  "object_details": { "serial_number": "29_099" },
  "description": "Не работает кнопка управления, при нажатии нет реакции",
  "occurrence_conditions": "Проявляется при включении после простоя больше суток",
  "error_codes": "E-12",
  "contract_number": "Д-45/2026",
  "order_number": "З-102",
  "ttn_number": "ТТН-778",
  "contact_name": "Иванов Иван",
  "contact_phone": "+375291234567",
  "contact_email": "ivanov@example.com",
  "customer_name": "ООО Ромашка",
  "attachments": [
    { "file_url": "/static/attachments/uuid.jpg", "file_name": "photo.jpg", "file_size_bytes": 204800, "mime_type": "image/jpeg" }
  ]
}
```
Обязательные поля: `object_type`, `description`, `contact_name`, `contact_phone`,
`contact_email`. Проверки доступа при подаче нет — рекламацию можно оставить про
что угодно, без привязки к конкретному зарегистрированному в системе объекту.

`object_details` — JSON, состав зависит от `object_type`. Для `cabinet` и `line`
он **обязателен** и состоит из одного ключа `serial_number` — заводской номер,
который заявитель вручную списывает с самого объекта (никакого выбора из реестра
ШУ нет, это просто текстовое поле формы). Для `component` обязательны все четыре
ключа — `name`/`model`/`article`/`serial_number`:
```json
{
  "object_type": "component",
  "object_details": {
    "name": "Контактор", "model": "LC1D18", "article": "LC1D18M7", "serial_number": "SN-4521"
  },
  ...
}
```
Без обязательного `object_details` — `400`: эти данные уходят в собственные
нативные поля процесса Bitrix («Заводской номер ШУ или линии» / «Данные ПКИ»),
и без них карточка уехала бы в Bitrix с пустыми этими полями. Для `software` и
`documentation` `object_details` не валидируется.

`contact_name`/`contact_phone`/`contact_email` — предзаполняйте из профиля
пользователя, но давайте редактировать перед отправкой: это **снимок** на момент
подачи, а не живая ссылка на профиль, так что заявку можно подать от имени
заказчика (`customer_name`), а более поздняя правка профиля задним числом никак
не повлияет на уже поданную заявку.

`attachments` — файлы, уже загруженные через `POST /upload/attachment` (см. раздел
`upload` выше): сначала грузите файл туда и получаете подписанный `file_url`, потом
передаёте его сюда вместе с метаданными из ответа на загрузку. Поле необязательное,
в Bitrix при создании уходит только первый файл — там это поле не множественное.

Ответ — созданная рекламация целиком, в том же виде, что и `GET /reclamations/{id}`
ниже.

### GET `/admin/reclamations`
Все рекламации (только `admin`, оператору недоступно). Параметры: `status`,
`object_type`, `warranty_classification` (`true`/`false`), `search`, `sort_by`,
`sort_order`, `page`, `size`.

`search` (1–200 символов) — поиск, устойчивый к регистру и разделителям
(`26_205_1` = `26 205 1`), по полям: ФИО и телефон аккаунта заявителя, имя и
телефон из формы заявки, описание, коды ошибок, номера договора/заказа/ТТН,
заводской номер (`object_details.serial_number`), название проекта и номер ШУ
(последние два — только у старых рекламаций, у новых проекта и ШУ нет). Также
находит по подписям, которые админка показывает на карточках: тип объекта
(`ШУ`, `Линия`, `ПКИ`, `ПО`, `Документация`) и статус (`Закрыта`,
`Принята в работу` и т.д.), гарантия (`Гарантийный случай`,
`Негарантийный случай`, `Не классифицирована`) и даты создания, закрытия и
срока (`29.09.2026`, `29.09.26`, `29.09`, `2026-09-29` — по местному времени
Минска). Подписи ищутся по началу слова и от двух букв.

Запрос из нескольких слов разбирается по словам, каждое должно найтись
где-нибудь (в любом поле, в любом порядке): `ШУ 26_205_1` — тип «ШУ» и номер
ШУ, `закрыта 28.09.2026 Иванов`. Если в слове есть цифра, это номер, и
ищется только точное вхождение: `26_204_1` не найдёт соседний `26_205_1`.
Слова без цифр прощают опечатки. Комбинируется с остальными фильтрами;
`total` считается по всем найденным, не по странице.

Те же правила — во всех остальных списках админки: слова ищутся порознь,
цифры — только точно, а в списках заявок (сервисные, регистрация, смена
номера, сброс пароля, документы, добавление ШУ) и пользователей ещё и по
подписям статуса/типа (`Одобрена`, `Отклонена`, `На рассмотрении`, `Открыта`,
`В работе`, `Закрыта`, `Ремонт`, `Диагностика`, `Организация`,
`Физическое лицо` и т.п.).

`sort_by` — `created_at` (по умолчанию) / `resolved_at` / `status` /
`deadline_at` / `object_type` / `user_full_name`, `sort_order` — `desc`
(по умолчанию) / `asc`. Записи без значения (например, без дедлайна) всегда в
конце списка, при равных значениях порядок стабилен между страницами.
```json
{
  "items": [
    {
      "id": 1, "object_type": "cabinet", "status": "in_progress",
      "warranty_classification": true, "description": "Не работает кнопка управления",
      "cabinet_object_number": "29_099", "project_name": null,
      "created_at": "2026-09-15T10:00:00Z",
      "resolved_at": null, "user_id": 8, "user_full_name": "Иванов Иван",
      "deadline_at": "2026-09-30"
    }
  ],
  "total": 1, "page": 1, "size": 20, "pages": 1
}
```

`status` — один из **шести** статусов, соответствуют стадиям Bitrix один к
одному. Таблица соответствия — в блоке «Статусы и стадии Bitrix» ниже.

### GET `/admin/reclamations/{reclamation_id}`
Подробности любой рекламации (только `admin`). То же самое, что
`GET /reclamations/{id}` у пользователя, плюс `user_id`/`user_full_name` — кто
подал (не путать с `contact_name` — это снимок с формы заявки, может отличаться),
`deadline_at` и `responsible_bitrix_user_id` (приходят только вебхуком из Bitrix,
см. ниже), `bitrix_item_id` (id карточки на портале, `null` — рекламация ещё не
доехала до Bitrix), `bitrix_deleted_at` (заполнено, если карточку в Bitrix
удалили — см. `bitrix-detached` ниже) и `pending_create_outbox` — не `null`,
если рекламация не доехала до Bitrix вообще, см. `bitrix-outbox` ниже.

#### Статусы и стадии Bitrix
Статусов шесть, и они соответствуют стадиям смарт-процесса Bitrix **один к
одному**. Отдельного поля под стадию нет намеренно: `status` и есть стадия.

| `status` | Стадия Bitrix | Подпись для интерфейса |
|---|---|---|
| `new` | `DT1176_69:NEW` | Новая рекламация |
| `review` | `DT1176_69:UC_DPZ1YJ` | На рассмотрении |
| `in_progress` | `DT1176_69:CLIENT` | Принята в работу |
| `resolved` | `DT1176_69:SUCCESS` | Закрыта |
| `rejected` | `DT1176_69:UC_RNKN52` | Отклонена |
| `invalid` | `DT1176_69:FAIL` | Ошибочные рекламации |

Статус двигает специалист прямо в карточке Bitrix — новое значение приезжает
вебхуком и видно в ответе API само, без каких-либо действий с нашей стороны.
У админки нет ручки, которая переводила бы рекламацию между статусами.

Новая заявка заводится со статусом `new`.

---

### Обработки через нашу админку нет

У рекламации нет `PATCH`-ручки — статус, гарантию, ответственного, срок и
подтверждающий документ нельзя выставить у нас. Специалист работает прямо в
карточке Bitrix, оттуда `deadline_at`, `responsible_bitrix_user_id` (вместе с
`responsible_name`/`responsible_phone`, которые Bitrix знает про назначенного)
и `warranty_classification` приходят к нам вебхуком и видны в ответе API сами.

При реальной смене статуса заявителю уходит пуш-уведомление (`request_status`)
с готовым текстом с сервера: `review` — «принята на рассмотрение», `in_progress`
— статус (гарантия/платно) + ФИО и телефон ответственного, `rejected`/`invalid`
— причина отклонения, `resolved` — итоговый комментарий. Переход в `new` пуш не
шлёт — это начальный статус, заявитель видит его сразу после подачи.

`root_cause`, `resolution_comment`, `rejection_reason`, `confirmation_file_url`,
`confirmation_file_name` остались в схеме ответа, но писать в них больше некому
— под эти поля никогда не было отдельного UF-поля в смарт-процессе, и раз у нас
нет `PATCH`, заполнить их негде и нам. У рекламаций, поданных раньше, там может
быть исторический текст — показывайте его как есть, если заполнено, но строить
вокруг этих полей форму обработки не нужно, её не существует.

### GET `/admin/reclamations/bitrix-outbox`
Недоставленные попытки отправки в Bitrix (`admin`) — retry-механизм. Когда
создание элемента падает с ошибкой (Bitrix недоступен, сетевой сбой, не хватает
обязательного поля и т.п.), вместо потери данных заводится строка здесь; фоновая
задача сама повторяет попытку каждые 15 минут, и при успехе строка исчезает
отсюда сама. Этот эндпоинт — список сразу по всем рекламациям, для одной
конкретной проще смотреть `pending_create_outbox` в её карточке
(`GET /admin/reclamations/{id}` выше).
```json
[
  {
    "id": 3, "reclamation_id": 12, "operation": "create",
    "payload": {
      "description": "...", "attachment_url": null,
      "object_serial_number": "AL-2026-014", "contract_info": null, "component_info": null
    },
    "attempts": 4, "last_error": "Bitrix crm.item.add: CRM_FIELD_ERROR_REQUIRED (Название)",
    "created_at": "2026-09-21T10:00:00Z", "last_attempted_at": "2026-09-21T11:00:00Z"
  }
]
```
`operation` практически всегда `create` — заявка никуда не доехала при подаче.
Остальные виды (`status`/`assignee`/`deadline`/`warranty`/`comment`) заводились
только из обработки через админку, которой больше нет, — новых таких записей не
появится, но старые, если что-то уже висело в очереди на момент перехода, всё
ещё могут встретиться и обрабатываются тем же механизмом. Ограничения на число
попыток нет — если что-то застряло надолго (много `attempts`, `last_attempted_at`
давно), это повод разобраться руками: почему конкретно эта операция не проходит.

`payload` — то, с чем именно вызывается Bitrix при повторе (снимок на момент
сбоя, не текущее состояние рекламации). По нему видно, чего не хватало.

Единственное исключение — удалённая карточка. На ответ `NOT_FOUND` повторы
прекращаются: рекламация отвязывается от Bitrix и переезжает в
`bitrix-detached` ниже.

---

### PATCH `/admin/reclamations/bitrix-outbox/{id}`
Ручная правка застрявшего `payload` и немедленный повтор (`admin`) — на крайний
случай, когда причина сбоя видна в `payload`, но сама она никогда не устранится
авторетраями. `id` для рекламации, которая не доехала до Bitrix, — это
`pending_create_outbox.id` из её карточки (`GET /admin/reclamations/{id}`).
Тело — произвольный объект, целиком заменяющий `payload` строки, состав ключей
должен совпадать с исходным:
```json
{ "payload": { "description": "Останавливается конвейер на третьей секции",
               "attachment_url": null, "object_serial_number": "AL-2026-014",
               "contract_info": null, "component_info": null } }
```
Сразу после правки — попытка отправки, не дожидаясь ближайшего 15-минутного
цикла:
```json
{ "success": true, "row": null }
```
`success: true` — отправилось, строка исчезла из очереди; перечитайте карточку
рекламации — `bitrix_item_id` заполнится, `pending_create_outbox` станет `null`.
`success: false` — снова не удалось, `row` — та же строка с обновлённым
`last_error`. `404`, если такой операции уже нет (например, её только что
удалили или она прошла сама между открытием карточки и правкой).

---

### DELETE `/admin/reclamations/bitrix-outbox/{id}`
Снять операцию с повторов (`admin`), `204` без тела — если чинить не
планируется (рекламация уже неактуальна, ошиблись при подаче и т.п.). Не
трогает саму рекламацию, только эту одну застрявшую операцию из очереди.
`404`, если такой операции уже нет.

---

### GET `/admin/reclamations/bitrix-detached`
Рекламации, чью карточку удалили в Bitrix (`admin`). Узнаём об этом либо из
события удаления на портале, либо по ответу `NOT_FOUND` при очередной отправке.
```json
[
  {
    "id": 16, "status": "in_progress", "description": "Не работает кнопка управления",
    "user_full_name": "Иванов Иван", "created_at": "2026-09-23T08:00:00Z",
    "bitrix_deleted_at": "2026-09-23T11:36:00Z"
  }
]
```
Заявка при этом **не удаляется и заново в Bitrix не заводится**: карточку
удалили осознанно, а претензия заявителя никуда не делась. Что с ней делать —
решение человека, поэтому она и висит здесь, а не исчезает молча. Пустой
ответ — норма.

В карточке рекламации то же самое видно по `bitrix_deleted_at`/`bitrix_item_id`:
заполнен `bitrix_deleted_at`, `bitrix_item_id` пуст — карточку удалили. Оба пусты
и `pending_create_outbox` не `null` — рекламация не доехала до Bitrix вообще
(см. `bitrix-outbox` выше). Оба пусты и `pending_create_outbox` тоже `null` —
обычная задержка, отправка ещё в процессе.

---

### DELETE `/admin/reclamations/{reclamation_id}`
Удаление рекламации (`admin`), `204` без тела. **Только для рекламаций из
списка `bitrix-detached`**, то есть тех, чью карточку уже удалили в Bitrix.
Для любой другой — `400`: у живой рекламации осталась бы карточка на портале
без пары у нас.

Удаление окончательное: вместе с рекламацией уходят её вложения и все
недоставленные операции. У заявителя она тоже пропадает из списка. В журнал
аудита пишется `reclamation.delete` — запись остаётся и после удаления.

## Рут `notifications` — уведомления

### GET `/notifications`
**История уведомлений** текущего пользователя — смены статусов заявок, гарантия, реклама. Параметры:
- `is_read=true|false`
- `type` — повторяемый: `?type=request_status&type=warranty_expiring`. Без него отдаются все типы
- `page`, `size`

История ведётся независимо от пуша: запись создаётся, даже если пуш не ушёл (выключен переключатель по типу — нет, см. ниже; но при **паузе** — да, запись будет). Сообщений в чатах здесь **нет**: они push-only, у чатов свои счётчики непрочитанного.

```json
{
  "items": [
    {
      "id": 1,
      "type": "request_status",
      "title": "Заявка одобрена",
      "body": "Ваш ШУ был успешно добавлен",
      "data": { "cabinet_id": 5 },
      "is_read": false,
      "created_at": "2026-05-15T10:00:00Z"
    }
  ],
  "total": 3, "page": 1, "size": 20, "pages": 1
}
```

Типы уведомлений (`type`), фактически отправляемые на данный момент:
- `warranty_expiring` — гарантия истекает через 30/10/1 день
- `promotional` — реклама: произвольное сообщение администратора (`broadcast`) либо заготовка из подборки (`promo/send`, в `data` будет `promo_id`)
- `chat_message` — новое сообщение от оператора или бота в чате
- `operator_requested` — пользователь запросил оператора (отправляется всем активным операторам и администраторам)
- `cabinet_alarm` — новая авария на ШУ (см. «Рут `cabinets`» → `GET /cabinets/{id}/telemetry`). `title` — `Авария ШУ «<название>»`, `body` — название именно этого бита из карты регистров, `data.cabinet_id`. Отправляется всем участникам проекта, которому принадлежит ШУ, **только на появление** аварии (переключение бита 0→1) — на снятие (1→0) push не шлётся, это видно и так по тому, что строка пропадает из ленты. Один пуш на каждую новую аварию, а не один общий на всё MQTT-сообщение — если разом взвелось несколько именованных бит, придёт несколько уведомлений
- `request_status` — решение по заявке. Отправляется заявителю при:
  - смене статуса сервисной заявки (в т.ч. когда статус приехал из Bitrix) — только при реальном изменении, плановый опрос Bitrix каждые 15 минут повторных уведомлений не шлёт;
  - смене статуса рекламации (см. «Рут `reclamations`») — текст зависит от нового статуса (на рассмотрении/в работе/отклонена/оформлена некорректно/исполнена), кроме `new` — начальный статус, заявитель видит его сразу после подачи, пуш не нужен;
  - одобрении/отклонении заявки на добавление ШУ (см. «Рут `admin: cabinet requests`»);
  - слиянии напрямую добавленного ШУ в проект при `POST /projects/add-by-qr`
    (см. врезку там же) — по одному уведомлению на каждый перенесённый ШУ;
  - отзыве доступа администратором: отвязка отдельно добавленного ШУ
    (`DELETE /admin/cabinets/{id}/users/{uid}`) или исключение из проекта
    (`DELETE /admin/projects/{id}/users/{uid}`) — причина из запроса в текст не попадает;
  - одобрении/отклонении заявки на документ;
  - смене телефона входа (см. раздел про смену номера).
- `bitrix_sync_error` — сбой синхронизации рекламации с Bitrix (п.8 ТЗ). Отправляется
  всем `admin`/`superadmin` (не `operator` — у него нет прав на обработку
  рекламаций) в двух случаях: рекламация не доехала до Bitrix и её создание
  легло в `bitrix-outbox` (только на первый сбой, не на каждый повтор раз в 15
  минут — иначе спамило бы, пока сбой не устранён), и когда карточку удалили в
  Bitrix (рекламация попала в `bitrix-detached`).

### POST `/notifications/mute`
**Пауза** — заглушить все уведомления на время.
```json
{ "hours": 2 }
```
`hours` — одно из `1`, `2`, `3`, `6`, `12`, `24`, либо `null` = бессрочно. Список закрытый: это кнопки в интерфейсе, а не свободный ввод. Ответ — те же `NotificationSettingsOut`.

Срок считается от момента вызова и **не продлевается**: нажали «на час», когда до конца прошлой паузы оставалось десять минут, — значит час, а не час десять.

Что именно глушится:
- **все пуши**, независимо от переключателей по типам — включая сообщения в чатах, ответы бота и служебный сигнал операторам. Проверка стоит в `send_push`, то есть покрывает и то, что идёт мимо `NotificationService`;
- **история продолжает копиться**. Пользователь просил не беспокоить, а не выбрасывать уведомления: вернувшись, он увидит в `GET /notifications` всё, что пришло за время тишины.

### POST `/admin/notifications/broadcast`
Разослать promotional уведомление. Только для администратора.
```json
{
  "title": "Новое обновление",
  "body": "Доступна новая версия документации",
  "role": null
}
```
- `role` — если `null`, рассылка всем активным пользователям. Если указать `"user"`, `"operator"` или `"admin"` — только по этой роли.

Ответ — счётчики, тот же формат, что у `POST /admin/notifications/promo/send`:
```json
{ "sent_to": 812, "skipped_opted_out": 47 }
```
`sent_to` — кому реально ушло (и запись в историю, и пуш), `skipped_opted_out` — сколько пропущено из-за выключенного `promotional`. Те же числа пишутся в журнал действий.

```json
[

    "body": "Регулярное ТО шкафа управления…", "data": { "screen": "service_request" } }
]
```

---

### POST `/admin/notifications/promo/send`
Разослать рекламу из подборки. Только для администратора. Параметры:
- `promo_id` — конкретная заготовка. Без него берётся **случайная**
- `role` — как в `broadcast`: `null` = всем активным, либо `user` / `operator` / `admin`

```json
{ "sent_to": 42, "skipped_opted_out": 7,
  "message": { "id": "remote_diagnostics", "title": "Удалённая диагностика", "body": "…", "data": {} } }
```
Уважает переключатель `promotional`, как и обычная рассылка. В `data` уведомления кладётся `promo_id` — по нему в приложении можно понять, какую именно заготовку показали. Действие пишется в журнал.

`400` — подборка пуста или файл не читается. `404` — заготовки с таким `promo_id` нет.

#### Файл с рекламой

Подборка лежит в `savt-backend/app/data/promo_messages.json` и правится руками:
```json
{
  "messages": [
    { "id": "service_reminder",
      "title": "Плановое обслуживание",
      "body": "Регулярное ТО шкафа управления продлевает срок службы…",
      "data": { "screen": "service_request" } }
  ]
}
```
- `id` — уникальный, попадает в `data.promo_id`;
- `title` до 255 символов, `body` до 1000 — длиннее обрезается;
- `data` — произвольные ключи для клиента (например, экран для перехода), значения приводятся к строкам;
- записи без `title` или `body` пропускаются с `WARNING` в логе, остальные всё равно разошлются.

Файл внутри образа только для чтения. Чтобы править без пересборки, положите свою копию рядом и укажите путь в `PROMO_MESSAGES_FILE` — например на уже примонтированной шаре NAS (`/mnt/projects/promo_messages.json`) или отдельным томом. Отсутствующий и битый файл рассылку не роняют: она просто не находит, что отправить, и говорит об этом `400`-м.

**Автоматическая рассылка** по умолчанию выключена. Включается `PROMO_AUTO_SEND_HOUR` — час (0–23), в который раз в сутки уходит случайная заготовка всем пользователям с ролью `user`. Пусто, не число или значение вне диапазона — рассылка не регистрируется вовсе, остаётся только кнопка. Так по умолчанию сделано намеренно: реклама уходит живым людям, и включать её стоит осознанно.

## RAG-бот Ася

Виртуальный ассистент, встроенный в чаты. Отвечает на вопросы пользователей по ШУ, используя базу знаний, FAQ и документацию ШУ.

### Принцип работы

```
Пользователь пишет сообщение
        ↓
Текст запроса → Yandex Embeddings (text-search-query) → вектор запроса
        ↓
pgvector cosine search → до 5 ближайших чанков из embeddings
  (если cabinet-чат → до 4 чанков ищутся среди документов конкретного ШУ,
   остальные — по всей базе embeddings; для больших документов (десятки
   чанков) лимит стоит поднимать дальше, если бот всё ещё не находит ответ,
   который точно есть в тексте)
        ↓
История диалога (до 5 предыдущих сообщений) + текущий вопрос с найденными чанками → YandexGPT-lite
        ↓
Ответ бота + цитата из источника → сохраняется в messages (sender = "Ася")
```

Ответ генерируется в фоне (`asyncio.create_task`) — пользователь не ждёт, основной запрос возвращается мгновенно.

> **Поиск по короткому ответу.** Сам вектор запроса строится из последнего
> сообщения пользователя — если оно короткое (≤4 слов, например «ШУ-52» в
> ответ на уточняющий вопрос бота «какая у вас модель?»), само по себе оно
> почти не несёт смысла для векторного поиска. В этом случае к нему
> подклеивается предыдущий реальный вопрос пользователя из истории **только
> для поиска по базе** — в промпт модели уходит фактический текст сообщения
> как есть, склейка не подменяет то, что пользователь на самом деле написал.
> Без этого бот «терял» тему разговора: спросили про красную кнопку, уточнили
> модель ШУ — а бот на «ШУ-52» отвечал так, будто это отдельный, ничем не
> связанный вопрос, потому что поиск по одному «ШУ-52» ничего не находил.

### Источники данных

| Тип | Метка в ответе | Индексируется |
|---|---|---|
| Записи FAQ | `[FAQ]` | При создании/изменении |
| Статьи базы знаний | `[База знаний]` | При создании/изменении/добавлении вложений |
| Документы ШУ | `[Документация ШУ]` | При загрузке |

> **Список ШУ проекта — отдельно от RAG.** Вопросы вида «есть ли ШУ-318 в
> этом проекте» или «когда гарантия на ШУ-52» в принципе не решаются поиском
> по документам — такого текста нигде не существует, это структурированные
> данные из таблицы `cabinets`, не из базы знаний. Для чата проекта (и чата
> конкретного ШУ — через его `project_id`, список остальных ШУ того же
> проекта) в промпт добавляется отдельный блок «ШУ этого проекта» с номером,
> типом и статусом гарантии каждого — помечен как точные данные из системы, а
> не из базы знаний, LLM не должна путать источники. Для чата поддержки (нет
> привязки к проекту) блок не добавляется — бот честно не знает, о каком
> проекте речь, лучше молчать, чем придумывать.

> **Документы с ограниченным или служебным доступом бот не использует.**
> `requires_approval: true` и `is_internal: true` (см. «Рут `admin: documents`»)
> исключаются из поиска — бот не должен пересказывать содержимое того, что
> пользователю по правилам недоступно, только потому что нашёл подходящий кусок
> текста. Для `is_internal` это на два уровня: такие документы вообще не
> индексируются (`index_document` не создаёт эмбеддинги, а удаляет уже
> существующие, если документ закрыли задним числом — см. `PATCH
> /admin/documents/{id}`), плюс сам поиск (`_retrieve_context`) отдельно
> отфильтровывает оба флага на случай рассинхронизации индекса.

### Поддерживаемые форматы вложений/документов

Перед индексацией любой файл нормализуется в обычный текст — дальше он чанкуется и эмбеддится одинаково, независимо от исходного формата.

| Формат | Извлечение текста |
|---|---|
| PDF с текстовым слоем | pypdf, постранично |
| PDF-скан (без текстового слоя) | автоматический fallback: встроенные изображения страницы (через pypdf, без poppler) распознаются через **Yandex Vision OCR** |
| `.docx` | python-docx — параграфы и таблицы |
| `.xlsx` | openpyxl — все листы, ячейки построчно |
| Изображения (`.jpg`, `.jpeg`, `.png`, `.webp`) | Yandex Vision OCR напрямую |
| `.doc` (Word 97-2003) | **не поддерживается** — пересохранить как `.docx` |
| `.xls` (Excel 97-2003) | **не поддерживается** — пересохранить как `.xlsx` |

OCR — тот же аккаунт/ключ Yandex Cloud, что и для YandexGPT/SpeechKit (`YANDEX_API_KEY`, `YANDEX_FOLDER_ID`), новых переменных окружения не требует. Для скана распознаётся только то, что реально не текстовое — если в PDF часть страниц с текстовым слоем, а часть — сканы, OCR прогоняется только по вторым (экономит вызовы API).

Если после индексации текст пустой — смотрите логи (`docker compose logs api | grep -i "разобрать\|извлеч.*пуст\|OCR"`): там указана точная причина (не найден файл, не удалось открыть, пустой текстовый слой, не поддерживаемый формат).

### Формат ответа бота

Бот даёт краткий ответ и добавляет цитату из найденного источника:
```
Гарантия на оборудование SAVT составляет 24 месяца с даты ввода в эксплуатацию.

> "Гарантийный срок устанавливается равным 24 месяцам со дня подписания акта ввода в эксплуатацию."
```

### Счётчик попыток и передача оператору

Два независимых сценария эскалации — предложил оператора сам бот, или его попросил пользователь без предложения:

**1. Бот исчерпал попытки и предложил оператора сам.** Если пользователь 3 раза подряд выражает недовольство (`bot_max_attempts`) — бот дописывает готовую фразу «Хотите, чтобы я позвал оператора?» и выставляет `chats.bot_offered_operator=true`. Следующий ответ пользователя трактуется **безусловно** именно по этому флагу, а не по счётчику:
- «да» → `operator_requested=true`, `bot_active=false`. Все активные операторы и администраторы получают push-уведомление `operator_requested` с номером чата.
- «нет» → счётчик `bot_no_count` сбрасывается, бот продолжает.
- любой другой ответ (например, сразу новый вопрос) → флаг снимается, сообщение уходит в обычный цикл RAG как новое.

> Сама LLM **не может** предложить оператора по своей инициативе — в системном промпте это явно запрещено, единственный источник предложения — код, через `bot_offered_operator`. Иначе модель могла упомянуть оператора раньше, чем счётчик реально доходил до порога, и последующее «да» пользователя не с чем было бы сопоставить — оно ушло бы в RAG как новый вопрос, и пользователь застрял бы в цикле.

**2. Пользователь сам просит оператора, без предложения от бота** (`chats.operator_insist_count`, слова из явного списка — «оператор»/«оператора», глаголы-команды и существительное «вызывай(те)»/«вызов(а)»/«позови(те)»/«зови»/«подключи(те)»/«переключи(те)» **сами по себе, без слова «оператор» рядом** (короткое повторное «вызывай» после первой просьбы значит то же самое), но не бытовые «да»/«нужно» — вне контекста прямого вопроса они ничего не значат). Бот не передаёт чат сразу — настаивает на своей помощи **1 раз** (`_OPERATOR_INSIST_LIMIT`), на вторую подряд такую просьбу передаёт немедленно, `operator_requested=true`, `bot_active=false`, операторам push с заголовком «Пользователь просит оператора». Счётчик пользователю не показывается, сбрасывается до нуля, как только пользователь получает обычный ответ без повторной просьбы оператора в том же сообщении.

> Растянутое написание для эмоции («вызываааааай», «нееееет») схлопывается
> перед сравнением со списками слов — 3 и более одинаковых буквы подряд
> сводятся к одной (`_ELONGATION_RE`). Двойные буквы не трогаются, они в
> русском обычное дело («касса», «группа»), а вот тройные в живых словах
> практически не встречаются — это касается всего разбора текста пользователя
> (сентимент, «да»/«нет» и т.п.), не только просьбы оператора.

Два подслучая настойчивой просьбы — по тому, есть ли в сообщении реальный вопрос:
- **Только просьба, без вопроса** («вызывай оператора», «ай вызывай оператора мне», «тогда вызывай») — до LLM не доходит вообще (`_is_bare_operator_request`, широкий список слов-«мусора»: местоимения, междометия, сами глаголы просьбы — не только буквально пустое сообщение): отвечать там нечему, а модель на пустой «вопрос» честно сказала бы «не могу вызвать оператора» или начала рассуждать вслух про то, что это решает система — рядом с настойчивой репликой бота это звучит как противоречие/бред. Вместо этого — фиксированное «Извините, может я всё-таки смогу вам помочь — задайте мне вопрос, и я обязательно постараюсь вам с ним помочь.», без обращения к LLM.
- **Вопрос + просьба одновременно** («не работает АСУ, позовите оператора») — бот отвечает по существу через обычный RAG-цикл, саму просьбу оператора никак не комментирует (см. системный промпт ниже) и ничего не приписывает от себя — угадать по ответу, что делать дальше, пользователь может только повторив просьбу.

- Оператор забирает чат: `POST /operator/chats/{chat_id}/take` → бот замолкает.
- Оператор возвращает чат боту: `POST /operator/chats/{chat_id}/return-to-bot`.

### Сбой Yandex API — пошаговый опрос

Если сам вызов Yandex (эмбеддинги или генерация) упал — ключ невалиден, закончились деньги, сеть недоступна — бот не выдаёт тишину/дежурную фразу и не передаёт чат оператору сразу. Вместо этого — пошаговый опрос (`chats.bot_down_intake_step`, 0 = не идёт, 1..5 = ждём ответ на вопрос с этим номером):
1. Бот сообщает о неполадке и задаёт **первый** из 5 уточняющих вопросов (кому вопрос — ШУ или общий, поломка или заявка на обслуживание, срочность, номер объекта, суть проблемы одним сообщением).
2. Каждое следующее сообщение пользователя, пока опрос идёт, трактуется **как ответ на текущий вопрос по счёту** — не через обычную логику бота (сентимент, просьба оператора и т.п.) — и бот присылает следующий вопрос.
3. После ответа на все 5 — `operator_requested=true`, `bot_active=false`, `bot_down_intake_step` сбрасывается в 0, операторам push с заголовком «Бот недоступен». Сама переписка (вопрос → ответ, вопрос → ответ) уже видна оператору в истории чата, отдельно собирать её не нужно.

Раньше все 5 вопросов уходили одним сообщением сразу с передачей чата оператору — не было способа отследить, ответил ли пользователь на все пункты или просто написал что-то в ответ на длинный список.

### Определение решённой проблемы

Если пользователь пишет «спасибо», «помогло», «разобрался» и т.п. — бот фиксирует `problem_status=resolved`, отправляет прощальное сообщение и прекращает follow-up цикл.

### Follow-up

Если пользователь написал и не получил решения (не отвечал дольше `BOT_FOLLOW_UP_MINUTES` минут) — бот сам пишет: «Удалось ли решить вашу проблему?». Follow-up отправляется только один раз — сбрасывается лишь когда пользователь снова выражает недовольство.

### Настройка (.env)

```env
YANDEX_FOLDER_ID=ваш_folder_id          # Folder ID из Yandex Cloud
YANDEX_API_KEY=ваш_api_key              # API-ключ сервисного аккаунта
YANDEX_GPT_MODEL=yandexgpt-lite         # Модель (yandexgpt-lite / yandexgpt)
BOT_FOLLOW_UP_MINUTES=60                # Через сколько минут бот пишет follow-up
BOT_MAX_ATTEMPTS=3                      # Сколько попыток до предложения оператора
```

> **Важно:** `YANDEX_FOLDER_ID` должен совпадать с folder сервисного аккаунта, к которому выдан `YANDEX_API_KEY`. Если это разные папки — Yandex вернёт 400.

### Первый запуск

После деплоя запустить полную индексацию (один раз):
```
POST /admin/bot/reindex?force=true
Authorization: Bearer {admin_token}
```
Ответ приходит сразу, не дожидаясь окончания (считает в фоне — иначе на большом объёме упрётесь в `504` от nginx):
```json
{ "status": "started", "message": "Индексация запущена в фоне, результат смотрите в логах" }
```
Итог смотреть в логах: `docker compose logs api --tail=50 | grep -i переиндекс`.

В дальнейшем `POST /admin/bot/reindex` (без `force`) индексирует только новые записи — уже проиндексированные пропускаются (`skipped`). Также индексация происходит автоматически при создании/изменении FAQ, KB и документов.

Если что-то было удалено в обход обычных эндпоинтов (см. `POST /admin/bot/prune` в разделе «Рут `admin: bot`» ниже) — эта ручка подчищает embeddings, оставшиеся от удалённых записей.

### Управление через БД (если нужно сбросить состояние)

```sql
-- Включить бота для всех чатов
UPDATE chats SET bot_active = true WHERE chat_type != 'notes';

-- Сбросить счётчик неудачных попыток и состояние эскалации оператора
UPDATE chats SET bot_no_count = 0, follow_up_sent = false, operator_requested = false,
  bot_offered_operator = false, operator_insist_count = 0, bot_down_intake_step = 0;

-- Посмотреть сколько чанков проиндексировано
SELECT source_type, COUNT(*) FROM embeddings GROUP BY source_type;
```

- `actor_role` — фильтр по роли: `admin` / `operator` / `user` / `system`
- `action` — фильтр по типу действия (строка)
- `entity_type` — фильтр по типу сущности (строка)
- `entity_id` — фильтр по ID сущности
- `date_from`, `date_to` — диапазон дат (ISO 8601)
- `search` — поиск по тексту
- `search_in` — где искать: `all` (по умолч.) / `action` / `entity_type` / `actor_name` / `payload`
- `sort_by` — `created_at` (по умолч.) / `action` / `entity_type` / `actor_role` / `actor_id`
- `sort_order` — `asc` / `desc`
- `page`, `size` — пагинация (по умолч. `1` / `50`, максимум `200`)

## Рут `admin: bot` — управление ботом

### POST `/admin/bot/reindex`
Индексация источников (FAQ, база знаний, документы ШУ). Только для администратора.

Параметры:
- `force=false` (по умолчанию) — индексирует только записи без существующих эмбеддингов (быстро)
- `force=true` — полная переиндексация всего (медленно, пропорционально объёму данных)

Считает в фоне — сам HTTP-запрос отвечает сразу (`202 Accepted`), не дожидаясь окончания. При заметном объёме данных `force=true` — это десятки/сотни синхронных вызовов Yandex API (эмбеддинги), что легко превышает `proxy_read_timeout` nginx, если считать синхронно внутри запроса.

Ответ:
```json
{ "status": "started", "message": "Индексация запущена в фоне, результат смотрите в логах" }
```
Итоговую статистику (`{"faq": 2, "kb_article": 0, "document": 5, "skipped": 28}`) смотреть в логах api (`docker compose logs api --tail=50 | grep -i переиндекс`) — там же видна ошибка, если фон упал.

На практике при штатной работе `skipped` почти всегда будет равен количеству всех существующих записей, а добавленных — `0`: создание и изменение записей уже индексируется автоматически в фоне (см. ниже), эта ручка нужна в основном для данных, попавших в БД в обход обычных create/update-эндпоинтов (восстановление из бэкапа, ручные правки), либо если фоновая автоиндексация когда-то не отработала.

### POST `/admin/bot/prune`
Удаляет embeddings, чей источник (FAQ/статья КБ/документ) больше не существует. Только для администратора.

Основной сценарий, когда это нужно: удаление категории каскадно сносит её статьи/вопросы на уровне БД (`ondelete=CASCADE`) в обход сервисного `delete()`, который обычно чистит embeddings сам — без дополнительной меры такой каскад оставлял бы осиротевшие embeddings. Поэтому сам каскад категорий дополнительно чистит embeddings дочерних записей заранее, а `prune` остаётся подстраховкой на нештатные случаи (восстановление из бэкапа, ручные правки в БД), не единственной защитой.

Ответ:
```json
{ "status": "ok", "removed": { "faq": 0, "kb_article": 3, "document": 0 } }
```

## Фоновые задачи (APScheduler)

Планировщик запускается автоматически при старте приложения.

### Уведомления об истечении гарантии

**Расписание:** каждый день в 09:00.

**Логика:**
- Находит все ШУ, у которых `warranty_ends_at` наступает ровно через 30, 10 или 1 день.
- Для каждого ШУ отправляет уведомление всем привязанным пользователям.
- Уважает настройки уведомлений пользователя — если `warranty_expiring: false`, push не приходит.
- Каждое уведомление (cabinet_id + порог в днях) отправляется **ровно один раз** — повторная отправка защищена таблицей `warranty_notif_log`.

**Пример push-уведомления:**
```
Заголовок: Гарантия истекает
Текст:     Гарантия ШУ «ШУ-18К» истекает через 30 дней
Data:      { "cabinet_id": 5, "days_left": 30 }
```

Тип уведомления в БД: `warranty_expiring`.

## Бэкапы базы данных

Скрипт `backup.sh` делает дамп PostgreSQL из Docker-контейнера, сжимает и хранит последние 5 файлов.

Гарантии скрипта:
- Дамп пишется во временный файл `.part` и переименовывается только при успехе — упавший `pg_dump` не оставит битый бэкап, который вытеснил бы хорошие при ротации.
- Пустой дамп считается ошибкой.
- Ротация: хранятся `BACKUP_KEEP_COUNT` (по умолчанию 5) последних файлов.
- Опционально копия выгружается в Yandex Object Storage (`BACKUP_S3_UPLOAD=1`) — переживёт смерть диска сервера. Использует ключи `YANDEX_STORAGE_*` из контейнера api, кладёт в `db-backups/` бакета.

Переменные окружения скрипта: `POSTGRES_DB` (умолч. `savt`), `POSTGRES_USER` (умолч. `postgres`), `BACKUP_KEEP_COUNT` (умолч. `5`), `BACKUP_S3_UPLOAD` (умолч. `0`), `BACKUP_DB_CONTAINER` / `BACKUP_API_CONTAINER` (умолч. `savt-backend-db-1` / `savt-backend-api-1`). Пароль БД не нужен — `pg_dump` внутри контейнера ходит через локальный сокет.

### Первый запуск (на сервере)

```bash
# Сделать скрипт исполняемым
chmod +x savt-backend/backup.sh

# Проверить вручную
cd savt-backend
./backup.sh
```

Бэкапы сохраняются в `savt-backend/backups/` с именем `savt_backup_YYYY-MM-DD_HH-MM-SS.sql.gz`.

### Автоматический запуск через cron

```bash
crontab -e
```

Добавить строку (запуск каждый день в 03:00, с выгрузкой в Object Storage):

```
0 3 * * * cd /path/to/savt-backend && BACKUP_S3_UPLOAD=1 ./backup.sh >> /var/log/savt-backup.log 2>&1
```

> Замените `/path/to/savt-backend` на реальный путь к директории на сервере.
> Если бакет Object Storage не настроен — уберите `BACKUP_S3_UPLOAD=1`.

### Проверить, что бэкапы реально делаются

```bash
crontab -l | grep backup            # строка на месте?
tail -n 20 /var/log/savt-backup.log # последние запуски без ошибок?
ls -lh savt-backend/backups/        # 5 файлов со свежими датами?
```

### Восстановление из бэкапа

```bash
# Распаковать и восстановить
gunzip -c backups/savt_backup_2026-05-18_03-00-00.sql.gz \
    | docker exec -i savt-backend-db-1 psql -U postgres -d savt
```

### Follow-up бота

**Расписание:** каждые 10 минут.

**Логика:**
- Находит все чаты где `bot_active=true`, `follow_up_sent=false`, и последнее сообщение пользователя старше `BOT_FOLLOW_UP_MINUTES` минут (по умолчанию 60).
- Отправляет от имени Аси: «Здравствуйте! Удалось ли решить вашу проблему? Если нет — я готов помочь.»
- Ставит `follow_up_sent=true` — повторно не пишет до нового сообщения от пользователя.

## Управление через CLI

```bash
# Создать суперадмина (только через CLI — намеренно нет API)
docker exec savt-backend-api-1 python -m app.cli create-superadmin <login> <password> [full_name]

# Создать администратора через CLI (альтернатива API POST /admin/users/admins, доступна суперадмину)
docker exec savt-backend-api-1 python -m app.cli create-admin <login> <password> [full_name]

# Создать оператора через CLI (альтернатива API POST /admin/users/operators)
docker exec savt-backend-api-1 python -m app.cli create-operator <login> <password> [full_name]
```

| Кто создаёт | Через CLI | Через API |
|---|---|---|
| Суперадмин | ✅ | ❌ только CLI |
| Администратор | ✅ | ✅ `POST /admin/users/admins` (суперадмин) |
| Оператор | ✅ | ✅ `POST /admin/users/operators` (администратор) |
