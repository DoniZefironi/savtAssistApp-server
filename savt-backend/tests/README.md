# Тесты

Отдельная тестовая БД — никогда не дев/прод. `BITRIX_WEBHOOK_URL` в тестах
всегда пустой (см. `conftest.py`): ни один тест не должен реально писать в
Bitrix, это явное решение, а не забытая настройка. Функции `bitrix_service`,
которые создают/меняют данные в Bitrix, в тестах подменяются (`mock_bitrix` в
`conftest.py`) — проверяется, что наш код вызвал нужную функцию с нужными
аргументами, а не то, что что-то реально ушло на портал. Читающие функции
(`get_reclamation_item` и т.п.) не подменяются глобально — кто их вызывает,
мокает сам в своём тесте.

## Поднять тестовую БД (один раз)

```bash
docker run -d --name savt-test-db \
  -e POSTGRES_USER=test -e POSTGRES_PASSWORD=test -e POSTGRES_DB=savt_test \
  -p 5433:5432 pgvector/pgvector:pg16
```

Применить миграции (использует тот же образ Python, что и прод — версия
SQLAlchemy в `requirements.txt` несовместима с Python 3.13+, локальный venv
на новом Python для этого не подойдёт):

```bash
cd savt-backend
docker run --rm -v "$(pwd):/code" -w /code \
  --network host \
  -e DATABASE_URL="postgresql+asyncpg://test:test@localhost:5433/savt_test" \
  python:3.12-slim bash -c "pip install -q -r requirements-dev.txt && alembic upgrade head"
```

(Если `--network host` недоступен на вашей платформе — создайте свою сеть
и подключите к ней `savt-test-db`: `docker network create savt-test-net &&
docker network connect savt-test-net savt-test-db`, а в команде выше замените
`--network host` на `--network savt-test-net` и `localhost` на `savt-test-db`.)

## Прогнать тесты

```bash
docker run --rm -v "$(pwd):/code" -w /code \
  --network host \
  -e DATABASE_URL="postgresql+asyncpg://test:test@localhost:5433/savt_test" \
  python:3.12-slim bash -c "pip install -q -r requirements-dev.txt && python -m pytest -v"
```

## Что уже покрыто

- `test_reclamation_bitrix_fields.py` — сборка нативных полей Bitrix
  (заводской номер/данные ПКИ) из `object_type`/`object_details`, чистая логика.
- `test_reclamation_outbox_retry.py` — повтор недоставленной операции
  (`_retry_outbox_row`): реальная БД, `bitrix_service` замокан.
- `test_auth_tokens.py` — вход, refresh-токены (одноразовость, окно гонки на
  10 секунд, детект кражи, лимит 5 активных сессий), выход. Ничего не мокает —
  Bitrix/Telegram тут вообще не задействованы, только БД + настоящий bcrypt/JWT.
- `test_project_access.py` — доступ к ШУ/проекту выводится из членства
  (`UserProject`), не хранится по-шкафно. Фиксирует и один несимметричный
  момент, требующий отдельного решения продукта — см. комментарий у
  `test_find_still_returns_membership_for_soft_deleted_project`.
- `test_bot_classification.py` — разбор реплик пользователя в чате с ботом
  (благодарность/жалоба, просьба оператора). Чистая логика, без БД и без LLM.
  Найден и исправлен реальный баг в `_explicit_operator_request`: отрицание
  проверялось только по одному слову перед совпадением, не по всей фразе —
  «Оператор не нужен, я сам разберусь» (без предшествующего вопроса бота)
  распознавалось как ПРОСЬБА позвать оператора, противоположное тому, что
  сказал человек. Теперь негатив учитывается в пределах двух слов перед
  триггером и сразу после него.
- `test_warranty_status.py` — классификация гарантии по дате (none/expired/
  expiring_soon/active), граница 30 дней. Чистая логика.
- `test_service_request_warranty.py` — `is_under_warranty` как снимок на
  момент создания заявки (и для ШУ, и для проекта), не пересчитывается
  задним числом. Сквозь реальный `ServiceRequestService.create()` — безопасно
  без моков, `bitrix_service.create_task()` сам не делает вызова без
  настроенного вебхука (пустой во всех тестах).
- `test_telemetry_decoding.py` — расшифровка регистров по битам (включая
  маску знакового 16-битного числа от контроллера), переходы бит между
  сообщениями, приоритет переопределения карты регистров для конкретного ШУ
  над стандартной картой (и что он не течёт на другие ШУ).
- `test_phone_change_requests.py` — смена номера только через заявку с
  решением администратора: занятость номера проверяется и на подачу, и
  повторно на одобрение (гонка — номер могли занять, пока заявка висела),
  `pending_rivals` (сколько ещё заявок претендует на тот же номер).
  `NotificationService`/`send_push` безопасны без моков — сами no-op без
  Firebase/токенов устройства.
- `test_document_access.py` — две независимые границы доступа к документам:
  `requires_approval` (документ виден в списке всем с доступом к проекту, но
  `file_url` остаётся `null` даже одобренным — скачивание только через
  `get_file_path`, проверяется на каждый запрос) и `is_internal` (служебный
  документ не виден вовсе, `NotFoundError`, не `PermissionDenied` — чтобы по
  коду ответа нельзя было узнать о его существовании).
- `test_cabinet_addition_requests.py` — заявки на добавление ШУ по фото:
  одобрение чинит принадлежность ничейного ШУ проекту заявителя, но ШУ,
  уже привязанный к ДРУГОМУ проекту — конфликт (`409`-уровня), не тихая
  перепривязка; заявки без `project_id` (старый формат) принадлежность ШУ
  не трогают вовсе.
- `test_reclamation_signed_urls.py` — подписанные ссылки на вложения
  рекламации перевыпускаются при каждом ответе, а не хранятся готовыми.
- `test_direct_cabinet_access.py` — два независимых пути доступа к ШУ
  (проект ИЛИ прямая привязка `UserCabinet`): объединение без дублей,
  удалённый ШУ, порядок пользователей; `find_active` скрывает удалённый проект.
- `test_qr_add_flows.py` — добавление проекта и ШУ по QR без одобрения,
  разбор кода из любого формата QR, слияние отдельно добавленного ШУ с
  проектом (прямая привязка снимается, чат остаётся, приходит уведомление),
  самостоятельное снятие своего ШУ.
- `test_admin_unlink.py` — админская отвязка ШУ и исключение из проекта:
  уведомление без причины, архивация чатов только этого пользователя, аудит;
  отдельно добавленные ШУ в карточке пользователя.
- `test_soft_deleted_project_gate.py` — по удалённому проекту нельзя открыть
  документы, чат, завести заявку; по живому — можно.
- `test_is_favorited.py` — `is_favorited` в KB, FAQ и документах, гость и
  чужое избранное дают `False`.
- `test_public_qr_page.py` — публичная страница QR: `intent://` без ссылки
  на саму страницу, формат пути, экранирование названия, адрес в QR без
  двойного слеша.
- `test_reclamation_admin_view.py` — `pending_create_outbox` в админской
  карточке рекламации и текст описания, уходящий в Bitrix.
- `test_delete_email.py` — очистка почты отдельной ручкой.
- `test_reclamation_admin_list.py` — поиск и сортировка в списке рекламаций
  админки: поля поиска, совмещение с фильтрами, `total` по всем найденным,
  пустые значения в конце при сортировке.

- `test_search_lists.py` — поиск во всех остальных списках: ШУ, проекты (в
  том числе по контактам заказчика), пользователи, сервисные заявки, заявки на
  регистрацию, база знаний, FAQ, журнал аудита, чаты. Запрос с цифрами
  (номер ШУ, телефон) находит только точное вхождение, а не соседний номер;
  слова ищутся с опечатками; в чатах `%` и `_` — обычные символы, не шаблон.

- `test_search_labels.py` — поиск по подписям (статус, тип, гарантия), по датам
  в разных форматах (с учётом минского часового пояса) и по нескольким словам
  в списках рекламаций, заявок и пользователей. Подпись ищется по началу слова:
  «Гарантийный» не находит «Негарантийный случай».

## Что ещё не покрыто (осознанно, следующий шаг)

`ReclamationService.create()` целиком — он пушит в Bitrix через
`asyncio.create_task(...)` на отдельной сессии (fire-and-forget), это
сознательный архитектурный выбор (чтобы ответ пользователю не ждал Bitrix), но
из-за него сам факт ухода в Bitrix тестом снаружи не поймать без доработки
(либо мокать `asyncio.create_task`, либо делать точку входа в фоновую задачу
awaitable для тестов) — отдельная тема для обсуждения, не для одной попытки.
